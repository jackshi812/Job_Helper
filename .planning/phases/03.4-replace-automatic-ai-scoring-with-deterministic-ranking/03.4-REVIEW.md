# Phase 03.4: Code Review Report

**Reviewed:** 2026-07-23T18:06:32Z
**Depth:** standard
**Files Reviewed:** 24
**Status:** issues_found

## Summary

The deterministic ranking cutover has several correctness and release-integrity defects that the current source-shape and in-memory tests do not exercise. The most serious issues can produce false title matches, permanently strand runs, lose resume-routing refreshes, certify a hosted worker whose bytes were never compared with the approved source, and hide valid open jobs from the feed.

This report was produced through the **generic-agent workaround** because typed `gsd-code-reviewer` dispatch was unavailable.

## Critical Issues

### CR-01: Multi-word acronym expansion creates false title matches

**File:** `supabase/functions/_shared/filters.ts:232-249,277-313`
**Issue:** `SYNONYM_INDEX` links every token in a multi-word expansion back to the acronym, and `titleConceptsMatch` accepts each preferred concept independently. Consequently, `Data Engineer` weak-matches the configured title `Data Scientist`: the job token `data` expands to `ds`, and the preferred concept `scientist` also accepts `ds`. The same bridge exists for aliases such as `swe`. This violates the all-concepts title requirement and ranks unrelated jobs as eligible.
**Fix:** Make aliases phrase-aware and directional. An exact job acronym such as `ds` may expand to the complete concept phrase `data scientist`, but an individual token such as `data` must not expand back to `ds` and then satisfy `scientist`. Add regressions proving `Data Engineer` does not match `Data Scientist`, while `DS` and `Data Scientist` still match as intended.

### CR-02: A third worker death leaves an item and owner permanently building

**File:** `supabase/migrations/0032_deterministic_ranking.sql:854-880`
**Issue:** A claim increments `attempts`, while eligibility requires `attempts < 3`. If the worker dies after the third claim but before staging, the item remains `claimed` with `attempts = 3`. It can never be reclaimed, never becomes `failed`, and the recovery sweep can only call a finalizer that returns `building` for the nonterminal item. The owner is then stuck indefinitely and cannot use the retry RPC because state never reaches `failed`.
**Fix:** Add a transactional expired-lease reaper before claiming. Expired claimed items at the attempt ceiling must atomically become `failed`, and their run/state must transition to the existing bounded failure/retry state. Cover death before staging on every attempt, especially the terminal attempt.

### CR-03: Saving preferences during a build leaves permanent pending/claimed queue rows

**File:** `supabase/migrations/0032_deterministic_ranking.sql:592-596`
**Issue:** Superseding a building run marks only the run as `stale`; its `pending` and `claimed` items remain nonterminal. `claim_deterministic_ranking_work` only joins building runs, so those rows can never be processed. Repeated saves accumulate orphan queue rows, make global queue counts permanently nonzero, and can cause in-flight staging to be reported as worker failures even though the newer run is healthy.
**Fix:** Introduce a terminal `stale`/`cancelled` item status (or delete unneeded staging rows under a documented retention policy) and transition every nonterminal item when its run is superseded. Queue and release probes should count only actionable current-run work. Add a real concurrency test for save-during-claim and repeated saves.

### CR-04: Finalization can erase a newer resume-routing refresh request

**File:** `supabase/migrations/0032_deterministic_ranking.sql:1196-1205`
**Issue:** Every successful finalizer unconditionally sets `route_refresh_requested_at = null`. If an upload, deletion, or extraction signals a route refresh while any ranking run is building, that newer timestamp is erased when the older run finalizes. The published Best-fit/runner-up IDs can therefore remain stale indefinitely. This race is especially likely when extraction completes while a full-snapshot run is processing.
**Fix:** Consume the request only when a route run is enqueued (the update at lines 1560-1564 already does this). Do not clear it in the generic finalizer. If stronger acknowledgement is needed, capture the request timestamp on the route run and clear with a compare-and-set only when no newer request exists. Add request-during-preference-run and request-during-route-run tests.

### CR-05: Release verification substitutes local hashes for hosted function hashes

**File:** `scripts/verify-phase-03-4-release.mjs:1058-1068`
**Issue:** `functionProbe` reads only hosted metadata (`id`, `version`, `status`, `verify_jwt`) but fills `indexSha256` and `bundleManifestSha256` directly from the local inventory passed by the caller. Later comparisons therefore prove that the local files match locally recorded evidence, not that the deployed Supabase function contains those bytes. A stale or otherwise different hosted worker can pass the claimed exact-source release gate.
**Fix:** Download or retrieve the deployed function bundle/source for the exact hosted version and hash those remote bytes independently. Compare the remote manifest and entry hash to the approved local inventory. Fail closed when the platform cannot provide verifiable deployed bytes; do not populate hosted probe fields from local values.

### CR-06: The feed applies the 200-row limit before rejecting closed jobs

**File:** `web/src/lib/feed.ts:156-169`
**Issue:** `listFeed` fetches up to 200 deterministic rows without a database predicate on `jobs.status`, then removes closed rows in JavaScript. Recently posted closed jobs can consume the entire database limit, hiding valid open matches and making the Dashboard report fewer—or zero—jobs even when open eligible rows exist.
**Fix:** Make `jobs` an inner embedded relation and apply `jobs.status = 'open'` in PostgREST before ordering and limiting. If company identity is required for visibility, move that eligibility into the database query or paginate until 200 valid rows have been collected. Add a test with more than 200 newer closed rows followed by open rows.

### CR-07: Explicit foreign countries outside a short hard-coded list remain eligible

**File:** `supabase/functions/_shared/deterministic-ranking.ts:234-266`
**Issue:** The location contract rejects explicitly foreign locations, but the classifier recognizes only a hand-maintained subset. Explicit values such as `Prague, Czech Republic`, `Bucharest, Romania`, or `Lagos, Nigeria` return `unknown` and remain eligible. This is not a countryless ambiguous city case; the country is stated and the hard filter is bypassed.
**Fix:** Use a reviewed, exhaustive set of ISO country names and supported aliases, excluding the United States, plus unambiguous foreign region markers. Keep city-only strings and countryless `Remote` as `unknown`. Add table-driven coverage across all accepted country names and aliases.

### CR-08: The advertised 45-second worker bound is not enforced around awaited I/O

**File:** `supabase/functions/score-tick/index.ts:268-289,312-345,401-425`
**Issue:** The deadline is checked only between batches and recovery iterations. `loadJobs`, `loadResumeExtracts`, `Promise.allSettled(processRow...)`, staging RPCs, and finalizer RPCs have no deadline or abort signal. One stalled request can hold the invocation past 45 seconds (or until platform termination), so the source constants and verifier do not establish the claimed non-overlap with the one-minute scheduler.
**Fix:** Create a deadline-scoped `AbortController` and attach its signal to every PostgREST/RPC request, with per-operation time remaining. Stop claiming new work before the deadline and ensure aborted items are safely lease-reclaimable. Test a never-resolving load/stage/finalize adapter and assert bounded return or controlled termination.

## Warnings

### WR-01: Resume mutations report failure after the durable mutation already succeeded

**File:** `web/src/lib/resumes.ts:71-94,113-128`
**Issue:** Upload and delete perform their irreversible storage/database changes before requesting a route refresh. If only the refresh RPC fails, the whole helper rejects, so the UI tells the user the upload/delete failed even though it committed. Retrying an upload can create duplicates, while retrying a delete reports confusing missing-object behavior.
**Fix:** Move refresh signaling into a database-side trigger/outbox tied to the metadata mutation, or treat the post-commit signal as separately retryable/best-effort and return the successful primary operation truthfully. Add tests for RPC failure after successful insert/delete.

### WR-02: Browser validation does not cover the database bounds for most preference arrays

**File:** `web/src/lib/preferences.ts:147-156`
**Issue:** Client validation enforces count/byte limits only for title exclusions. Titles, locations, include keywords, and general exclude keywords share the same server limits (50 entries, 4,096 serialized bytes, trimmed 1–200 character entries) but the form permits invalid values and then shows a generic “check the highlighted values” error without highlighting the offending chips.
**Fix:** Create one shared text-array validator matching `is_valid_ranking_text_array` and apply it to every preference field before RPC submission. Surface a field-specific accessible error and focus the first invalid chip input.

### WR-03: “Integration” and liveness tests reimplement simplified models instead of executing the SQL/worker

**File:** `web/tests/deterministic-ranking-snapshot.integration.test.ts:29-65`
**Issue:** The snapshot test validates a standalone TypeScript model, and the liveness suite similarly models a reduced state machine. Neither executes migration 0032 or the worker RPC protocol. The models omit route-refresh timestamps, stale item statuses, lease exhaustion, and awaited-I/O deadlines—the same areas where the runtime defects above occur—so passing tests provide misleading coverage.
**Fix:** Run migration 0032 against disposable Postgres/Supabase in tests and exercise authenticated/service RPCs with concurrent transactions and lease-time manipulation. Keep pure models only as supplemental unit tests, not as the integration or liveness gate.
