`POST https://api.supabase.com/v1/projects/{project_ref}/database/query`
with `SUPABASE_ACCESS_TOKEN`. The behavior verifier obtains the service-role
key with the project-local CLI `projects api-keys --project-ref {project_ref}
--reveal --output json`, parses it only in memory, then performs behavior
assertions through two independently authenticated publishable-key sessions.
Neither credential may be printed, persisted, placed in an approval token, or
written to evidence.

Catalog parity must assert these exact deployed contracts before PASS:
- `create_manual_application(p_company text, p_title text, p_apply_url text, p_notes text, p_stage text, p_occurred_on date) returns table(application_id uuid, duplicate_warning boolean)`.
- `dashboard_applied_applications() returns table(application_id uuid, company text, title text, location text, apply_url text, applied_on date, current_stage text, current_stage_date date)`, with nullable HTTPS/no-credentials `apply_url` and `applied_on` selected from the earliest Applied event by `ORDER BY occurred_on ASC, created_at ASC, id ASC LIMIT 1`.

`verify-tracker-schema.ts` accepts only `--mode preflight|assert-hosted`,
`--migration <path>`, `--output <path>` for preflight, and
`--preflight <path> --evidence <path>` for assert-hosted.
`verify-tracker-rls.ts` accepts only `--mode contract|hosted` and, for hosted,
`--preflight <path> --catalog-evidence <path> --evidence <path>`. The
approval-bound migration/verifier/fixture digests are read from the preflight
and recomputed; they are not accepted from an untrusted free-form payload.
