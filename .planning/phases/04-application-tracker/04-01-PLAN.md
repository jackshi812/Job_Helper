Existing browser seam:
- `markJobApplied(userJobId: string): Promise<void>` in `web/src/lib/feed.ts` currently writes `user_jobs.applied_at` directly; replace it with `Promise<string>` returning the tracker application UUID from `mark_job_applied`.
- `safeApplyUrl(value)` in `web/src/lib/feed.ts` accepts only HTTPS URLs without embedded credentials; tracker manual and snapshot links use the same rule.
- Dashboard already calls `markJobApplied` from the Mark Applied button. Preserve that call site so changing the library function immediately crosses UI → RPC → database.

New database contracts created here and consumed in Plans 03–05:
- `applications` stores one owner-scoped `system` or `manual` aggregate with immutable system snapshots, manual fields, notes, pin, optional owner-bound resume, and database-derived current stage/date.
- `application_stage_events` stores repeated chronological events ordered by `occurred_on`, `created_at`, then `id`.
- Manual-create RPC: `create_manual_application(p_company text, p_title text, p_apply_url text, p_notes text, p_stage text, p_occurred_on date) returns table(application_id uuid, duplicate_warning boolean)`. It returns exactly one row; optional location and description are absent from this signature and use the post-create field RPC.
- Other RPCs: `mark_job_applied(p_user_job_id uuid) returns uuid`, `set_application_pin(p_application_id uuid,p_pinned boolean)`, `update_application_text_field(p_application_id uuid,p_field text,p_value text)`, `set_application_resume(p_application_id uuid,p_resume_id uuid)`, `append_application_stage(p_application_id uuid,p_stage text,p_occurred_on date)`, `update_application_stage_event(p_event_id uuid,p_stage text,p_occurred_on date)`, and `delete_application_stage_event(p_event_id uuid)`.
- Read projection: `dashboard_applied_applications() returns table(application_id uuid, company text, title text, location text, apply_url text, applied_on date, current_stage text, current_stage_date date)`. It returns owned system snapshots independent of a live/open `jobs` row; `apply_url` is nullable and emitted only when it passes the HTTPS/no-credentials rule. `applied_on` is the first Applied event under `ORDER BY occurred_on ASC, created_at ASC, id ASC LIMIT 1`, so later repeated Applied events never rewrite original history.
- TypeScript: `createManualApplication(input: ManualApplicationCreateInput): Promise<ManualApplicationCreateResult>` accepts `{ company, title, applyUrl, notes, stage }`, sends exactly `p_company`, `p_title`, `p_apply_url`, `p_notes`, `p_stage`, and an automatically derived current date as `p_occurred_on`, and does not expose a draft date input; `listDashboardAppliedApplications(): Promise<DashboardAppliedApplication[]>` parses the exact projection columns above into camelCase `{ applicationId, company, title, location, applyUrl, appliedOn, currentStage, currentStageDate }`.

## Trust Boundaries

OWASP ASVS Level 1; any HIGH or CRITICAL finding blocks completion.

| Boundary | Description |
|---|---|
| Dashboard browser → `mark_job_applied` | Untrusted user-job UUID enters a transaction that may snapshot shared job data and mutate owner state |
| Authenticated browser → tracker tables/RPCs | Application IDs, fields, stage values, dates, URLs, notes, and resume IDs are attacker-controlled |
| `applications` → `application_stage_events` | Parent/event ownership and derived current stage must remain consistent |
| `applications.resume_id` → private `resumes` | A guessed resume UUID must never create a cross-owner association |
| Stored snapshots → browser rendering | Provider HTML and external URLs remain untrusted after persistence |
| Legacy `user_jobs.applied_at` → tracker backfill | Existing owner history must migrate without loss, duplication, or re-parenting |
