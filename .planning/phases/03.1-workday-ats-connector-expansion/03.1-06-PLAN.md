<objective>
Convert the Workday adapter from a single hardcoded Capital One identity to a per-tenant adapter, and replace its all-or-nothing detail contract with bounded incremental enrichment.

Purpose: research §3.3 established that sequential per-posting detail fetches cannot complete inside one Edge invocation for tenants listing thousands of postings. Under the inherited contract every large tenant would degrade permanently for a capacity reason rather than a trust reason, and could therefore never accumulate the clean windows D-20 requires. This plan splits list completeness from detail enrichment while preserving closure safety exactly.
Output: a per-tenant `pollWorkday` with a monotonic invocation deadline, a hard detail-request ceiling, and list-only ingestion for un-enriched postings.

## Two design decisions this plan makes explicit

**WD-ID — the Workday external identifier becomes the canonical `externalPath`.**
The list response carries `externalPath`; the stored external identifier currently comes from the post-detail `jobPostingInfo.id`, which is unavailable until after a detail fetch. Under bounded enrichment some postings will have no detail this tick, so a detail-derived identifier cannot exist for every posting in a complete observation, and the known-identifier set the scheduler passes in could never be matched against a list posting. Deriving the identifier from the path by suffix convention was rejected — it is a per-tenant guess across eight undocumented tenants.

Instead the adapter uses the already-unique, already-validated, always-present `externalPath` as the external identifier. This is safe to change now and only now: migration 0016 records that Phase 02.1 expects zero Workday job rows while Capital One is experimental and unclaimable, so no stored row's identity is being rewritten. Plan 08's migration asserts that zero-row precondition in SQL before the allowlist constraint lands, so if the assumption is ever false the migration fails rather than silently splitting job identity.

**WD-COUNT — the adapter returns a FULL reconciled observation; the predicate never narrows it.**
`isCredibleCompleteObservation` requires the expected count to equal the returned job count. If the predicate removed postings from the returned list while the expected count still held the provider total, every predicate-filtered observation would silently lose closure credibility and no tenant could ever accumulate D-20's three clean windows — the same fail-closed-for-a-capacity-reason trap this plan exists to prevent. So the adapter returns every list posting with the expected count equal to the provider total. The predicate is passed in for one purpose only: choosing which unknown postings are worth a detail request. Plan 09 applies the predicate to derive the ingest set and re-bases the expected count for the lifecycle call.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| edge function -> tenant candidate-experience host | Outbound unauthenticated request to an undocumented third-party contract |
| provider list and detail payloads -> stored snapshots | Untrusted input that determines what is ingested and what may be closed |
| tenant A identity -> tenant B origin | Cross-tenant boundary that must never be crossable through a provider-supplied path |
