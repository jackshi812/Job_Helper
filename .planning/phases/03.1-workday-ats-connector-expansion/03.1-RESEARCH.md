## 2. Inherited Rules Carried Forward (non-negotiable)

From `02.1-CONTEXT.md`, migration `0016_workday_experimental.sql`, and the Phase 02.1 summaries:

- **R-1 — No tenant generalization.** One proven Workday tenant never authorizes another. Phase 02.1 proved the fixed Capital One identity and explicitly refused to generalize it (`02.1-06-SUMMARY.md`).
- **R-2 — Closure requires credible positive evidence.** A failed, drifted, capped, or implausibly empty observation preserves prior jobs and must never close them (`credibleForClosure: false`).
- **R-3 — Provider-confirmed zero is `implausible_empty` for undocumented contracts.** There is no safe local mechanism to distinguish "board is empty" from "board is broken."
- **R-4 — Independent, repeated, closure-credible evidence per tenant before scheduled polling.** Minimum three distinct server-timed windows, zero warnings, reconciled counts. Evidence must be per tenant, never per provider.
- **R-5 — Defense in depth on activation.** Scheduling exclusion is enforced at both the SQL claim boundary (`claim_due_companies`) and in application dispatch (`pollConnector`), so a drifted `activation_state` alone cannot start polling.
- **R-6 — Server-authoritative identity.** All tenant/site identity is derived and validated server-side in `verify-board`; pasted URLs are never trusted.
- **R-7 — Honest unsupported state.** If a provider's public path is authenticated, prohibited, bot-blocked, or too unstable to poll safely, record `unsupported_with_reason` rather than disguising scraping as coverage (D-04).

## 3. Track A — Workday Tenant Identity Findings

> **PARTIALLY SUPERSEDED by `03.1-CONTEXT.md`.** The identity model, the CXS contract shape, and the per-tenant safety findings in this section are current and are what plans 05 through 09 implement. **The company set is not current:** the pilot is eight companies and **PIMCO is excluded** (D-02). Treat any nine-company or ten-company framing below as historical. The authoritative tenant list is `supabase/functions/_shared/adapters/workday-allowlist.ts` as built by plan 05.

### 3.1 The identity model

A Workday candidate board is identified by three server-owned tokens, not one:

```
https://{tenant}.{region}.myworkdayjobs.com/{site}
       ↳ CXS root: https://{tenant}.{region}.myworkdayjobs.com/wday/cxs/{tenant}/{site}
       ↳ list:     POST {CXS root}/jobs   body {appliedFacets:{}, limit, offset, searchText:""}
       ↳ detail:   GET  {CXS root}{externalPath}
```

Existing source-key convention (from `workday.ts` / migration 0013): `workday:{region}:{tenant}:{site}`.

**Critical finding — the tenant slug is not the company.** Apollo Global Management's careers board is hosted on the **`athene`** tenant (`athene.wd5.myworkdayjobs.com/Apollo_Careers`); Athene is an Apollo subsidiary. Any code that derives a display company name from the tenant slug would label Apollo's jobs "Athene." Company display names must come from a reviewed allowlist entry, never from the slug and never from provider free text.

**Second finding — one company can expose several sites.** Visa exposes both `Visa` and `Visa_Early_Careers`; Workday exposes `Workday`, `Workday_Early_Career`, and `Workday_Executive_Site`. Each site is a **separate source identity** with its own completeness and closure semantics. Selecting one site per company is a coverage boundary that must be recorded, not silently treated as full coverage.

**Third finding — locale-prefixed paths exist** (`/en-US/External`, `/en-GB/Apollo_Careers`). These are display variants of the same site. Detection must canonicalize to the bare single-segment site token and reject locale-prefixed and faceted URLs rather than minting a second identity for the same board.

### 3.3 Blocking scale finding — detail fan-out will not fit the invocation budget

This is the highest-impact discovery of this research and it changes the shape of the phase.

The current adapter fetches **one detail request per posting, sequentially**, with a 15-second timeout and caps of 2,000 jobs / 2,000 details. Capital One tolerated this. The pilot tenants will not:

- Visa, BMO, and State Street each list postings in the **thousands**.
- CXS list pagination is capped at `limit: 20` per page, so a 2,000-posting board needs **100 list requests plus 2,000 detail requests** for one full observation.
- Supabase Edge Functions have a per-invocation wall-clock cap (~150 s on the free plan). Sequential detail fetches make a full observation of a large tenant **structurally impossible** within one invocation.
- Egress also matters: the Supabase free plan allows 5 GB/month, and full detail bodies for thousands of postings polled every few minutes would threaten it.

Under the current contract, every large tenant would return `page_cap_exceeded` / timeout → `credibleForClosure: false` forever. Those tenants could never accumulate the three clean windows R-4 requires, so **the pilot would fail closed permanently, for a capacity reason rather than a trust reason.**

**Recommended resolution — split the completeness contract into list-completeness and detail-enrichment:**

- The **list** observation remains the sole closure authority. It is `complete` only when every page reconciles against the provider's `total`, no page/byte/schema cap trips, and no duplicate `externalPath` appears. Closure credibility is unchanged and still requires a fully reconciled positive list. R-2 and R-3 are preserved exactly.
- **Detail fetching becomes bounded incremental enrichment.** Only postings whose `externalPath`/external ID is not already stored get a detail fetch (the `knownIds` pattern already used by the Greenhouse adapter), under a monotonic per-invocation deadline (the pattern already used by the SmartRecruiters adapter) and a hard request ceiling.
- A posting whose detail was not fetched this tick is ingested from list fields only (title, location, canonical URL) with **`snapshotPartial: true`**, and is enriched on a later tick. It is never dropped and never fabricated.

This is a genuine change to the inherited Workday contract and **requires explicit owner confirmation before planning proceeds** (see CONTEXT §Open Decisions). The safety property it must preserve is exact: *a job may be closed only on a fully reconciled, positive, complete list observation.* Missing detail bodies must never authorize closure and must never be treated as an empty board.

**Rejected alternatives:**
- *Raise the caps and hope* — does not fit the wall clock; produces permanent degradation.
- *Parallel detail fetching* — multiplies load on an undocumented endpoint and invites rate limiting; contradicts the bounded-politeness posture already established.
- *Drop detail entirely* — loses description text, which Phase 3 scoring depends on.

### 3.4 Cadence and sharding

Nine tenants polled on every tick would exceed both wall clock and politeness limits. The existing pattern (shard across ticks, one slice per tick) applies directly: with pg_cron at one-minute granularity and one tenant per tick, each tenant is refreshed roughly every nine minutes — inside the 5–15 minute product target — while each invocation handles a single tenant's list sweep plus a bounded detail batch. Per-tenant claim staleness must be independent so one slow or failing tenant cannot delay or block the others.

### 3.5 Compliance posture

The CXS endpoints are the same unauthenticated JSON calls the public careers page itself makes. Nothing here involves login, CAPTCHA bypass, or concealment of automated traffic, and it remains distinct from the prohibited LinkedIn surfaces. The contract is nonetheless **undocumented**, which is precisely why R-1 through R-5 exist. Politeness bounds (sequential requests, per-host throttle, small caps, honest user agent) must be retained per tenant, not per provider.

## 4. Track B — SAP SuccessFactors

> ## ⚠ FULLY SUPERSEDED — this track is NOT part of Phase 03.1
>
> **`03.1-CONTEXT.md` removed SuccessFactors from this phase entirely.** The bounded spike recommended below **was not adopted** and must not be executed here. No plan in this phase may add SuccessFactors code, a schema value, a detection branch, a catalog change, or a spike of any kind; plan 10 Task 3 enforces its total absence as a standing test. This section is retained solely as the evidence base for deferring it to its own later phase. **Nothing below is an instruction.**

**Finding (historical): there is no documented public jobs API. Recommend planning this as a bounded evidence spike whose most likely honest outcome is `unsupported_with_reason`.**

| Access path | What it is | Verdict |
|---|---|---|
| OData v2 `/odata/v2/JobRequisition` | The official API | **Unusable.** Requires per-tenant employer credentials and "Recruiter Operator" permission; Basic Auth is deprecated in favor of OAuth2 + SAML assertion with an X.509 certificate. Not available to us for arbitrary employers. Matches the 02.1 "authentication mismatch" risk exactly. |
| Career Site Builder `POST /services/recruiting/v1/jobs` | The undocumented call the public career site makes client-side. Body carries `locale`, `pageNumber`, `sortBy`, `keywords`, `location`, `facetFilters`, `brand`, `categoryId`. | **Undocumented, tenant-variable, and metadata-only** — reported to omit full job descriptions. Host varies by data center (`career{n}.successfactors.com`, `.eu`, plus ~15 more) and by tenant configuration. |
| `/sitemap.xml` on the career-site host | Lists posting URLs | HTML detail pages behind it; this is arbitrary-HTML scraping, which D-07 and the "What NOT to Use" list already exclude. |

Three independent problems compound: the endpoint is undocumented (like Workday), the host is not derivable from the company name (unlike Workday), and the response reportedly lacks descriptions that Phase 3 scoring needs. Workday at least has a single deterministic host formula; SuccessFactors does not.

**Recommended plan shape:** one bounded, read-only spike that attempts identity resolution and a single observation for two or three named real employers, records the evidence, and then either (a) proposes a closed allowlist contract on the strength of that evidence, or (b) records `unsupported_with_reason` and stops. The spike must not be allowed to expand into a generic HTML scraper. **Do not commit this phase to shipping a SuccessFactors connector.**

## 5. Track C — Paylocity Recruiting

**Finding: this is the one genuinely documented public contract in the phase and the lowest-risk deliverable. Recommend implementing it first.**

- **Official documentation:** `https://recruiting.paylocity.com/recruiting/v2/api/feed/documentation` (v1 equivalent also exists).
- **Endpoint:** `GET https://recruiting.paylocity.com/recruiting/v2/api/feed/jobs/{guid}` with optional repeatable `departments` and `locations` filters. JSON by default; XML via `Accept`.
- **Identity:** a per-company GUID. It is public, and it appears in the employer's own public careers URL (`recruiting.paylocity.com/recruiting/jobs/All/{guid}/{Company-Name}`), so **the GUID is derivable server-side from a pasted careers URL** — this fits the existing `detect.ts` → `verify-board` boundary without inventing a new credential concept. It is a public board identifier, not a secret; it must still be validated as a strict UUID and never accepted from client-supplied free text without re-derivation server-side.
- **Response shape:** root `{ displayName, jobs[] }`; each job carries `jobId`, `title`, `companyName`, `applyUrl`, `displayUrl`, `listUrl`, `createdUtc`, `publishedDate`, `description`, `requirements` (both HTML), `jobLocation{ address, city, state, zip, metro, locationDisplayName }`, `jobCode`, `salaryDescription`, `hiringDepartment`, `jobTypes`.
- **Descriptions are included in the list response** — no per-job detail fan-out, so none of the Track A scale problem applies.
- **Gaps to resolve during planning/execution:** the documentation states no pagination model, no rate limits, and no terms. Treat the response as a **single whole-board snapshot**, and treat the absence of a documented pagination or count field as meaning there is no independent total to reconcile against. Completeness must therefore rest on: HTTP 200, JSON content type, a well-formed root object with a non-empty `displayName`, an array `jobs`, every job passing schema validation, and a byte cap. A zero-length `jobs` array has no independent corroboration and must be treated as `implausible_empty` under R-3 — same posture as Workday.
- **Company identity:** prefer root `displayName`, cross-checked against per-job `companyName`; a mismatch is drift and is closure-ineligible.

## 7. Risks

| Risk | Severity | Mitigation |
|---|---|---|
| Detail fan-out exceeds Edge wall clock for large tenants | **blocking** | §3.3 split contract; per-invocation deadline; incremental `knownIds` detail |
| Tenant slug misidentifies the company (Apollo/`athene`) | high | Display names come from the reviewed allowlist only, never from slug or provider free text |
| A single allowlist widening silently authorizes an unproven tenant | high | Allowlist membership grants *eligibility to gather evidence*, never scheduling. Per-tenant proof is a separate, independently recorded gate at both SQL and dispatch boundaries |
| One failing tenant closes another tenant's jobs | high | Per-company observation and closure; explicit cross-tenant isolation regression test |
| Multi-site companies (Visa, Workday) treated as full coverage | medium | Record the selected site as an explicit coverage boundary per company |
| Egress growth from 9 tenants of full detail bodies | medium | Incremental detail, sharded cadence, byte caps; monitor against the 5 GB free-tier ceiling |
| SuccessFactors spike expands into a generic scraper | medium | Spike is bounded and read-only; `unsupported_with_reason` is an accepted, expected outcome |
| Paylocity has no documented total to reconcile | medium | Whole-snapshot semantics; empty array is `implausible_empty`; strict schema and byte caps |
| Undocumented CXS schema drift across nine tenants at once | medium | Per-tenant fixtures; drift degrades only the affected tenant |
