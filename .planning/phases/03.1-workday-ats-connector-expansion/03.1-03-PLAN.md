<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authenticated user -> `verify-board` | A signed-in user submits a URL that selects a server-owned identity |
| `verify-board` -> companies table | Server-owned write of identity and activation state |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03.1-03-01 | Elevation of privilege | activation state on insert | high | mitigate | The new provider is added to the staged set, so the server writes a staged state with a zero success counter; the client cannot supply an activation state and cannot reach an active state without three server-timed accepted observations |
| T-03.1-03-02 | Spoofing | company name on the created row | medium | mitigate | The company name is read from the verified observation, which the adapter derived from the reviewed root display name and cross-checked per job (D-27); the pasted URL's display segment is never used |
| T-03.1-03-03 | Tampering | source key and canonical careers URL | high | mitigate | Both are derived server-side from the validated GUID through the shared deterministic derivation; client free text never reaches either |
| T-03.1-03-04 | Information disclosure | verification error surface | medium | mitigate | The existing bounded-code filter collapses any provider error that is not a short lowercase code, so provider internals cannot leak into the response |
| T-03.1-03-05 | Elevation of privilege | registry exhaustiveness | medium | mitigate | `satisfies Record<ProviderId, ProviderConnector>` plus the three exact registry-array assertions make an unreviewed registry addition a compile or test failure |
</threat_model>
