<domain>
## Phase Boundary

Add Paylocity Recruiting to the executable connector pipeline and perform a bounded SAP SuccessFactors employer pilot. A SuccessFactors employer may become executable only when its exact public contract is proven safe and repeatable; otherwise the phase records an honest `unsupported_with_reason` disposition.

**In scope:**
- Paylocity detection, canonical identity, adapter, verification, staged activation, recurring polling, persistence, scoring, and dashboard delivery
- Exact-employer SuccessFactors research, allowlisted identity, bounded adapter work where a safe public contract is proven, and truthful unsupported evidence where it is not
- Complete-observation closure safety, deduplication, independent source health, and recovery after transient failure
- Local fixtures, integration tests, schema migration, deployment checkpoint, and live provider evidence

**Out of scope:**
- Any new Workday tenant, generalized Workday detector, Workday allowlist, Workday scheduler change, or Workday schema widening
- Changes to the shipped Capital One Workday identity, adapter, activation, filter, or polling contract
- Generic HTML scraping, browser automation, CAPTCHA bypass, authenticated/private provider APIs, or credentials obtained from employers
- Entry-level experience extraction and company visibility controls, which remain Phase 03.2

</domain>

<decisions>
## Implementation Decisions

### Scope and ordering

- **D-01:** Phase 03.1 covers **SAP SuccessFactors and Paylocity Recruiting only**. New Workday expansion is deferred.
- **D-02:** The existing fixed Capital One Workday connector remains untouched. Regression tests must prove the phase does not widen its exact identity or provider eligibility.
- **D-03:** Paylocity ships first because it exposes a documented public Job Feed V2 contract. SuccessFactors begins with a bounded employer-specific proof before implementation is authorized.

### Paylocity contract

- **D-04:** Paylocity uses the documented public endpoint `GET https://recruiting.paylocity.com/recruiting/v2/api/feed/jobs/{guid}`.
- **D-05:** The company GUID is derived server-side from a canonical public employer URL and validated as a strict UUID. Client-provided GUIDs, alternate origins, credentials, ports, fragments, and ambiguous paths are rejected before network access.
- **D-06:** A Paylocity observation is closure-credible only after HTTP 200, JSON content type, byte-cap compliance, well-formed root identity, a jobs array, and schema validation of every row. A malformed row degrades the whole observation for closure purposes while preserving any safely parsed rows as partial evidence.
- **D-07:** Root `displayName` is the company identity source and is cross-checked against per-job company data when present. Identity disagreement is drift and cannot authorize closure or activation.
- **D-08:** Provider job identifiers remain immutable external IDs. Re-polling the same feed must update last-seen lifecycle state without creating duplicates or overwriting first-sight snapshots.

### SuccessFactors contract

- **D-09:** SuccessFactors is not treated as one universal public API. Research must identify two or three named real employers and record the exact public host, locale, company/site identifier, list request, detail request, pagination/count behavior, and response fields for each.
- **D-10:** Only exact, server-owned employer identities may be fetched. Detection parses a supported public careers URL into an allowlist lookup; user-controlled hostnames, data-center substitutions, guessed tenant IDs, and arbitrary query endpoints are rejected.
- **D-11:** A SuccessFactors adapter may be implemented only if live proof establishes a repeatable unauthenticated JSON contract with stable external IDs, truthful company identity, complete list pagination/count reconciliation, job detail sufficient for the existing scoring pipeline, and bounded request behavior.
- **D-12:** If those conditions cannot be proven, the employer and provider disposition is `unsupported_with_reason`. The phase must not fall back to generic DOM/HTML scraping or label recognition as support.
- **D-13:** Proof for one SuccessFactors employer authorizes only that exact allowlisted identity. No tenant, host, locale, or data-center generalization occurs without its own fixtures and live evidence.

### Observation, activation, and polling safety

- **D-14:** Only a complete, positive, reconciled observation may close missing jobs. Timeouts, non-2xx responses, content-type drift, schema drift, byte/page/deadline caps, partial pagination, duplicate-path conflicts, and implausible emptiness retain prior jobs and last successful health.
- **D-15:** Provider-confirmed zero results for an established board remain `implausible_empty`; they never read as a healthy empty board without an independently justified cold-start rule.
- **D-16:** Each company must earn at least three distinct server-timed, warning-free, closure-credible verification windows before scheduled activation. Evidence is company-specific and provider-specific.
- **D-17:** Scheduling is fail-closed at both boundaries: SQL claim eligibility and application dispatch. Catalog recognition or UI activation state alone cannot authorize polling.
- **D-18:** One employer's failure, drift, or unsupported disposition cannot close another employer's jobs, delay its polling, or promote its activation.
- **D-19:** Recurring jobs use the existing scheduler and source-observation health contracts. New provider-specific cron infrastructure is prohibited unless the existing claim/dispatch model cannot express the contract and the plan documents why.

### Dashboard delivery and schema

- **D-20:** Provider jobs enter the existing `jobs` persistence, preference filter, scoring, and All/Focused feed contracts. No provider-specific frontend insertion, synthetic score, or bypass is allowed.
- **D-21:** Schema work starts after the already-shipped `0028_capital_one_recent_active.sql`; refreshed plans must not reuse migration number 0028.
- **D-22:** Production schema pushes, Edge deployments, scheduler activation, and live state mutations remain explicit owner-approved checkpoints. Local implementation and read-only public endpoint research may proceed without production mutation.

### the agent's Discretion

- Exact representative employers selected for the bounded public SuccessFactors and Paylocity proofs, based on current verifiable career sites
- Byte, page, request, concurrency, and monotonic deadline caps within existing Edge limits
- Whether exact SuccessFactors identities live in a typed module or migration-backed catalog, provided the server owns them
- Plan sequencing, fixture organization, and test decomposition

</decisions>

<risks>
## Difficulties and Required Mitigations

- **SuccessFactors public-contract fragmentation:** hosts and request shapes vary by employer/data center. Mitigation: exact allowlist, per-employer proof, no generalized adapter from one sample.
- **Description availability:** public list calls may omit job descriptions required for useful scoring. Mitigation: prove a bounded detail contract or record unsupported.
- **False completeness:** an HTTP 200 can still be truncated, silently filtered, or schema-shifted. Mitigation: total reconciliation, pagination tests, caps, and closure-ineligible degradation.
- **Paylocity documentation gaps:** the public feed documents the endpoint but not every operational limit. Mitigation: whole-snapshot validation, hard byte/deadline caps, conservative cadence, repeated evidence.
- **Exact-assertion regression:** connector tests enumerate provider/source unions and Capital One identity. Update deliberate unions for the two new providers while retaining exact Workday assertions.
- **Free-tier pressure:** avoid unnecessary detail fan-out and reuse the existing scheduler cadence and scoring deduplication.

</risks>
