# Phase 03.1: Workday & ATS Connector Expansion — Context

**Gathered:** 2026-07-20
**Status:** Ready for planning
**Research:** `.planning/phases/03.1-workday-ats-connector-expansion/03.1-RESEARCH.md`

<domain>
## Phase Boundary

Expand connector coverage to a bounded, fail-closed Workday pilot across named tenants, and add a Paylocity Recruiting connector. Every Workday tenant earns its own independent evidence before scheduled polling; no tenant's success authorizes another.

**In scope:**
- Per-tenant Workday allowlist replacing the single fixed Capital One identity
- Bounded, closure-safe observation for each allowlisted tenant
- Paylocity Recruiting connector on its documented public feed API
- An ingest predicate (location + title terms + seniority exclusion) that bounds detail fan-out and storage
- Per-tenant activation evidence, truthful health states, and cross-tenant failure isolation

**Out of scope:**
- **SAP SuccessFactors — deferred to its own later phase** (owner decision, 2026-07-20). No SuccessFactors code, schema value, detection, or catalog change belongs in Phase 03.1.
- Entry-level determination from job descriptions — belongs to Phase 03.2
- Company visibility filtering — Phase 03.2
- Scoring, resume tailoring, tracker — Phases 3 and 4

</domain>

<decisions>
## Implementation Decisions

### Pilot scope

- **D-01:** The Workday pilot covers **eight named companies**: BMO, Capital One, Avant, Visa, Workday, Apollo Global Management, State Street, Invesco.
- **D-02:** **PIMCO is removed from the pilot** (owner decision, 2026-07-20). No PIMCO identity may be added, guessed, or seeded. Research could not resolve a PIMCO Workday host, and its careers page rejects automated fetches.
- **D-03:** The ten-company target requires **two further distinct companies** from the owner. Until both are supplied, **no artifact, summary, commit message, or UI copy may describe the pilot as a completed ten-company round.** Eight is the honest current scope.

### Workday identity (supersedes the fixed Capital One identity)

- **D-04:** Replace the single hardcoded identity with a **server-owned allowlist** of reviewed `{tenant, region, site, displayName, locationRule}` entries. The allowlist is the SSRF gate: a URL is supported only if its parsed identity matches an entry exactly. Host pattern parsing never widens what is reachable.
- **D-05:** Source key convention is unchanged: `workday:{region}:{tenant}:{site}`. It is derived per tenant and validated against the allowlist entry, never assembled from display data.
- **D-06:** **Company display names come from the reviewed allowlist entry only** — never from the tenant slug and never from provider free text. Apollo Global Management is hosted on the `athene` tenant; slug-derived naming would mislabel every Apollo job.
- **D-07:** Locale-prefixed (`/en-US/External`) and faceted board URLs are rejected in favour of the canonical single-segment site token, so one board never mints two identities.
- **D-08:** Where a company exposes several sites (Visa, Workday), the pilot polls one selected site per company and **records that as an explicit coverage boundary**. It is not full-coverage for that employer.

**Candidate identities (search-level evidence, none live-verified except Capital One):**

|---|---|---|---|---|
| BMO | `bmo` | `wd3` | `External` | **none — unfiltered** |

Every row except Capital One must be confirmed by live server-side observation during execution. An identity that fails to resolve becomes `unsupported_with_reason`, exactly as PIMCO did — it does not become a guess.

### Completeness contract (changes the inherited Workday contract)

- **D-09:** **List completeness is the sole closure authority.** A list observation is `complete` only when every page reconciles against the provider `total`, no page/byte/schema/duplicate-path failure occurs, and the result is positive. Closure credibility is otherwise unchanged from Phase 02.1.
- **D-10:** **Detail fetching becomes bounded incremental enrichment.** Only postings whose external identity is not already stored get a detail request, under a monotonic per-invocation deadline and a hard request ceiling. Reason: sequential per-posting detail fetches cannot complete inside a Supabase Edge invocation for tenants listing thousands of postings, so the inherited all-or-nothing contract would degrade large tenants permanently for a capacity reason rather than a trust reason.
- **D-11:** A posting whose detail has not yet been fetched is ingested from list fields only with **`snapshotPartial: true`** and enriched on a later tick. **Missing detail never authorizes closure and never reads as an empty board.** Nothing is dropped and nothing is fabricated.
- **D-12:** R-3 is retained: a provider-confirmed zero remains `implausible_empty` for both Workday and Paylocity.

### Ingest predicate

- **D-13:** A predicate is applied to the **complete, reconciled** list to decide which postings receive a detail call and a stored row. The full list is always observed; the predicate never narrows what is fetched at list level.
- **D-14:** Closure rule becomes: a stored job closes when it is absent from a complete reconciled list **or** no longer matches the predicate. Predicate-driven closure must be recorded distinctly from upstream closure — "no longer matches" is not "no longer posted."
- **D-15:** Predicate definition:

```
location:  US match, except BMO which is unfiltered (all countries)
title:     \b(data|analyst|quantitative|machine learning|equity)\b
exclude:   \b(senior|sr\.?|staff|principal|lead|director|vp|
             vice president|head of|chief|manager|mgr|executive|
             II|III|IV)\b
```

- **D-16:** Location filtering runs at **list level from `locationsText`** by default. Server-side `appliedFacets` location filtering is an optional per-tenant optimization admitted **only** with proof it applied — an unrecognized facet appears to be silently ignored, returning the full unfiltered board with HTTP 200. Facet IDs are read from the tenant's own `facets` response, never hardcoded. If filtered total does not fall below unfiltered total, the facet is treated as not applied and that tenant falls back to list-level matching.
- **D-17:** **`searchText` is not used for filtering.** Its semantics are undocumented and tenant-dependent, it takes one term rather than a set, and shifting server-side relevance would make jobs vanish from results for reasons unrelated to closure.
- **D-18:** Real entry-level determination is **not** attempted here. The list response carries no seniority or experience data — that lives in descriptions, behind the detail call the predicate exists to bound. Title-level seniority *exclusion* (D-15) is a cheap high-precision bound, not an entry-level filter. Entry-level eligibility remains Phase 03.2's, where descriptions are available.

### Activation and safety

- **D-19:** Allowlist membership grants **eligibility to gather evidence only**. It never grants scheduling.
- **D-20:** Each tenant independently requires at least three distinct server-timed windows of complete, closure-credible, warning-free observations before it may be scheduled. Evidence is per tenant; a provider-wide promotion is prohibited.
- **D-21:** Defense in depth is retained: scheduling exclusion is enforced at **both** the SQL claim boundary (`claim_due_companies`) and application dispatch (`pollConnector`). The current provider-wide `inactive_connector:workday_experimental_only` ban becomes a per-tenant proof check — it must not become a provider-wide allow.
- **D-22:** One tenant failing, drifting, or returning an implausible result must never close another tenant's jobs, delay its polling, or block its promotion. This requires an explicit cross-tenant isolation regression test.
- **D-23:** Tenants are sharded across scheduler ticks (one tenant per tick) so each invocation handles one list sweep plus a bounded detail batch, keeping refresh inside the 5–15 minute product target.

### Paylocity

- **D-24:** Paylocity ships **first** — it is the only documented public contract in the phase (`GET https://recruiting.paylocity.com/recruiting/v2/api/feed/jobs/{guid}`).
- **D-25:** The company GUID is derived **server-side** from the employer's public careers URL (`recruiting.paylocity.com/recruiting/jobs/All/{guid}/{Company-Name}`) and validated as a strict UUID. It is a public board identifier, not a secret, and is never accepted from client free text without server re-derivation.
- **D-26:** The response is a **single whole-board snapshot** with descriptions included, so no detail fan-out and none of D-09/D-10 apply. Documentation states no pagination model, no rate limits, and no terms — so there is no independent total to reconcile against. Completeness rests on HTTP 200, JSON content type, well-formed root with non-empty `displayName`, an array `jobs`, every job passing schema validation, and a byte cap.
- **D-27:** Company identity prefers root `displayName`, cross-checked against per-job `companyName`; a mismatch is drift and is closure-ineligible.

### Claude's Discretion

- Exact caps: per-invocation detail ceiling, deadline value, byte/page caps, per-host throttle
- Allowlist storage shape (typed module constant vs. table), provided it is server-owned and migration-enforced
- Whether the predicate lives in shared code or per-adapter, provided it is pure and fixture-testable
- Plan sequencing and task decomposition within the ordering constraint that Paylocity precedes the Workday pilot

</decisions>

<risks>
## Difficulties and Required Mitigations

- **Detail fan-out vs. Edge wall clock** — the blocking constraint that drove D-09 through D-11. Verify caps against real tenant sizes during execution.
- **Silent filter failure** — an ignored facet returns the full board with HTTP 200 and looks like success. D-16's proof requirement is the mitigation.
- **Over-narrow ingest predicate is irreversible without backfill** — unmatched postings are never stored. `equity` also matches diversity-and-inclusion titles, and `analyst`/`associate` seniority inverts between finance tenants (Apollo, State Street, Invesco) and tech tenants (Visa, Avant). Keep the predicate loose and let Phase 3 scoring discriminate.
- **Allowlist widening as a silent authorization path** — D-19 and D-21 keep eligibility and scheduling separate at two independent boundaries.
- **Schema drift across eight undocumented tenants at once** — per-tenant fixtures; drift degrades only the affected tenant.
- **Free-tier pressure** — 500 MB Postgres and 5 GB monthly egress across eight tenants. The predicate, incremental detail, and sharded cadence are the controls.
- **Exact-assertion test churn** — `detect.test.ts`, `adapters.test.ts`, `workday-connector.integration.test.ts`, `public-connectors.integration.test.ts`, `source-observation.integration.test.ts`, and `activation-policy.test.ts` carry exact registry-size and fixed-identity assertions. Phase 02.1 hit this exact regression class; update deliberately, never loosen.
- **Compliance** — CXS and Paylocity feed calls are the same unauthenticated requests the public pages make. No logged-in surface, no CAPTCHA bypass, no concealment of automated traffic. Undocumented ≠ prohibited, but it is why the fail-closed rules exist.

</risks>
