Output: a per-tenant `pollConnector` gate, an allowlist-driven `verifyWorkday`, and one shared source-key derivation.
</objective>

    - An active, allowlisted Workday company whose recorded window count is below three is rejected with a bounded unproven-tenant code and never reaches the adapter.

    - An active, allowlisted Workday company whose source key does not equal the key derived from its own tokens is rejected — a drifted stored key must not select a different tenant's identity.

    Write the behavior cases above as tests in `workday-connector.integration.test.ts` first, and commit them red. Update the existing provider-wide dispatch-rejection assertion rather than deleting it: it becomes the unproven-tenant case, which is the same protection expressed per tenant.

    Then add `resolveWorkdayIdentity(company)` returning the reviewed identity or null: it reads the company's board token, region, and site token, requires all three to be present, looks the triple up in the allowlist, and additionally requires the company's stored source key to equal the key derived from the matched entry. The stored-key consistency check is deliberate — the stored key is the reconciliation anchor used everywhere else in the system, and letting a drifted key through would let one tenant's row poll another tenant's board.

Two gates that fail independently is the requirement; two gates that read the same value would be one gate.

    Do not add a provider-wide allow anywhere. There must be no code path where being a Workday company is sufficient for dispatch.
