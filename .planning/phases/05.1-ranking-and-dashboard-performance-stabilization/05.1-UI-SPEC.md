# Phase 05.1 — UI Design Contract

> Visual and interaction contract for the approved Dashboard dismissal stabilization only. Generated by gsd-ui-researcher for verification by gsd-ui-checker.

---

## Scope

This phase changes only the behavior and feedback around the existing **Dismiss** action in the Active jobs table. Preserve the current page title, description, lifecycle control, filters, ranking notices, result count, table layout, column widths, row styling, ordering, pagination, dark mode, and responsive behavior.

Do not add a page, route, modal, toast system, navigation item, filter, ranking treatment, animation system, or replacement dashboard component. Do not change **Mark Applied** product semantics. The only permitted visual addition is one compact, retryable post-dismiss refresh warning in the existing Dashboard feedback band above the result count and table.

## Color

Retain the existing zinc/slate palette and system dark mode. The percentages describe the established Dashboard visual hierarchy, not a new palette.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | Light `#f8fafc`; dark `#09090b` | Page background and surrounding canvas |
| Secondary (30%) | Light `#ffffff`; dark `#18181b` | Table, cards, and compact feedback surfaces |
| Accent (10%) | Light `#18181b`; dark `#f4f4f5` | Existing primary fills, focus outlines, and the neutral outlined **Retry refresh** control |
| Warning | Light border/bg/text `#fde68a` / `#fffbeb` / `#78350f`; dark `#78350f` / `#451a03` / `#fde68a` | Post-dismiss background refresh warning only |
| Destructive / error | Light `#b91c1c`; dark `#f87171` | Dismissal RPC failure message only |

Accent is reserved for existing primary filled controls, keyboard focus outlines, and the **Retry refresh** control's neutral border/text. Do not apply accent color to the whole warning, every row action, or the dismissed row. Keep the existing **Dismiss** button neutral; do not recolor it red.

Color is never the only state signal: warning and error states always include explicit text, and pending controls use both `disabled` state and a label change where the control remains visible.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | Visible label: **Dismiss**. Accessible name: `Dismiss {job title}`. Preserve the current label. |
| Success announcement | `Dismissed {job title} permanently.` |
| Empty state heading | Preserve the existing scope-specific heading: `No watchlist matches yet` or `No matches yet`. Dismissal creates no new empty state. |
| Empty state body | Preserve the existing scope-specific body and preference link exactly; do not add dismissal instructions. |
| Dismissal RPC error | `Couldn’t dismiss {job title}. The job was restored. Try again.` |
| Post-dismiss refresh warning | `Job dismissed. We couldn’t fully refresh this list. Your current results may be out of date.` |
| Refresh retry CTA | Idle: `Retry refresh`. Pending: `Refreshing…`. Success announcement: `Job list refreshed.` |
| Destructive confirmation | **Dismiss** remains immediate and permanent, with no confirmation dialog and no Undo. The row-level accessible name supplies the target. |

Use the existing `Untitled role` fallback when no safe job title is available. Never show backend error codes, routing terminology, RPC names, or wording that implies a successfully dismissed job has returned.

## Dismissal Interaction Contract

### State and transition contract

| State | Visual contract | Interaction contract |
|-------|-----------------|----------------------|
| Idle | Existing row and existing neutral **Dismiss** button | All row actions are available. |
| Activated, 0–100ms | Remove only the targeted row from the current table with no exit animation, whole-table loading state, or filter reset. Decrement the visible result count in the same optimistic render. | Capture the exact query identity, page, row index, row data, and focus neighbors before removal. Disable both lifecycle actions only for the targeted row until it leaves the DOM. |
| Dismissal RPC pending | Target row remains absent. No spinner, toast, overlay, or page-level pending state appears. | Other cards, filters, pagination, links, and both lifecycle actions on other cards remain usable, including for a second dismissal. Same-card duplicate submission is impossible. |
| RPC success | Keep the target absent and announce `Dismissed {job title} permanently.` through the existing polite live region. | The user-blocking mutation is complete immediately when `dismiss_job_permanently` succeeds. Clear that row's pending state; do not await refill, cache reconciliation, or resume routing. |
| Background reconciliation succeeds | Merge/refetch data without replacing already loaded rows with a skeleton, resetting scroll, or changing filters. Clear any existing refresh warning. | Refill, inactive-cache reconciliation, and resume routing run outside the dismissal mutation. A later successful automatic refresh also clears the warning. |
| Background reconciliation fails after RPC success | Keep the dismissed row absent. Show one compact warning above the result count/table; coalesce repeated failures rather than stacking warnings. | Keep all card actions enabled. The warning's **Retry refresh** control retries the full reconciliation. Never roll back the durable dismissal. |
| Retry refresh pending | Warning remains in place; only its button changes to `Refreshing…` and becomes disabled. | All job-card actions remain usable. A repeated failure leaves the same warning retryable. A success announces `Job list refreshed.`, moves focus to the table region before removing the focused warning control, and clears the warning. |
| RPC failure | Restore the exact card in its prior page and visual position with its original content; do not append it to the end or refetch the whole table first. Show the dismissal error above the result count/table. | Clear the target's pending state, focus its restored **Dismiss** button, and allow immediate retry. Do not start background reconciliation or show a success announcement. |

### Durable-state invariant

The dismissal RPC is the commit boundary. Once it succeeds, no cache snapshot, rejected refill, failed resume-routing request, late response, automatic refetch, or retry failure may reinsert the targeted card. A refresh failure is a stale-view problem, not a dismissal failure.

### Row-scoped concurrency

Dismissal pending state is keyed by `user_job_id`; it must not be derived from a single global `dismissMutation.isPending` flag or combined into the current global `lifecycleMutationPending` value. A pending dismissal may disable the target's **Mark Applied** and **Dismiss** controls only. It must not disable either control on any other row. Concurrent dismissals keep independent snapshots, rollback positions, announcements, and outcomes.

### Layout and placement

- Render the refresh warning in the existing feedback band after ranking status and before the result count/table.
- Use a compact `rounded-lg` bordered surface with 12px padding, 14px text, an 8px gap, and a wrapping inline layout so the control remains visible at 320px viewport width.
- Reuse the existing amber warning tokens already present on the Dashboard; use a neutral outlined retry button with the existing focus-ring treatment.
- The warning must not be a fixed toast, modal, dialog, or full-width page blocker.
- Preserve current table row height, column widths, horizontal-scroll region, hover/focus-within styles, and all filter state.

## Focus, Keyboard, and Announcements

- **Dismiss** remains a native button activated by keyboard or pointer. Preserve the row-specific `aria-label`.
- On optimistic removal, move focus to the next row's first lifecycle action; if none exists, use the previous row's first lifecycle action; if the table is empty, focus the table region. Do not focus the warning or page heading automatically.
- On RPC failure, restore focus to the restored row's **Dismiss** button after the row is rendered.
- Announce RPC failure with `role="alert"` / assertive semantics. Announce dismissal success, refresh warning, and refresh success politely so background work does not interrupt unrelated actions.
- The warning button has a visible focus outline, an accessible name matching its visible label, and a 44px coarse-pointer target.
- Do not use an animated row collapse. Immediate removal is required for the 100ms target and inherently respects reduced-motion preferences.

## Performance Acceptance Contract

| Measure | Required result |
|---------|-----------------|
| Optimistic disappearance | Target row is absent from the rendered table within 100ms of activation. |
| Targeted mutation P95 | From activation to dismissal RPC success announcement or failure rollback is at most 1.5s at P95. |
| Critical-path boundary | Feed refill, inactive-cache work, and resume routing are excluded from mutation pending/settled timing. |
| Unrelated actions | No unrelated row action becomes disabled or receives pending styling during a dismissal. |
| RPC failure recovery | Exact card, page, index/order, content, and actionable state are restored without a full-table loading state. |
| Post-success failure | Dismissed card remains absent; warning appears and remains retryable while other actions stay available. |

Acceptance must exercise pointer and keyboard activation, a deliberately slow background refill, a routing failure after RPC success, an RPC rejection, concurrent dismissals, the last visible row, light/dark mode, and a 320px coarse-pointer viewport. Subjective “feels faster” judgment does not replace the measured 100ms and P95 gates.
