## Decisions Made

- Routine enqueue scans only deduplicated queued changes for initialized idle owners; it never interprets missing ranking revisions as work and never backfills the open-job catalog.
- A claimed batch is one atomic database unit: evaluator errors are records in the same JSON payload, partial acknowledgement is fatal, and finalization follows only a successful full-count stage.
- Retry fixture ownership is derived from the actual failed run rather than a hardcoded owner. The retry RPC result is materialized and carried across the PostgreSQL command snapshot by exact run ID before membership assertions.
- Migration 0063 remains immutable and byte-identical; migration 0064 has `deployment_status: not_deployed` and no release approval claim.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Made the delta retry pgTAP fixture deterministic under PostgreSQL planning and command snapshots**

- **Found during:** Task 3 (disposable real-PostgreSQL verification)
- **Issue:** The fixture hardcoded one owner and joined the volatile retry RPC to an initially empty retry table. PostgreSQL could skip the RPC, and after forcing it, the same command snapshot could not yet read the inserted retry row.
- **Fix:** Derive authenticated ownership from the actual failed run, execute the retry RPC through a materialized CTE, preserve its exact returned run ID in a transaction-local setting, and assert both expected count and item membership against that ID in following statements.
- **Files modified:** `supabase/tests/0064_delta_deterministic_ranking_and_batch_staging.test.sql`
- **Verification:** Disposable PostgreSQL runner passed 31/31 assertions twice with successful teardown.
