# Phase 03.2: Dashboard Precision & Company Visibility - Context

**Gathered:** 2026-07-22
**Status:** Ready for planning

<domain>
## Phase Boundary

Improve the existing scored-job Dashboard without changing ingestion: add session-only current-feed company visibility controls, score-tier filtering, a configurable maximum required-experience preference, and a full-width resizable table. Company controls hide or reveal already-loaded results only; new employers still enter through the existing URL/watchlist flow. Match reasons remain available on job detail rather than occupying a feed column.

</domain>

<decisions>
## Implementation Decisions

### Company visibility behavior
- **D-01:** The Dashboard supports hiding current-list companies and an optional preferred-companies-only view; prioritization is a filter mode, not a ranking boost or pinned section.
- **D-02:** Company visibility is session-only. It resets on Dashboard refresh/navigation and never changes matching, scoring, persistence, polling, or future ingestion.
- **D-03:** Default state shows all companies. Checked means visible; unchecked hides that company's current rows. The panel has a company-filter Reset action.
- **D-04:** The company list and autocomplete derive only from truthful company names already present in the current authorized feed. Users cannot type arbitrary companies here; genuinely new companies are added through the existing URL/watchlist flow.

### Company control placement
- **D-05:** Controls live only on the Dashboard in an inline expandable panel above results, not in Preferences or a modal/side panel.
- **D-06:** The panel includes a search/autocomplete input, checkbox list, Reset, and Show results interaction modeled on the user's reference screenshot.

### Entry-level preference semantics
- **D-07:** Add a user-configurable maximum required-experience preference. A value of 3 keeps jobs requiring 3 years and removes jobs whose explicit required minimum exceeds 3 years.
- **D-08:** Do not infer seniority from title words such as Senior, Lead, Manager, Director, Staff, or Principal. Filtering is based on explicit required years in the job description.
- **D-09:** Jobs with missing, ambiguous, or unparseable required-years language remain eligible.
- **D-10:** For a range such as 3–5 years, use the required minimum (3). Preferred, desired, bonus, or nice-to-have years never exclude a job.
- **D-11:** Preference changes reuse the existing per-user refilter/rescore invalidation path; the filter remains provider-neutral.

### Dashboard precision and table layout
- **D-12:** The complete current preference-pass feed is the single Dashboard scope. Strong/Good/Weak toggles all start selected and are the sole score-boundary controls.
- **D-13:** Company visibility and tier selections compose with AND semantics: a row must match a selected tier and a visible company.
- **D-14:** Keep the existing navigation/header shell but let Dashboard use the full remaining browser width instead of the shell's current `max-w-6xl` content window.
- **D-15:** Remove Match reason from the table; the full reason content remains on job detail after the user opens a job.
- **D-16:** Add a Location column using the existing `jobs.location` feed field.
- **D-17:** Table columns are draggable/resizable. Widths persist per browser using local storage; no reset-width action is required. This is independent of the company-filter Reset action.

### the agent's Discretion
- Exact accessible resize-handle implementation, minimum/maximum widths, and keyboard affordance.
- Exact required-years parser grammar and precedence rules, provided D-07 through D-10 hold.
- Responsive behavior on narrow screens while preserving full-width desktop use and accessible horizontal overflow where necessary.
- Visual styling details within the existing dense-table, zinc, light/dark design system.

### Folded Todos
- **Add company visibility filter:** Folded into D-01 through D-06. The original persistence request is superseded by the owner's session-only decision.
- **Add entry-level-only job preference filter:** Folded into D-07 through D-11. The original title-based and `3+` exclusion proposal is superseded by the owner's explicit required-years-only and `> threshold` decisions.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `Dashboard.tsx`: existing TanStack Query feed, view/dismiss/sort state, table markup, and optimistic dismiss/restore mutations.
- `feed.ts`: `companyName`, `tierPresentation`, `preferenceVisible`, and the already-selected `jobs.location` field.
- `preferences.ts`: single per-user preference row and `mark_recent_jobs_for_refilter` mutation sequence.
- `JobDetail.tsx`: already owns detailed score reasons and job-description presentation.

### Established Patterns
- Feed eligibility is enforced before client presentation; UI filters may only narrow already-authorized, preference-passing rows.
- Company identity must come from normalized company data or bounded source-provided identity; identity-less rows remain excluded.
- Dense tables use horizontal overflow, explicit accessible labels, pure mappers, and tested thin data helpers.
- Preference changes persist first, then signal recent rows for refilter/rescore.

### Integration Points
- Dashboard state/filter composition and table columns in `web/src/pages/Dashboard.tsx`.
- Dashboard-specific shell width handling in `web/src/components/Shell.tsx` or route-aware layout composition.
- Preference schema/data/UI in the next migration, `web/src/lib/preferences.ts`, and `web/src/pages/Preferences.tsx`.
- Required-experience parsing and filter outcomes in `supabase/functions/_shared/filters.ts`, consumed by `score-tick`.

</code_context>
