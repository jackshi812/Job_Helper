## Summary

Goldman is implementable through the existing connector architecture without a new provider family or frontend surface. The current frozen identity, adapter, normalized job contract, Experimental observer, Active poller, lifecycle reconciler, and Phase 03.9 release tooling already provide the required seams. The current Goldman implementation is not acceptable for this phase because it writes `postedAt: null`, persists a Higher role page instead of the provider-supplied Oracle Apply URL, accepts broad Oracle paths, marks complete observations closure-eligible, does not prove exact list/detail category labels or career population, and does not hide provider-open jobs after the rolling window. [VERIFIED: `branded-identities.ts`, `goldman-higher.ts`, `observe-connectors/index.ts`, `poll-tick/index.ts`, and `lifecycle.ts`]

The live contract resolves the posting-date ambiguity. `ExternalRoleGraphQlDTO` and `ExtendedRoleGraphQlDTO` expose `startDate`, `lastPostedDate`, and other timestamps. For live role `179875`, Higher returned `startDate=2026-07-24T18:03:34Z`; Goldman's public Oracle detail returned `ExternalPostedStartDate=2026-07-24T18:03:41+00:00`, while Higher's `lastPostedDate` was `2026-07-27T13:40:41.103Z`. Therefore use `startDate` as the posting timestamp and explicitly reject `lastPostedDate` as freshness authority. Require list/detail `startDate` equality after canonical parsing and apply an exact `pollWallClock - 168h <= startDate <= pollWallClock` check with no calendar-day rounding. [VERIFIED: live Goldman Higher GraphQL and Goldman Oracle Candidate Experience inspection on 2026-07-27]

Request `EARLY_CAREER` and `PROFESSIONAL` as two independently reconciled listing slices, then hydrate the deduplicated selected union. The official anonymous schema enumerated `PROFESSIONAL`, `EARLY_CAREER`, `CAMPUS`, and `INTERNAL_MOBILITY`; live counts were 1,197 Professional and 6 Early Career, while the combined query reported 1,203. Detail `recruitingType` returned `GS_MID_CAREER` and `GS_EARLY_CAREER` for inspected roles. Accept only those two detail values, but do not require a one-to-one mapping to the query slice because a live role returned by the Professional slice carried an Early Career role identifier; the union of both requested populations is the authority. [VERIFIED: live Goldman Higher GraphQL inspection on 2026-07-27]

**Primary recommendation:** Extend the existing Goldman adapter into a two-slice, exact-168-hour, list/detail-proven selective observation; persist a Goldman-specific evidence shape and direct Oracle Apply URL; set `allowMissingClosure=false` on every outcome; hide aged Goldman rows only in the Active Dashboard feed; and reuse the Phase 03.9 hash-bound migration, activation, natural-poll, isolation, cleanup, and owner-browser acceptance sequence. [VERIFIED: live contract and repository precedent]

## Live Contract Findings

### Exact network and navigation identity

`POST https://api-higher.gs.com/gateway/api/v1/graphql` anonymously returned JSON for the frozen `GetRoles` operation. The public `/results` route returned HTTP 200; `/roles` returned HTTP 307 to `/results`; `/jobs` returned HTTP 404. Canonical storage should therefore become `/results`, while exact `/results`, `/results/`, `/roles`, and `/roles/` recognition may resolve to the same frozen object. Query strings, fragments, credentials, ports, redirects supplied as input, subpaths, and other hosts must fail before provider access. [VERIFIED: live Goldman endpoints on 2026-07-27]

The Higher detail returned the provider-supplied URL `https://hdpc.fa.us2.oraclecloud.com/hcmUI/CandidateExperience/en/sites/LateralHiring/job/180084/apply/email` for the inspected eligible role. Freeze host `hdpc.fa.us2.oraclecloud.com` and require the exact path grammar `/hcmUI/CandidateExperience/en/sites/LateralHiring/job/{numericSourceId}/apply/email`, no credentials, port, query, or fragment, and exact equality between the path ID and list/detail `externalSource.sourceId`. The current `startsWith` plus `includes` validator is too permissive. [VERIFIED: live Higher detail and `goldman-higher.ts` inspection]

### Listing contract and completeness

`RoleSearchQueryInput` exposes `page`, optional `sort`, `searchTerm`, non-null `experiences`, and optional `filters`. `roleSearch` returns `page { pageSize pageNumber hasNext }`, `totalCount`, and `items`; each item can provide `roleId`, `jobTitle`, `jobFunction`, `division`, `locations`, `status`, `externalJobStatus`, `startDate`, `lastPostedDate`, `createdDate`, and `externalSource { sourceId externalSourceType }`. [VERIFIED: anonymous Goldman GraphQL introspection on 2026-07-27]

Plan two exact slices: one request stream with `experiences: ['EARLY_CAREER']`, one with `experiences: ['PROFESSIONAL']`, both with `filters: []` and `searchTerm: ''`. For each page require the echoed page number and page size, internally consistent `hasNext`, one stable `totalCount` across pages, item count at most page size, monotonic page progression, and final raw fetched count exactly equal to the slice total. Reject zero combined selected jobs, cap exhaustion, repeated/duplicate role IDs, duplicate source IDs, cross-slice identity drift, count drift, or missing page metadata. [VERIFIED: live schema and existing adapter bounds; recommendation derives from D-12/D-16]

Retain the current hard maximums of 100 rows/page, 100 pages, 5,000 raw jobs, 5,000 details, four concurrent details, 1 MB/response, 15 seconds/request, and 120 seconds total unless a deterministic full live dry run proves a smaller safe bound. The live combined population was 1,203, so these current maximums covered the observed population with headroom. [VERIFIED: `branded-identities.ts` and live count on 2026-07-27]

### Posting timestamp and population proof

Query `startDate` in both list and detail. Parse it to a canonical instant, require exact list/detail instant equality, reject missing/malformed/future timestamps, and reject any instant older than `wallClockNow - 168 * 60 * 60 * 1000`. Inject a wall-clock dependency separately from the monotonic deadline clock so tests can prove boundary inclusivity and clock behavior. Do not use `lastPostedDate`, `createdDate`, or title text as a substitute. [VERIFIED: live timestamp cross-check; existing Oracle adapter demonstrates separate clocks]

Query detail `recruitingType` and require exactly `GS_EARLY_CAREER` or `GS_MID_CAREER`; reject any other value as an incomplete observation. Also require the stable `roleId` suffix to agree with the detail recruiting type when the provider supplies the current `_GS_EARLY_CAREER` or `_GS_MID_CAREER` form, but keep membership in either requested listing slice as the primary population proof. [VERIFIED: live inspected detail values and role ID forms; strict suffix agreement is a recommended drift check]

### Category, country, detail, and Apply proof

Preserve the seven-term matcher in `scope.ts`; it already applies NFKC normalization, locale-aware lowercase conversion, Unicode letter/number tokens, longest-term precedence, and contiguous whole-token matching. It correctly prevents `Data` from matching `Database`. [VERIFIED: `scope.ts` and focused baseline tests]

For each list role, evaluate `jobFunction` first and then `division`, recording the exact field chosen, normalized provider label, and matched term. An empty non-selected field is allowed. Hydration must require that same field, same normalized label, and same term on detail; equality of only the matched term is insufficient. If both fields disappear, become malformed, or the selected field drifts, the whole observation is incomplete. [VERIFIED: current adapter gap; recommendation derives from D-09/D-10]

Require list/detail equality for role ID, source ID, title, selected U.S. location tuple, selected category field/label/term, posting instant, and allowed recruiting type. Require `status=POSTED`, `externalJobStatus=POSTED`, `applyActive=true`, `externalSourceType=ORACLE`, `applyInExternalSource=true`, a bounded nonempty full description, and the exact safe Apply URL. [VERIFIED: live schema/detail fields; recommendation derives from D-03/D-16/D-19]

A real current role satisfied the acceptance shape during research: role `180084_GS_MID_CAREER`, source ID `180084`, New York U.S. location, `Research Analyst` / `Global Investment Research Division` provider labels, `startDate=2026-07-23T17:01:09Z`, `GS_MID_CAREER`, a 4,118-character description, and the exact Oracle Apply URL. This proves feasibility, not release acceptance; the rollout must obtain fresh evidence on the approved deployed release. [VERIFIED: live Higher detail on 2026-07-27]

### Anti-Patterns to Avoid

- **Using `lastPostedDate`:** It can reflect Higher refresh/repost timing instead of the Oracle posting start and can falsely admit stale roles. [VERIFIED: live cross-check]

- **Closing on age or absence:** A role leaving the selected 168-hour window says nothing about provider-open status. [VERIFIED: D-07/D-17]
- **Updating deployed migrations:** Migrations 0040–0047 are historical production artifacts; add a forward migration only. [VERIFIED: repository history and project decisions]

## Common Pitfalls

### Pitfall 1: False freshness from `lastPostedDate`

**What goes wrong:** Old Oracle jobs can appear newly posted after a Higher refresh. [VERIFIED: live role 179875]

**Why it happens:** `lastPostedDate` was three days later than Oracle `ExternalPostedStartDate`, while Higher `startDate` matched the Oracle instant within seconds. [VERIFIED: live cross-check]

**How to avoid:** Use only list/detail `startDate`, canonicalize it, require agreement, and apply exact rolling milliseconds. [VERIFIED: recommended contract]

**Warning signs:** Large batches suddenly share today's `createdDate`/`lastPostedDate` while `startDate` is older. [VERIFIED: live first page]

### Pitfall 2: Treating selective completeness as closure authority

**What goes wrong:** A role aging out of the 168-hour selection is falsely closed. [VERIFIED: lifecycle semantics]

**Why it happens:** The current Goldman success returns `allowMissingClosure:true`. [VERIFIED: `goldman-higher.ts`]

**How to avoid:** Return false on every Goldman outcome and make connector, observer, poller, and tests require false. [VERIFIED: Phase 03.9 pattern]

**Warning signs:** A Goldman Active poll reports any positive `closed` count or the lifecycle planner receives a closure-eligible Goldman observation. [VERIFIED: D-17]

### Pitfall 3: “Same term” masks category drift

**What goes wrong:** List `jobFunction` and detail `division` can both happen to contain one allowed term even though the selected provider evidence changed. [ASSUMED]

**Why it happens:** The current adapter records only label/term and detail compares only the term. [VERIFIED: `goldman-higher.ts`]

**How to avoid:** Bind the selected field and normalized label, then require exact list/detail agreement. [VERIFIED: D-10]

**Warning signs:** Detail evidence succeeds after deleting or changing the selected list field in a fixture. [VERIFIED: required negative test]

### Pitfall 4: Apply URL looks valid but is not exact

**What goes wrong:** A URL on the right host but wrong site, extra path, query, or job ID is persisted. [ASSUMED]

**Why it happens:** The current validator accepts any Candidate Experience site prefix and only checks that the expected job segment occurs somewhere. [VERIFIED: `safeApplyUrl`]

**How to avoid:** Match one exact parsed path and require empty query/fragment plus numeric source-ID equality. [VERIFIED: live Apply path]

**Warning signs:** Hostile fixtures containing `/job/{id}/apply/email/extra` or `?redirect=` pass. [ASSUMED]

### Pitfall 5: Raw count and selected count are conflated

**What goes wrong:** `expectedCount` can mean provider population size in one branch and normalized selected jobs in another, weakening reconciliation evidence. [VERIFIED: current adapter's incomplete/success calls]

**Why it happens:** The adapter uses `eligible.length` for some incomplete expected counts and `jobs.length` for final `expectedCount`, while aggregate evidence separately receives the raw total. [VERIFIED: `goldman-higher.ts`]

**How to avoid:** Track per-slice `reported`, `fetched`, and `pages` separately; reserve `PollObservation.expectedCount` for the final deduplicated selected job count used by activation. [VERIFIED: Phase 03.9 pattern]

**Warning signs:** A page/count error can still produce `expectedCount === jobs.length`. [ASSUMED]

### Pitfall 6: SQL authority widens sibling providers

**What goes wrong:** Replacing shared RPC definitions can accidentally omit JPMorgan/Workday branches or re-enable Morgan Stanley. [VERIFIED: migration history]

**Why it happens:** `record_connector_observation`, `claim_due_experimental_connectors`, `claim_due_companies`, `jobs_scope_evidence_check`, and `companies_branded_identity_check` are whole-object replacements in forward migrations. [VERIFIED: migrations 0045/0047]

**How to avoid:** Snapshot exact definitions/ACLs and add only the literal Goldman branch while preserving every current branch. [VERIFIED: D-21 and Phase 03.9 migration tests]

**Warning signs:** Diff-based migration tests do not assert all existing source keys and ACLs. [ASSUMED]

### Pitfall 7: UAT certifies a different release

**What goes wrong:** The owner views a mutable production URL after assets or functions changed. [VERIFIED: prior release risks documented in STATE]

**Why it happens:** Deployment, activation, and UAT evidence are not bound to the same commit, migration chain, function hashes, and web asset identity. [VERIFIED: Phase 03.9 rollout precedent]

**How to avoid:** Recompute exact release identity before every mutation stage and before owner UAT; invalidate approval on drift. [VERIFIED: D-20]

**Warning signs:** A reused Phase 03.9 approval string or unverified hosted function version is accepted. [ASSUMED]

// Source: live provider URL; recommended strict replacement for safeApplyUrl
function safeGoldmanApplyUrl(value: unknown, sourceId: string): string | null {
  if (typeof value !== 'string' || !/^[0-9]{1,256}$/.test(sourceId)) return null
  try {
    const url = new URL(value)
    const expectedPath =
      `/hcmUI/CandidateExperience/en/sites/LateralHiring/job/${sourceId}/apply/email`
    return url.protocol === 'https:'
      && url.hostname === 'hdpc.fa.us2.oraclecloud.com'
      && !url.username && !url.password && !url.port
      && !url.search && !url.hash
      && url.pathname === expectedPath
      ? url.toString()
      : null
  } catch {
    return null
  }
}
