# Phase 03.5: Code Review Report

**Reviewed:** 2026-07-24T20:30:28Z
**Depth:** standard
**Files Reviewed:** 12
**Status:** issues_found

## Summary

The generalized Workday implementation has six ship-blocking correctness and identity-integrity defects. Most importantly, Fidelity's inclusion facets are never proven to have affected the scoped response, the shared recent importer silently applies Capital One's U.S./experience filters to Fidelity, and migration 0035's purported exact allowlist accepts malformed Workday rows through PostgreSQL's three-valued `CHECK` semantics. Requisition/tombstone identity normalization also disagrees on common `-1`/`-2` path suffixes.

The targeted `workday-connector`, `migration-0035`, `detect`, and `watchlist` suites pass (211 tests), but their fixtures encode the happy path and miss these adversarial cases.

## Narrative Findings (AI reviewer)

## Critical Issues

### CR-01: Fidelity's applied category filter is not verified

**Classification:** BLOCKER

**File:** `supabase/functions/_shared/adapters/workday.ts:630-635`

**Issue:** Discovery proves only that all unfiltered family counts sum to the unfiltered total, then returns the kept IDs while discarding the kept-count total. On the filtered request, the code accepts any first-page `providerTotal`; the only applied-facet reconciliation at lines 733-756 is gated to `identity.keptFacetIds` and therefore never runs for Fidelity. If Workday ignores an applied facet, partially applies the IDs, or returns a drifted ID mapping, the importer can ingest Sales, Customer Service, or Sales Support rows while reporting a complete, warning-free observation. List/detail rows do not carry a family field that could detect the leakage later.

**Fix:** Return both the kept IDs and the expected kept count from discovery, reject negative counts and duplicate descriptors/IDs, and require the first filtered response's total to equal that kept count before accepting any rows.

```ts
type DiscoveredFacets = { ids: string[]; expectedKeptCount: number }

const expectedKeptCount = kept.reduce((sum, value) => sum + value.count, 0)
return { ids: kept.map((value) => value.id), expectedKeptCount }

// First scoped page:
if (pageCount === 0 && providerTotal !== expectedKeptCount) {
  return incomplete([], 'category_filter_unverified', undefined, 1)
}
```

Add a regression where discovery reports kept=2/excluded=3 but the filtered endpoint ignores facets and returns total=5; it must fail with `category_filter_unverified`.

### CR-02: Fidelity jobs are silently dropped by Capital One-only eligibility filters

**Classification:** BLOCKER

**File:** `supabase/functions/_shared/adapters/workday.ts:859-864`

**Also affected:** `web/src/lib/watchlist.ts:264-267`

**Issue:** `pollWorkdayRecent` unconditionally requires every new Workday detail to have a recent start date, be U.S.-based, and have required experience below three years. That behavior was inherited from the Capital One importer, but Fidelity's documented scope is family exclusion with required-experience filtering downstream. The Watchlist explicitly tells users experience is not filtered by the connector. In reality, Fidelity roles requiring three or more years—and all non-U.S. roles—are never ingested, so the dashboard cannot apply or change those filters later. This is silent source-data loss and makes the UI statement false.

**Fix:** Put eligibility policy on `WorkdayIdentity` (or branch explicitly by identity) and apply U.S./experience predicates only to Capital One. Fidelity should retain every recent detail returned by the verified kept-family facet scope and let downstream ranking/filtering decide eligibility.

```ts
const eligible = !identity.applyCapitalOneEligibility
  || (isUnitedStatesDetail(detail) && isEntryLevelWorkdayDetail(detail))
if (!recentStartDate(detail.jobPostingInfo.startDate, nowMs, recentDays) || !eligible) continue
```

Add Fidelity regressions for a non-U.S. job and a job requiring 3+ years; both should be ingested when their family is in the kept scope.

### CR-03: The database Workday allowlist is bypassable with NULL identity fields

**Classification:** BLOCKER

**File:** `supabase/migrations/0035_generic_workday_fidelity.sql:28-44`

**Issue:** `region` and `site_token` are nullable columns. PostgreSQL accepts a `CHECK` expression that evaluates to `NULL`, not only one that evaluates to `TRUE`. A Workday row such as the Capital One board/source key with `region = NULL` or `site_token = NULL` makes its tuple conjunction `NULL`, and the overall allowlist expression can also be `NULL`; the row therefore passes `companies_workday_identity_check` despite not matching either exact identity. `companies_region_check` explicitly permits `region IS NULL`, and `claim_due_companies` checks only the Workday source key at lines 273-277, so malformed active rows are claimable and repeatedly fail only later in application dispatch. The migration's text-regex test cannot detect this truth-table bug.

**Fix:** Because 0035 is already reported as deployed, do not edit it. Add a forward-only 0036 migration that makes the Workday branch itself required to be `TRUE`, for example:

```sql
check (
  ats_type <> 'workday'
  or (
    (
      board_token = 'capitalone'
      and region = 'wd12'
      and site_token = 'Capital_One'
      and source_key = 'workday:wd12:capitalone:Capital_One'
      and activation_state in ('experimental', 'active')
    )
    or (
      board_token = 'fmr'
      and region = 'wd1'
      and site_token = 'FidelityCareers'
      and source_key = 'workday:wd1:fmr:FidelityCareers'
      and activation_state in ('experimental', 'active')
    )
  ) is true
)
```

Exercise the constraint against a real PostgreSQL test database with NULL `region` and NULL `site_token` cases; regex parity assertions are insufficient.

### CR-04: Fidelity is persisted as `fmr`, breaking cross-source fingerprint identity

**Classification:** BLOCKER

**File:** `supabase/functions/_shared/workday-identities.ts:57-67`

**Also affected:** `supabase/functions/_shared/connectors.ts:202-208`, `supabase/functions/verify-board/index.ts:261-275`, `supabase/functions/poll-tick/index.ts:230-237`

**Issue:** Fidelity's identity sets `companyName: null`; verification then falls back to `detected.slug`, so verify-board persists the company name as the tenant code `fmr`. Workday normalized jobs also have a null company name, causing poll-tick to fingerprint them with `company.name`—again `fmr`. Jobs from another source use the real company name `Fidelity`, so identical postings cannot match the same cross-source fingerprint and exact-once deduplication is defeated. The catalog masks the bad name in Watchlist presentation but does not correct the company row or job fingerprints.

**Fix:** Give the frozen Fidelity identity the truthful stable name `Fidelity` and use it for both verification and normalized jobs. Since the incorrect row and jobs are already in production, repair them only through a reviewed forward migration/controlled lifecycle operation keyed to the exact Fidelity source key; update or recompute affected fingerprints consistently rather than changing only `companies.name`.

```ts
const fidelityIdentity: WorkdayIdentity = Object.freeze({
  // ...
  companyName: 'Fidelity',
})
```

Add a test proving a Fidelity Workday job and an otherwise-identical `Fidelity` aggregator job produce the same fingerprint input.

### CR-05: Listing/tombstone collision checks compare different requisition identifiers

**Classification:** BLOCKER

**File:** `supabase/functions/_shared/adapters/workday.ts:270-272`

**Also affected:** `supabase/functions/_shared/adapters/workday.ts:783-799`, `supabase/functions/_shared/adapters/workday.ts:957-971`

**Issue:** `listingRequisitionIdentifier` captures the entire terminal string after `_`. For normal Workday occurrence paths such as `_R200001-1` or Fidelity numeric paths such as `_2130089-2`, it returns `R200001-1` or `2130089-2`. Tombstones carry the canonical identifier (`R200001` or `2130089`). The collision sets therefore do not recognize that a listing and tombstone refer to the same requisition, allowing contradictory rows to be counted as complete and potentially allowing the listed form to be ingested.

**Fix:** Derive collision identity with the same authoritative normalization used by `listExternalId`, including bullet-field binding for numeric IDs, and use that canonical ID in both polling and verification.

```ts
function listingRequisitionIdentifier(posting: WorkdayListPosting) {
  return listExternalId(posting)
}
```

Add collision cases for both `_R200001-1` + tombstone `R200001` and `_2130089-2` + tombstone `2130089`.

### CR-06: “Exact-equivalent” overlap ignores the numeric identity field

**Classification:** BLOCKER

**File:** `supabase/functions/_shared/adapters/workday.ts:247-255`

**Also affected:** `supabase/functions/_shared/adapters/workday.ts:956-964`

**Issue:** Verification accepts repeated paths when title, location, and posting age match, but `equivalentListPosting` does not compare `bulletFields`. For Fidelity's numeric postings, that field is the authoritative requisition identity. Two rows with the same path/display fields but conflicting bullet identifiers are therefore treated as exact-equivalent overlap and can contribute to a supposedly complete activation observation. This contradicts the release claim that only byte-equivalent overlap is tolerated.

**Fix:** Parse and compare the canonical requisition identity (or all validated identity-bearing fields) before accepting overlap. A mismatch must throw `provider_identity_drift` or `count_mismatch`.

```ts
return left.externalPath === right.externalPath
  && listExternalId(left) === listExternalId(right)
  && left.title === right.title
  && left.locationsText === right.locationsText
  && left.postedOn === right.postedOn
```

Add a verification regression with identical path/title/location/date but different one-element `bulletFields` arrays.

## Warnings

### WR-01: Provider identity drift escapes the observation contract

**Classification:** WARNING

**File:** `supabase/functions/_shared/adapters/workday.ts:822-865`

**Issue:** `listExternalId` and `mapRecentDetail` can throw `ProviderError('provider_identity_drift')` outside the request try/catch. The integration tests explicitly expect promise rejection for these cases. Poll-tick catches that only at the company boundary, discards any already validated partial rows, and records generic `source_poll_failed` rather than the bounded provider diagnostic. Other adapter failures return a closure-ineligible `PollObservation`, so this is an inconsistent and less informative failure path.

**Fix:** Catch `ProviderError` around candidate identity derivation and mapping and return `incomplete(jobs, error.code, candidates.length, pageCount)`. Update the tests to assert a partial/unknown observation with `provider_identity_drift`, not a rejected promise.

### WR-02: The UI does not recognize the emitted `provider_timeout` health code

**Classification:** WARNING

**File:** `web/src/lib/watchlist.ts:284-296`

**Also affected:** `supabase/functions/_shared/adapters/workday.ts:346-350`

**Issue:** Workday emits `provider_timeout`, and `observationHealthUpdate` persists that warning as `last_error_code`. `degradedDetail` recognizes only `timeout`, so the production Fidelity timeout described in the phase evidence renders the generic “Latest sync could not be completed” message instead of the intended timeout-specific copy.

**Fix:** Treat both bounded codes identically and add a presentation test for the exact adapter-emitted value.

```ts
if (code === 'timeout' || code === 'provider_timeout') {
  return 'Timed out while syncing.'
}
```
