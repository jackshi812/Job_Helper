# Phase 03.9: JPMorgan Chase Selective Oracle Monitoring - Context

**Gathered:** 2026-07-26
**Status:** Ready for planning

<domain>
## Phase Boundary

Turn the existing fail-closed JPMorgan Chase Oracle Recruiting candidate into
a narrowly scoped monitored source. Poll only exact United States postings
from the preceding seven days in six owner-approved, provider-owned job
families, then pass accepted jobs through the normal user preference filters.

This phase covers JPMorgan Chase only. It does not reopen Phase 03.8, change
the four active Workday companies from that phase, implement Goldman Sachs or
Charles Schwab, redesign the Watchlist or Dashboard, or weaken safe closure,
activation, authentication, and source-identity contracts.

</domain>

<decisions>
## Implementation Decisions

### Company and Portal Scope
- **D-01:** Target exactly JPMorgan Chase through the primary public Oracle
  Recruiting Candidate Experience site `CX_1001`.
- **D-02:** Treat the current official `/jobs` route as the canonical
  navigation route. Preserve compatibility with the previously reviewed
  `/requisitions` route only if research proves it is an exact redirect to the
  same frozen site identity; no caller-controlled Oracle host, site, facet, or
  path is authorized.
- **D-03:** JPMorgan remains isolated from Goldman Sachs, Charles Schwab, and
  every existing connector. Success or failure here must not mutate another
  company's identity, health, activation, jobs, or scheduling.

### Selective Oracle Scope
- **D-04:** Admit exact United States jobs only. A provider location facet is a
  list filter, not sufficient country proof by itself; every persisted job must
  retain authoritative United States detail evidence.
- **D-05:** Admit only postings in Oracle's provider-owned **Finance**,
  **Data & Analytics**, **Risk**, **Product/Investment Management**,
  **Strategy & Development**, and **Program Analysts & Associate** job
  families.
- **D-06:** Apply Oracle's **Less than 7 days** posting-date facet at the source.
  Also validate the posting timestamp so a missing, malformed, ignored, or
  drifted facet cannot admit an older job or authorize closure.
- **D-07:** Category/job-family admission must come from exact provider facets
  and fields. Titles and descriptions may be used later by the normal
  preference system, but they must never manufacture missing Oracle scope
  evidence.
- **D-08:** The source connector performs company, country, recency, and
  provider-family scoping. Existing user preferences remain the downstream
  relevance filter and are not duplicated or bypassed in the connector.

### Completeness, Activation, and Acceptance
- **D-09:** Reconcile every selected Oracle slice with stable IDs, pagination,
  expected counts, exact facet labels, and job-detail evidence. Deduplicate
  jobs that appear in more than one selected family.
- **D-10:** Any provider drift, ignored facet, schema mismatch, count mismatch,
  cap, timeout, missing detail, non-U.S. detail, or stale posting produces an
  incomplete observation. Incomplete observations retain last-known jobs and
  authorize no missing-job closure.
- **D-11:** Reuse the existing Experimental-to-Active admission contract:
  three clean server-timed positive observations followed by one healthy
  natural scheduled poll on the exact deployed release.
- **D-12:** Phase acceptance requires at least one eligible JPMorgan job
  persisted end-to-end with exact source, U.S., recency, and provider-family
  evidence. If the live provider cannot prove that contract, JPMorgan remains
  truthfully Unsupported with a precise bounded reason rather than being
  labeled monitored.
- **D-13:** Production schema/function deployment, activation observations,
  and signed-in UAT require an explicit exact-release approval. Local
  implementation and deterministic verification precede that checkpoint.

### the agent's Discretion
- Choose whether the safest implementation uses one Oracle request per title
  family or a smaller equivalent query set, provided every selected family is
  independently proven and reconciled.
- Choose exact request/page/detail bounds, concurrency, invocation reserve,
  stagger, migration numbering, fixtures, and evidence digests without
  weakening D-04 through D-13.
- Choose how to represent provider title-family provenance in the existing
  bounded `scope_evidence` contract while maintaining compatibility with
  current job rows and all other connectors.

</decisions>

## Existing Code Insights

### Reusable Assets
- `pollJpmorganOracleRecruiting` already provides strict JSON-only requests,
  per-slice pagination, detail hydration, deduplication, bounded execution,
  country checks, incomplete observations, and aggregate evidence.
- `ORACLE_JPMC_SOURCE_KEY` and `resolveBrandedIdentity` already enforce one
  exact server-owned JPMorgan identity.
- The branded connector registry, `verify-board`, observation ledger,
  activation RPCs, poll scheduler, lifecycle persistence, and health UI are
  already wired; this phase should extend the exact identity and evidence
  contract rather than create a parallel ingestion path.

### Established Patterns
- Deployed migrations are immutable; every schema/catalog/activation change is
  a new forward-only migration.
- Provider filters must be verified from response identity and exact labels.
  A request parameter alone is never trusted as proof that the provider
  honored the requested scope.
- Partial, empty, capped, timed-out, or drifted observations never close
  last-known jobs.
- Each candidate activates independently after repeatable clean observations,
  and final acceptance is bound to immutable migration/function/web hashes.

### Integration Points
- Extend the JPMorgan identity with the approved title-family facets and the
  seven-day posting-date facet.
- Extend the Oracle adapter's request construction, page reconciliation,
  detail validation, deduplication, and `scope_evidence` generation.
- Extend deterministic Oracle identity/adapter/connector/observation tests.
- Add a forward migration that moves JPMorgan from catalog-only Unsupported to
  exact Experimental authority without changing other companies.
- Add a Phase 03.9 release verifier and explicit approval checkpoint before any
  production mutation.

</code_context>
