## User Constraints (from CONTEXT.md)

### Phase Boundary

Expand the completed Phase 2 ingestion architecture beyond Greenhouse, Lever, and Ashby. This phase is a representative source-coverage proof, not a requirement to pre-populate 100 companies and not a promise to scrape every arbitrary career website. It adds one test company for each feasible additional platform, validates an agreed set of major finance-company career sites, adds a Link column, and hardens degraded-source behavior. Scoring, preferences, notifications, resume tailoring, and arbitrary universal scraping remain outside this phase.

### Implementation Decisions

#### Coverage strategy
- **D-01:** Use a **major-employers-first** strategy. Prefer stable shared adapters; add allowlisted company-specific adapters only when a branded site cannot be resolved to a reusable platform.
- **D-02:** Do not seed 100 companies in this phase. Prove connectivity with one publicly testable company per supported source platform.
- **D-03:** Preserve existing Greenhouse, Lever, and Ashby support. Research and attempt representative coverage for SmartRecruiters, Recruitee, Workday, Oracle Recruiting, iCIMS, SuccessFactors, and Eightfold.
- **D-04:** A named platform is a research target, not a pre-judged guarantee. If its public access path is authenticated, prohibited, bot-blocked, or too unstable for safe polling, document the evidence and leave it unsupported rather than disguising scraping as reliable coverage.

#### Branded/custom finance validation set
- **D-05:** Validate direct-source coverage for: Morgan Stanley, Goldman Sachs, JPMorgan Chase, Bank of America, Citi, BlackRock, Wells Fargo, UBS, Barclays, Capital One, Fidelity, and Charles Schwab.
- **D-06:** Detect the underlying ATS/portal behind each branded domain first. Reuse a shared adapter when possible. Build a company-specific adapter only for a truly custom public source.
- **D-07:** Branded/custom adapters are explicit allowlist entries, not a generic arbitrary-HTML scraper.

#### Watchlist link
- **D-08:** Add a **Link** column to the Watchlist table.
- **D-09:** The link uses the stored canonical job-search/careers URL and opens in a new tab with safe external-link attributes. Prefer a directly searchable job board over a generic corporate careers landing page.

#### Failure semantics
- **D-10:** When a source is blocked, changed, failed, or implausibly empty, preserve last-known jobs and show **Degraded** with last-success time and useful error detail.
- **D-11:** A failed or implausibly empty observation must never mark jobs closed. Closure remains allowed only after a credible successful source response.
- **D-12:** Do not silently substitute Adzuna for a failed direct source in this phase. Direct-source degradation must remain visible and attributable.

#### Activation
- **D-13:** Use staged activation for every new connector: manual verification, fixture/contract tests, several successful syncs, then scheduled polling.
- **D-14:** Keep unstable connectors manual or disabled until they meet the activation gate. The UI and planning artifacts must distinguish experimental, active, and degraded states.

#### Claude's Discretion
- Select the representative company for each public platform based on a currently reachable, legally usable, publicly testable endpoint.
- Define adapter interfaces and whether platform detection uses URL patterns, a provider registry, or both.
- Choose the exact number of consecutive successful syncs required for activation, with a minimum of two observations across separate polling opportunities.
- Choose per-host rate limits, pagination caps, timeouts, and retry/backoff values within Supabase Edge and free-tier constraints.
- Group finance sites by their detected underlying provider after research; the named company list is fixed, but one shared adapter may satisfy several companies.

### Deferred Ideas

- Pre-populating a catalog of 100 companies — explicitly not required for this phase.
- A universal arbitrary-site scraper or headless-browser farm.
- Adzuna fallback that masks a failed direct source.
- Guaranteed global/locale-complete coverage for every named finance company.
- Scoring, feed, and notifications — remain Phase 3.

## Executive Summary

Phase 02.1 should be planned as a **connector platform and evidence-backed coverage proof**, not as twelve one-off scrapers. Two new sources are suitable for normal shared adapters now: SmartRecruiters and Recruitee. Workday's public candidate CXS endpoint is demonstrably usable for Capital One, but it is undocumented; it should be implemented behind an explicit tenant/site registry and remain `experimental` until fixture tests and a three-observation hosted soak pass. The official or documented machine APIs for Oracle Recruiting, iCIMS, SuccessFactors, and Eightfold require privileged credentials, are restricted to partners/internal use, or lack a supported anonymous listing contract. D-04 therefore requires an honest `unsupported_with_reason` disposition unless a separate public candidate contract is proven during execution.

The most important engineering work is not another parser. The current `poll-tick` returns only `NormalizedJob[]`, dispatches Greenhouse/Lever explicitly, and otherwise implicitly falls through to Ashby. It can distinguish an exception from a non-empty success, but it cannot express partial pagination, detail-fetch failure, or a provider-confirmed credible empty board. Before adding providers, introduce an exhaustive source registry and a `PollObservation` result whose `complete` and `credibleForClosure` fields are required before lifecycle closure. This makes D-10/D-11 true by construction and prevents a portal schema change from mass-closing jobs.

The finance-company validation set is useful even where monitoring is unsupported: it establishes the canonical link, detected platform, access boundary, representative probe, and disposition. Capital One is the strongest active finance proof through Workday. Morgan Stanley is Eightfold-backed, JPMorgan Chase is Oracle Recruiting-backed, Charles Schwab is iCIMS-backed, and UBS appears Taleo-backed; the official machine contracts for those platforms are not anonymous general-purpose feeds. Citi, BlackRock, Barclays, and several other branded search sites use Radancy/TalentBrew or custom frontends. A generic HTML adapter would violate D-07 and create unacceptable schema-drift and false-closure risk. Their rows should remain visible and linkable but disabled for scheduled direct polling until a stable, legally usable feed is separately proven.

**Primary recommendation:** first harden the connector contract and schema, then add SmartRecruiters and Recruitee, then add Workday as an experimental allowlisted connector using Capital One, and finally seed the full finance evidence matrix with active/experimental/unsupported dispositions. Do not make phase completion depend on pretending every named platform is feasible.

## Existing Code and Gap Analysis

### Reusable assets

- `supabase/functions/_shared/adapters/{greenhouse,lever,ashby,adzuna}.ts` already isolates provider parsing and returns the shared normalized job shape.
- `supabase/functions/_shared/detect.ts` is a pure URL-to-provider detector and constructs allowed polling endpoints rather than fetching arbitrary user URLs.
- `supabase/functions/verify-board/index.ts` provides the correct server-authoritative one-live-call boundary.
- `supabase/functions/_shared/lifecycle.ts` already avoids closure for an empty returned set and supports reopening.
- `supabase/functions/poll-tick/index.ts` already records success/failure health and has an implausibly-empty guard when open jobs exist.
- `web/src/lib/watchlist.ts` and `web/src/pages/Watchlist.tsx` are the correct seams for PREF-05 and richer health/activation display.

### Gaps that must be addressed before adding connectors

1. `NormalizedJob.source` is a literal union of Greenhouse, Lever, Ashby, and Adzuna. Expand only for adapters actually implemented.
2. `detect.ts` returns only Greenhouse, Lever, or Ashby. Detection must become registry-driven and must reject host lookalikes.
3. `companies.ats_type` is constrained to three values; `jobs.source` is constrained to four. Schema migration must retain strict validation rather than changing these fields to arbitrary unchecked strings.
4. `companies` stores provider token/region but not the human-facing canonical careers URL. Add `careers_url` separately from polling identity.
5. The current `pollCompany` has explicit Greenhouse and Lever branches and an implicit Ashby fallback. Adding types to that union could route an unknown provider into Ashby. Replace with an exhaustive provider registry before expanding the union.
6. `NormalizedJob[]` cannot distinguish complete, partial, empty-but-credible, malformed, or detail-incomplete observations. Without this distinction, new paginated connectors can create false closure.
7. Current health derives `ok/failing/stale` from failure counts and times. Phase 02.1 also requires connector activation (`experimental/active/disabled`) and operational health (`ok/degraded/stale`) to be distinguishable.
8. Current unique company identity `(ats_type, board_token)` cannot represent providers with tenant plus site (for example Workday). Add an explicit stable `source_key` or a null-safe unique provider/tenant/site identity.

## Recommended Architecture

### 1. Provider registry, not a growing switch

Use one registry shared by detection, verification, and polling:

```ts
type ProviderId =
  | 'greenhouse'
  | 'lever'
  | 'ashby'
  | 'smartrecruiters'
  | 'recruitee'
  | 'workday'

type ConnectorIdentity = {
  provider: ProviderId
  tenant: string
  site?: string
  region?: string
}

type PollObservation = {
  jobs: NormalizedJob[]
  completeness: 'complete' | 'partial' | 'unknown'
  credibleForClosure: boolean
  pageCount: number
  expectedCount?: number
  warnings: string[]
}

type ProviderConnector = {
  detect(url: URL): ConnectorIdentity | null
  canonicalPollUrl(identity: ConnectorIdentity): URL
  verify(identity: ConnectorIdentity): Promise<PollObservation>
  poll(identity: ConnectorIdentity): Promise<PollObservation>
}
```

The registry must construct URLs from validated pieces. Never persist or fetch a raw user-supplied polling URL. `ProviderId` remains closed and exhaustive, so an implemented connector and a database enum/check constraint move together.

### 2. Separate activation from health

Recommended state model:

- `activation_state`: `experimental | active | disabled`
- `health_state`: derived or stored as `ok | degraded | stale`
- `last_success_at`, `last_error`, `last_error_code`, `consecutive_failures`
- `activation_successes`, `last_verified_at`, `last_observation_count`

Recommended activation gate: manual verify succeeds, fixture/contract tests pass, then **three** complete successful observations across separate scheduled opportunities. Three is still lightweight but is stronger than the locked minimum of two for an undocumented portal. An experimental connector is never selected by the normal due queue. A dedicated verification/soak action records its successes; only the server/service role can transition it to active.

Operational degradation does not automatically alter activation. An active connector may become degraded and back off while preserving last-known jobs. Repeated authentication/prohibition/schema errors may require an explicit disable action, never an automatic provider substitution.

### 3. Closure is a capability of an observation

Only call lifecycle closure when all are true:

- HTTP and parsing succeeded;
- all bounded pages required for the connector were received;
- required details were fetched for every job whose normalized record depends on them;
- provider count/pagination invariants reconcile;
- observation is not implausibly empty relative to prior state;
- connector sets `credibleForClosure: true`.

Any timeout, 429, WAF response, malformed object, exceeded pagination cap, detail fan-out failure, or unexplained sharp count drop produces `partial`/`unknown`, marks health Degraded, preserves every existing job, and skips closure. A genuinely empty new board may be recorded as success only after provider-specific count evidence confirms zero; for experimental sources, require a subsequent separate confirmation before allowing empty-board closure.

### 4. Schema direction

Prefer an additive migration:

- `companies.careers_url text` with HTTPS validation and an explicit backfill policy for existing rows;
- `companies.site_token text` and `companies.source_key text unique` for multi-part provider identity;
- strict expanded `ats_type` check only for implemented adapters;
- `activation_state`, activation counters, `last_verified_at`, `last_error_code`, and `last_observation_count`;
- strict expanded `jobs.source` check only for implemented adapters.

Do not store arbitrary endpoint templates in `provider_config` if the server can derive them from a typed identity. If JSON configuration is unavoidable, validate every field against a provider-specific schema before network use and exclude raw URLs.

Backfill existing Greenhouse/Lever/Ashby rows as `active`; preserve all job rows and uniqueness. Existing canonical URLs may be derived from provider/token when no original user URL was stored, but future adds must retain the directly searchable canonical link.

## Provider Implementation Notes

### SmartRecruiters

- Detect only exact approved board/API host patterns; the company identifier is a conservative slug.
- Use offset/limit with a fixed page cap and reconcile `totalFound` against collected records.
- Fetch detail only if the list omits fields required by `NormalizedJob`/snapshot.
- Treat the documentation/authentication conflict as a contract risk: store a fixture from the current anonymous response, capture status/content-type/schema during manual verification, and keep experimental until three independent successes.
- A 401/403 is a hard degraded observation and must never trigger fallback or closure.

### Recruitee

- Detect exact `{tenant}.recruitee.com` public career hosts; reject nested/lookalike suffixes.
- Use the documented `/api/offers/` endpoint, validate wrapper/array shape, and preserve the public offer URL as the apply URL.
- Confirm pagination semantics with a current board fixture during implementation because the official example board is stale.
- No credentials are needed for the Careers Site API, so no secret-management addition is required.

### Workday

- Store explicit region host, tenant, and site values; construct the CXS URL from a provider allowlist. Never accept an arbitrary `wdNN` URL as an endpoint without parser validation.
- POST a fixed JSON body with bounded `limit`/`offset`; reconcile `total` and page lengths. Cap total pages and mark a truncated run partial.
- Treat detail paths as untrusted relative paths: reject schemes, protocol-relative values, `..`, and any final origin change.
- Start with one allowlisted identity: Capital One / `wd12` / tenant `capitalone` / site `Capital_One`.
- Because CXS is undocumented, any response-shape change is Degraded, not an empty success. Keep a fixture and a non-destructive hosted contract probe.

### Unsupported providers

Oracle, iCIMS, SuccessFactors, and Eightfold should still be represented in the source matrix and UI data model, but must not be inserted into the pollable `ats_type` constraint unless an adapter is implemented. Model unsupported catalog evidence separately from live `companies` rows, or allow a disabled connector record whose scheduler selection explicitly requires `activation_state = 'active'`. Do not let an unsupported provider value reach polling dispatch.

## Watchlist UI Behavior

- Add a `Link` column using the stored `careers_url`.
- Display a short accessible label such as `Open jobs` rather than the full URL; include an external-link indicator if consistent with the existing design.
- Use `target="_blank" rel="noopener noreferrer"` and only render clickable `https:` values. Malformed or legacy-missing links render `Unavailable`, never raw HTML.
- Show activation and health separately. Examples: `Experimental · 2/3 checks`, `Active · OK`, `Active · Degraded`, `Disabled · unsupported API`.
- Degraded detail should include last successful sync, concise error code/message, and the fact that last-known jobs were retained.
- Unsupported finance entries should remain useful as canonical links but must not be labeled monitored.

## Scheduling and Resource Controls

No new universal cadence should be assumed. Keep the existing direct-source 5–15-minute target for connectors that are active and capacity-safe. Recommended initial controls:

- Greenhouse/Lever/Ashby: preserve current cadence.
- SmartRecruiters/Recruitee: active cadence of 10 minutes after soak, subject to observed headers/terms.
- Workday: manual/experimental checks no more than every 30 minutes during soak; only move toward 10–15 minutes if repeated calls are stable and allowed.
- Unsupported/custom/WAF-backed sources: no schedule.
- Per-host concurrency: 1 during experimental soak, at most 2 for documented APIs unless the provider publishes a higher safe limit.
- Request timeout: 15 seconds; bounded retry only for transient network/5xx/429, honoring `Retry-After`.
- Pagination: provider-specific caps plus total-count reconciliation; exceeding a cap means partial, never success-for-closure.
- Payload: enforce content-type and maximum bytes before parsing; limit description/detail fan-out.

This phase should not change the user-approved Adzuna schedule (every 30 minutes from 06:00 to noon Chicago, then every two hours). Direct-source failure must remain visible and must never be hidden by Adzuna results.

## Security and Compliance

### SSRF and redirect control

- Parse user input with `URL`, require HTTPS, and match exact/suffix-safe provider hosts.
- Construct network targets from typed provider identity and fixed templates; never `fetch(careers_url)` or a stored raw polling endpoint.
- Use manual redirect handling or revalidate every redirect target against the same allowlist. Reject redirects to private/link-local/loopback hosts, alternate schemes, credentials in URLs, or unexpected ports.
- For Workday detail `externalPath`, append only a validated relative path to the already approved origin.

### Untrusted response handling

- Treat every third-party JSON/HTML field as untrusted data. Validate root types, required scalar types, lengths, counts, and pagination invariants before normalization.
- Bound response bytes, nesting, page count, job count, and detail fan-out to prevent memory/CPU exhaustion in Supabase Edge.
- Store descriptions as data and render through the existing safe path; never execute provider HTML/scripts.
- Redact query strings, credentials, response bodies, and applicant links from logs. Use stable error codes plus bounded diagnostic text.

### Authorization and state transitions

- Users may add/edit/remove their shared watchlist according to existing policy, but only server/service-role verification may mark a connector active or increment activation successes.
- RLS must continue to prevent direct mutation of operational health/activation columns from the browser.
- Unsupported or disabled sources must be excluded at the database claim query as well as in application dispatch.

### Public-access boundaries

- Do not log in, bypass CAPTCHA/WAF, rotate identities to evade controls, or call endpoints documented as internal/partner-only.
- Record robots and terms evidence per host before activation. A restrictive robots rule prevents polling that path; a permissive rule does not by itself grant permission.
- Use a clear product user agent and conservative rate limits where the provider permits automated public access.

## Common Pitfalls

1. **Treating HTTP 200 as a credible observation.** A WAF page, empty wrapper, partial page, or changed schema may all be 200. Validate content type, schema, counts, and completeness.
2. **Expanding the provider union before dispatch is exhaustive.** The current implicit Ashby fallback would misroute a new provider.
3. **Equating a branded careers hostname with its ATS.** Detect the authoritative listing backend and preserve the branded URL only as the user-facing link.
4. **Using official customer APIs as if they were public job feeds.** Workday REST, iCIMS, SuccessFactors, and Eightfold official APIs generally require customer/partner credentials.
5. **Closing on pagination/detail failure.** Any incomplete fan-out invalidates closure even if some jobs were returned.
6. **Building a generic Radancy/custom HTML scraper.** It violates D-07 and multiplies schema-drift, compliance, and false-closure risk.
7. **Calling an unsupported link monitored.** The evidence catalog and scheduled connector state must be distinct.
8. **Losing the canonical URL during ATS normalization.** Store `careers_url` independently from tenant/site identity.

## Planning Recommendations

### Suggested plan boundaries

1. **Connector contract and schema hardening:** provider registry, `PollObservation`, credible-closure gating, activation/health fields, canonical `careers_url`, migrations/backfills, and regression tests for existing providers.
2. **Watchlist Link and state UI:** Link column, safe external behavior, activation/Degraded detail, and unsupported-state truthfulness.

5. **Finance coverage catalog and acceptance checkpoint:** seed/record all twelve canonical links and evidence dispositions; explicitly resolve the DISC-08 wording conflict before phase completion.

Plans 1 and 2 may run in parallel only after the migration contract is fixed. SmartRecruiters/Recruitee and Workday adapters can be implemented in parallel after the registry lands. The finance catalog should consume adapter results, not define separate scraper implementations.

- Existing Greenhouse, Lever, and Ashby fixture/regression suites remain green.
- A simulated exception, 429, WAF HTML 200, malformed JSON, partial pagination, detail failure, and implausible empty response each preserve jobs and skip closure.

- All twelve finance companies have canonical links, detected provider/front end, evidence, and an honest active/experimental/unsupported disposition.
- Watchlist Link opens safely in a new tab and unsupported sources are never presented as monitored.
- DISC-08 is either narrowed/clarified or explicitly accepted as validation-with-documented-unsupported outcomes; no plan may mark it complete merely because links were added.
