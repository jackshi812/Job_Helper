## Narrative Findings (AI reviewer)

## Summary

The provider identities, closed registry, bearer-token boundary, activation RPC privileges, closure credibility checks, and Workday origin/path restrictions are generally fail-closed. Four actionable defects remain: the hosted pipeline verifier mutates an arbitrary production job without a race-safe restore; successful experimental observations are rendered as degraded; SmartRecruiters detail fan-out has no invocation-wide budget; and removal failures are exposed outside the active modal.

## Critical Issues

### CR-01: The “non-destructive” hosted verifier mutates an arbitrary production job and cannot restore it safely

**Classification:** BLOCKER  
**File:** `scripts/verify-pipeline.ts:470-511,563-569`  
**Issue:** Probe 15 selects an arbitrary open job belonging to one of the real seed companies, changes it to `closed`, backdates `last_seen_at`, and forces a real poll. On the success path, line 511 clears `reopenProbeRestore`, so the original `last_seen_at` is never restored. On an error path, the `finally` block unconditionally writes `status = 'open'`; if a concurrent scheduler legitimately closed the job after the snapshot, the verifier resurrects it. If the provider removes the selected posting during the probe, the assertion fails and the unconditional cleanup also reopens a job that should remain closed. This contradicts Plan 07's non-destructive/rerunnable contract and risks corrupting production lifecycle state.

**Fix:** Never exercise reopen behavior against a pre-existing production job. Create an invocation-scoped, exact-prefix disposable company/job fixture whose full lifecycle is owned by the verifier, then remove it in `finally`. If an existing row absolutely must be used, persist every original field and use compare-and-swap predicates over every value written by the probe before restoring; however, a disposable fixture is the only robust approach under a live scheduler.

### CR-02: Successful experimental verification is displayed as degraded forever for unscheduled Workday

**Classification:** BLOCKER  
**Files:** `supabase/migrations/0015_activation_windows.sql:197-209`; `web/src/lib/watchlist.ts:105-110,127-131`  
**Issue:** An accepted activation observation updates `last_verified_at`, clears `last_error_code`, and increments progress, but it never updates `last_success_at`. The Watchlist health mapper ignores `last_verified_at` and classifies every row with `last_success_at === null` as degraded. A newly verified experimental connector therefore shows `Degraded` even after one, two, or three complete credible observations. Capital One Workday is intentionally never scheduled, so it can never acquire a polling `last_success_at` and remains falsely degraded after the hosted 3/3 success. This directly contradicts the UI contract that an experimental connector's last success refers to verification/soak observations and that a complete latest observation renders `OK`.

**Fix:** Model the latest credible observation timestamp explicitly. The cleanest fix is a dedicated server-owned `last_observation_success_at` updated atomically by both accepted manual verification and credible scheduled polls, then use it for Watchlist health. A smaller fix is to make experimental presentation use `last_verified_at` when `activation_successes > 0` and no error is present, while active rows continue using polling `last_success_at`. Add a test for Workday at 3/3 with `last_success_at: null`, `last_verified_at` set, and no error; it must render `OK` with the verification timestamp.

## Warnings

### WR-01: SmartRecruiters detail fan-out can exceed the Edge invocation lifetime

**Classification:** WARNING  
**File:** `supabase/functions/_shared/adapters/smartrecruiters.ts:263-287`  
**Issue:** The adapter permits up to 1,000 postings and performs required detail requests in sequential batches of two. Each request has its own 15-second timeout, but there is no total detail-count or wall-clock budget. A valid large board whose list records omit descriptions can therefore require hundreds of sequential batches and outlive the Supabase Edge invocation. The function is then terminated externally rather than returning the intended closure-ineligible partial observation, defeating the adapter's bounded/degraded contract.

**Fix:** Add an invocation-wide deadline and a conservative detail budget suitable for the deployed Edge limit. Before starting each batch, stop and return the validated list rows as `partial` with a stable code such as `detail_budget_exceeded`. Keep the concurrency cap of two, and test that exceeding the total detail/time budget returns promptly without closure credibility.

### WR-02: Removal failures are announced outside an active aria-modal dialog

**Classification:** WARNING  
**Files:** `web/src/pages/Watchlist.tsx:209-213,284-294`; `web/src/components/ConfirmDialog.tsx:72-80,83-117`  
**Issue:** `ConfirmDialog` catches a rejected `onConfirm` and remains open, while the mutation's `role="alert"` is rendered on the page behind the `aria-modal` dialog. Focus remains trapped inside the dialog and assistive technology is expected to treat content outside an aria-modal as unavailable. The user can therefore be left in an unchanged modal without an accessible explanation of why removal failed.

**Fix:** Pass the bounded mutation error into `ConfirmDialog` and render a linked `role="alert"` inside the dialog (optionally via `aria-describedby`). Keep both actions usable after the request settles so the user can retry or cancel. The page-level alert may remain for failures that occur after the dialog closes, but it must not be the sole error channel while the modal is active.
