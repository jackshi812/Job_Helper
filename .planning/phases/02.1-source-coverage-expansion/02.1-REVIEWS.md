## Plan 01 — PollObservation and closure-safe degradation

**Summary:** Correctly targeted highest-risk gap first. `lifecycle.ts:58` proves the danger is real and currently latent (existing adapters return full lists, so no live bug — but any paginated provider added without this plan would mass-close). Right sequencing: contract before providers.

**Strengths**
- Exact-file scope (5 files) matches the real seams; `planCompanySync` at `lifecycle.ts:30` is the single closure authority and `poll-tick/index.ts:237` its only caller — one gate to guard.
- Positive-case requirement ("closure remains possible after credible complete evidence") prevents over-tightening into never-close.
- Preserves `Promise.allSettled` isolation (`poll-tick/index.ts:285-287`) and heartbeat-first ordering (274-277).

**Concerns**
- **MEDIUM** — Plan 01 must_have says failures "report Degraded", but no `Degraded` state exists in schema until Plan 02's migration 0012. In wave 1 the only representable failure state is `consecutive_failures`/`last_error` (`0005_watchlist.sql:15-16`). The truth is satisfiable only in a weakened sense (failure recorded, closure skipped). Wording should say "recorded as failed, never closed" for wave 1.
- **LOW** — File named `source-observation.e2e.test.ts` but is fixture-driven Vitest, no network. Misleading name, harmless.
- **LOW** — Task 2 rewires `poll-tick` dispatch explicitly; Plan 02 Task 3 then replaces that same dispatch with `pollConnector`. Deliberate staging, but same code rewritten twice within two waves.

**Risk: LOW** — pure refactor with strong existing test scaffolding (`lifecycle.test.ts` 12 cases already green).

## Plan 02 — Registry, server-owned state, verified-add

**Summary:** Attacks two verified real gaps: browser-forgeable operational columns (`0005_watchlist.sql:35-38`) and browser-side insert (`watchlist.ts:62-71`). Direction correct. One mechanism under-specified.

**Strengths**
- "Active-only in claim SQL AND application guard" is correct defense-in-depth; current `claim_due_companies` (`0008:11-18`) filters nothing but due time.
- `returns setof public.companies` (`0008:6`) means new columns flow to `poll-tick` automatically after migration — low breakage.
- Backfill honesty: no URL column exists in `companies` (`0005:7-19`), so deriving canonical links from `ats_type`/`board_token` is the only option; research acknowledges this and plan follows.

**Concerns**
- **HIGH** — "Narrow browser mutation authority so operational fields are server-owned" names no mechanism. Postgres RLS policies are row-level, not column-level. Achieving this needs either column-level `GRANT UPDATE (name) ...` replacing the table-wide grant at `0005:25`, revoking `insert`/`update` entirely (since verify-board now inserts server-side), or a trigger rejecting operational-column changes. Migration 0012 must pick one; executor guessing here risks a policy that looks narrowed but isn't. Specify: revoke `insert, update` from `authenticated`, keep `select, delete`.
- **MEDIUM** — Moving insert into `verify-board` changes its CORS/authorization posture: it currently returns permissive CORS (`verify-board/index.ts:11-14`) and does no user-identity check beyond gateway JWT. Acceptable for the 2-user app, but the plan should state that any authenticated user's verify call now performs a service-role write — that's the intended shared-watchlist semantics, worth an explicit test.
- **LOW** — `watchlist.test.ts` currently mocks the browser insert path; Task 1 rewrites it. Fine, just churn.

**Risk: MEDIUM** — the RLS-narrowing mechanism gap is the one place an executor can produce something that passes tests but not the threat model.

## Plan 05 — Activation windows, replay rejection

**Summary:** Right invariants (server clock, unique windows, atomic promotion, no client timestamp). One structural testing problem.

**Concerns**
- **HIGH** — `web/tests/activation-policy.test.ts` cannot execute a `security definer` plpgsql RPC using `clock_timestamp()`: Docker absent, Deno absent, no local Postgres (research Environment table confirms). Same limitation Phase 2 hit — its "SQL tests" inspected SQL text, flagged in `02-VERIFICATION.md` anti-patterns ("SQL tests inspect locking/order text rather than execute PostgreSQL"). Plan 05's acceptance criteria ("Database constraints reject replay and same-window duplicates") are therefore unprovable locally; Vitest can only assert migration text or a TypeScript mirror of window logic. Real proof arrives only in Plan 07's hosted run. Plan should say explicitly: local tests = SQL-text/structural + pure-TS window-math mirror; behavioral proof = Plan 07. Otherwise executor may fake a "database clock seam" that tests nothing.
- **MEDIUM** — Promotion path: SmartRecruiters/Recruitee auto-promote at three windows recorded via `verify-board`, which any authenticated user can call. So a user pressing verify three times across 20+ minutes activates scheduled polling with no service-role decision beyond the RPC's own checks. That matches D-13's "manual verification" reading, but it means activation is user-drivable end to end — worth an explicit statement that this is intended.
- **LOW** — Migration 0015 ordering note says "after Plan 04's expansion", but Plan 05 depends only on 04 while 03 (0013) runs parallel in wave 3. If wave gating slips and 03 lags, files 0013/0015 exist out of creation order — harmless since push is deferred to Plan 07, but `supabase migration list` ordering is lexical, so no actual hazard. Noted only.

**Risk: MEDIUM-HIGH** on local-verifiability claims; the design itself is sound.

## Plan 07 — Hosted push, deploy, resumable proof

**Summary:** The load-bearing plan. Structure mirrors proven Phase 2 verifiers (`scripts/verify-pipeline.ts`, `verify-watchlist.ts` exist and passed; conventions cited accurately). Resumability design is genuinely necessary and well-specified.

**Concerns**
- **HIGH (operational, not correctness)** — Wall-clock math: three distinct 10-min windows = ≥20 min minimum for each of SmartRecruiters/Recruitee; three 30-min Workday windows = ≥60 min. With ≤60s polling sleeps, one full run is roughly 60–90 minutes of live agent execution against Bash's 10-min command timeout. The verifier must be architected to exit between windows and rely on `--resume`, not sleep through them in one process — the plan's ≤60s wait rule plus resume supports this, but Task 3's verify command runs the verifier as a single blocking invocation twice. Executor should invoke it repeatedly under resume until complete, and the plan should say so explicitly, or the verify command times out by construction.
- **MEDIUM** — Task 3 "controlled partial/failed/empty retention" probes against hosted state: the reopen-probe restoration pattern (`verify-pipeline.ts:416-457` per PATTERNS) exists, but forcing a *failed observation* for an active hosted connector non-destructively is harder than forcing a state flip — how do you make hosted SmartRecruiters return a WAF page on demand? Likely answer: inject a synthetic company row with an unreachable token, which is fine, but plan doesn't specify and "controlled degraded observation" is doing a lot of unstated work.
- **LOW** — `cd web && npx supabase db push --linked` resolves (supabase 2.109.1 devDep confirmed). Auth-gate handling matches the established checkpoint protocol.

**Risk: MEDIUM-HIGH** — highest execution-failure likelihood of any plan; failure mode is stall/timeout, not bad data.

## Top Recommendations (ordered)

1. **Plan 02:** Specify the exact browser-write-narrowing mechanism in the 0012 migration — revoke `insert, update` on `companies` from `authenticated` (verify-board now owns both), keep `select, delete`. Column-level grants only if a user-editable field remains.
2. **Plan 05:** Rewrite acceptance criteria to separate what Vitest can prove (pure window-math mirror, migration-text assertions) from what only Plan 07's hosted run proves (constraint rejection, `clock_timestamp` behavior). Current wording will push the executor toward fake proof.
3. **Plan 07:** State explicitly the verifier is invoked repeatedly under `--resume` across the ~60–90 min soak, never as one blocking process; budget the wall clock in the plan so the executor doesn't fight command timeouts.
4. **Plan 03/06:** Pin the literal Capital One `source_key` string in one shared place (0013 seed + constant) so catalog/company reconciliation cannot drift.
5. **Plan 04:** Add a fallback disposition for SmartRecruiters if anonymous access closes mid-phase (flip to `unsupported_with_reason`, phase still passes with Recruitee + Workday as the DISC-07 representatives).
6. **Plan 01:** Reword the wave-1 "reports Degraded" truth to "records failure and skips closure" — the Degraded state has no schema representation until Plan 02.

## Overall Risk Assessment

**MEDIUM.** Plans are unusually well-grounded — every code citation checked out, the architectural motivation (partial-observation false closure, forgeable operational columns, Ashby fallback) is verified real, and the sequencing (contract → state → providers → activation → hosted proof → deploy) is correct. Residual risk concentrates in three places: an under-specified RLS narrowing mechanism (fixable in planning), local unprovability of SQL activation logic (structural repo limitation, mitigated by hosted proof), and Plan 07's long-wall-clock hosted soak (operational, resumability designed but invocation strategy under-stated). Nothing found that blocks execution; items 1–3 above are worth fixing before wave 2.
