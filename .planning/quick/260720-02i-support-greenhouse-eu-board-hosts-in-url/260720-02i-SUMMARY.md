## Follow-up candidates

Assessed purely from the code's matching strategy and each provider's `buildEndpoint` branch. No live network calls were made to confirm whether any of these alternate hosts actually exist — that unverified status is exactly what keeps these follow-up candidates rather than work for this task. No gap below was fixed.

**Ashby** — Current strategy: single exact host equality, `host === 'jobs.ashbyhq.com'`. Gap plausibility: plausible, structurally the same failure mode Greenhouse had — one hardcoded display host with no room for an alternate or regional variant, which would fall straight through to `unsupported`. Identity implication: `buildEndpoint` hardcodes one unified API host (`api.ashbyhq.com/posting-api/job-board/{slug}`) with no region branch, so any alternate display host found later would almost certainly be display-only and should fold into a single global identity with no `region` — the Greenhouse pattern, not the Lever one.

**SmartRecruiters** — Current strategy: single exact host equality, `host === 'jobs.smartrecruiters.com'`, plus a `!url.search` rejection. Gap plausibility: plausible, same single-host shape as Ashby; the extra `!url.search` guard also means any regional host that signalled its region through a query parameter would be rejected even if the host itself were allowlisted. Identity implication: `buildEndpoint` targets one unified API host (`api.smartrecruiters.com/v1/companies/{slug}/postings`), so a confirmed alternate host would point to unified identity with no `region`. Caveat: SmartRecruiters is the provider most likely to have genuine data-residency-driven API separation, so this one warrants an actual endpoint probe before assuming unified.

**Recruitee** — Current strategy: structurally different from the others — a suffix match, `host.endsWith('.recruitee.com')`, with the slug derived from the host prefix rather than the path. Gap plausibility: plausible but by a different mechanism. The suffix already admits any subdomain, so a regional host such as `uturn.eu.recruitee.com` would pass the host check and then fail on the slug: the derived prefix `uturn.eu` contains a dot and is rejected by `strictSlug`. The existing `nested.uturn.recruitee.com` negative test pins this behavior. Identity implication: because `buildEndpoint` reconstructs the API URL from the slug (`https://{slug}.recruitee.com/api/offers/`), the slug and the API host are the same value here — so a regional variant could not be folded into one identity as cheaply as Greenhouse was. It would need either a region field or a separate host-to-endpoint mapping, closer to the Lever pattern. Note the suffix match itself is not an SSRF hole: `uturn.recruitee.com.evil.example` does not end with `.recruitee.com`, and it is covered by an existing negative test.
