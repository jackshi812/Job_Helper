# Phase 03.9: JPMorgan Chase Selective Oracle Monitoring - Research

**Researched:** 2026-07-26
**Status:** Complete
**Recommendation:** Implement as a source-specific extension of the existing
fail-closed Oracle adapter, with six exact title-family slices, the seven-day
posting facet, detail revalidation, closure disabled for the rolling window,
and a new forward-only admission migration.

## Executive Summary

JPMorgan is feasible with the owner-approved scope. Its anonymous Oracle
Candidate Experience contract currently honors all three requested dimensions:

- exact site `CX_1001`;
- exact United States location facet `300000000289738`;
- exact posting-date facet `7` / `Less than 7 days`;
- one exact title-family facet per request.

The six selected U.S. seven-day slices returned 134 list rows on 2026-07-26.
Every slice reconciled its reported total in a single 100-row page, every row
had a unique stable numeric ID, `PrimaryLocationCountry: US`, a posting date,
and a `JobFunction` exactly equal to the selected family label. One detail
request from each slice repeated the exact ID, `US` country, exact job
function, parseable full timestamp, and usable full description.

The old connector failed because it was designed around
`SelectedCategoriesFacet=Credit Risk`, requires the list `JobFamily` to equal
that category, and stores a seven-term generic category proof. The approved
scope uses Oracle's broader `SelectedTitlesFacet`; Oracle exposes the selected
family per row and detail as `JobFunction`, while `JobFamily` is a narrower
sub-category. The adapter and database proof must therefore be changed
deliberately rather than swapping facet IDs.

The critical lifecycle result is that a rolling seven-day observation must set
`allowMissingClosure=false`. A job naturally falling out of the seven-day
window is not proof that JPMorgan closed it. This matches the selective Workday
precedent deployed in Phase 03.8.

## Existing-Code Gap Analysis

### Identity model

`OracleRecruitingBrandedIdentity` currently has:

- one country facet;
- `categoryFacets`;
- no posting-date facet;
- the historical `/requisitions` navigation URL.

It should gain exact title-family facets and the exact posting-date facet. The
public navigation URL should become `/jobs`, while detection may accept the
old route only through an exact server-owned alias that resolves to the same
frozen identity.

### List parsing

The current adapter:

- sends `selectedCategoriesFacet`;
- validates `SelectedCategoriesFacet` and `categoriesFacet`;
- requires list `JobFamily` to equal the selected category.

The new contract should:

- send `selectedTitlesFacet` and `selectedPostingDatesFacet`;
- validate `SelectedTitlesFacet`, `SelectedPostingDatesFacet`,
  `titlesFacet`, `postingDatesFacet`, and `locationsFacet`;
- require list `JobFunction` to equal the selected family label;
- retain list `JobFamily` as optional/narrow metadata, never as the selected
  family proof;
- reject missing/malformed dates and rows outside the local seven-day
  backstop.

### Detail parsing

`detailCategory` currently accepts either `Category` or `JobFunction` when a
generic allowed term matches. That is too permissive for the approved exact
family list. JPMorgan detail normalization should require exact
`JobFunction === selectedFamily.expectedLabel`, exact `US`, exact stable ID,
a consistent title, a usable description, and a recent
`ExternalPostedStartDate`.

Use a wall-clock dependency separate from the monotonic invocation-budget
clock. Calendar-day comparison should match the provider's date-only list
semantics while remaining deterministic in tests.

### Evidence model

The existing job evidence shape can remain bounded:

- `sourceKey`;
- `providerCategoryLabel`;
- `matchedTerm`;
- `detailCountryCode`;
- `externalIdDigest`.

For JPMorgan, `providerCategoryLabel` should store the normalized exact
`JobFunction` family. Use a source-specific exact mapping:

| Provider family | Evidence term |
|---|---|
| Finance | Finance |
| Data & Analytics | Data |
| Risk | Risk |
| Product/Investment Mgmt | Investment |
| Strategy & Development | Strategy |
| Program Analysts & Associate | Program Analysts |

Do not make `Strategy` or `Program Analysts` generic admission terms for
Morgan Stanley or Goldman Sachs. The new migration should enforce the six
exact Oracle label/term pairs for `oracle:jpmc:CX_1001`, while preserving
existing evidence bytes for all other sources. Recompute
`externalIdDigest` through the same five-field formula.

Aggregate slice digests should include the source key, exact title-family ID
and label, U.S. facet ID, posting-date facet ID and label, reported/fetched
counts, and page count. The aggregate category/family and country digests can
retain their current field names for compatibility.

### Lifecycle semantics

Return:

- `completeness: complete` only after every one of the six slices and every
  selected detail reconciles;
- `credibleForClosure: true` for a fully proven selective observation;
- `allowMissingClosure: false` always for this rolling seven-day source;
- `expectedCount` equal to the deduplicated normalized job count;
- no warnings on an admissible observation.

All cap, deadline, duplicate, offset, total, facet, schema, country, family,
date, detail, or content failures return a partial/unknown observation and
remain closure-ineligible.

### Production authority

Migration `0043` intentionally removed all branded providers from:

- `record_connector_observation`;
- `claim_due_experimental_connectors`;
- `claim_due_companies`;
- the branded terminalization RPC's execution authority.

A new forward-only migration—expected next number `0045`—must reauthorize
only `oracle:jpmc:CX_1001`. It should not re-enable Eightfold or Goldman.
Required effects:

1. update the exact JPMorgan catalog URL/evidence;
2. provide a replay-safe, service-role-only JPMorgan admission/terminal
   boundary;
3. admit exactly one Experimental company row only after positive exact live
   proof;
4. permit Oracle in the shared observation RPC only for the exact source key;
5. permit that exact source in the Experimental claim function;
6. permit it in active scheduled claims after 3/3 promotion;
7. extend `jobs_scope_evidence_check` with exact Oracle family/term pairs;
8. preserve every existing Workday and public ATS branch byte-for-byte where
   practical;
9. keep unsupported/failed proof cleanup safe and idempotent.

## Threats and Mitigations

| Threat | Severity | Mitigation |
|---|---|---|
| Caller substitutes Oracle host/site/facet | High | Frozen identity object; exact re-resolution before every request |
| Provider ignores a requested filter | High | Validate selected fields and exact facet ID/label/count in every page |
| Old job appears through date drift | High | Exact posting facet plus deterministic list/detail calendar-date backstop |
| Rolling window falsely closes an open job | High | `allowMissingClosure=false` for every JPMorgan observation |
| Broad new evidence terms admit sibling providers | High | Source-specific exact Oracle label/term mapping and SQL constraint |
| Partial fan-out activates or closes | High | All-or-nothing aggregate proof; incomplete observations are non-authoritative |
| Provider payload exhausts runtime | Medium | Existing byte/page/job/detail/deadline/concurrency caps |
| Internal-use API drifts | Medium | Exact schema checks, bounded reason codes, healthy last-known data retained |
| Deployment mutates an unapproved release | High | Hash-bound manifest, explicit approval, hosted parity, cleanup verifier |

## Planning Conclusion

No new architecture is required. The existing Oracle adapter, branded evidence,
Experimental observation, shared scheduler, and lifecycle system are the
correct seams. The key implementation changes are:

1. category slices → exact title-family slices;
2. add and prove the seven-day facet;
3. use exact `JobFunction` as per-job family evidence;
4. add two Oracle-only evidence terms;
5. disable missing-job closure for the rolling window;
6. restore production authority for JPMorgan only through migration `0045`.

The live contract is currently strong enough to plan and implement Phase 03.9.
