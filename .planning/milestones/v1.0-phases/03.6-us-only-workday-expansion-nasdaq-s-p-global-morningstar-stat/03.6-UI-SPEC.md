Phase 03.6 extends the shipped Dashboard rather than redesigning it. Retain its dense zinc table, light/dark color scheme, rounded 1px borders, underlined links, explicit focus outlines, resizable columns, full-width Dashboard shell, and horizontally scrollable result region. Do not add a component dependency, icon package, modal, page-number control, or third-party registry.

## Scope and Page Anatomy

### Dashboard order

Preserve the current Dashboard route and page width. Render:

1. `Dashboard` heading and a lifecycle-appropriate description.
2. One compact lifecycle control group containing `Show applied` beside `Show dismissed`.
3. The existing Companies and Score tiers controls; any persisted keyword/location eligibility remains active without adding duplicate Dashboard inputs.
4. Existing company or tier filter surface when open.
5. Existing ranking update/failure notice.
6. Lifecycle-qualified result count.
7. Existing resizable results table or its loading/error/empty state.
8. `Load more` / end-of-queue footer.
9. A fixed neutral Undo notice only while a Mark Applied action can be undone.

The four Workday additions do not create new Dashboard badges, source labels, cards, or company-specific controls. Their eligible jobs render exactly like every other job.

### Lifecycle views

- Active is represented by both lifecycle controls unpressed and is the default on every Dashboard mount.
- Pressing `Show applied` selects Applied and clears Dismissed. Pressing it again returns to Active.
- Pressing `Show dismissed` selects Dismissed and clears Applied. Pressing it again returns to Active.
- Wrap both buttons in a group labeled `Lifecycle view`. Keep filters visible and preserve their current session state when the lifecycle view changes.
- Use dynamic description copy and result-count nouns so users do not need color to know the current view.

## Interaction Contract

### Lifecycle query and ordering

1. Query exactly one lifecycle at a time. A row is Active only when both `applied_at` and `dismissed_at` are null; Applied only when `applied_at` is non-null; Dismissed only when `dismissed_at` is non-null.
2. Apply lifecycle, deterministic eligibility, stored keyword/title/location eligibility, company selection, and tier selection in the database before each 200-row limit. Applied or Dismissed rows must never consume Active slots.
3. Active retains the established deterministic/newest-first default and current optional Score sort. Applied is fixed newest `applied_at` first. Dismissed is fixed newest `dismissed_at` first.
4. In Applied and Dismissed, the Score header is a non-interactive header with `aria-sort="none"`; it must not override lifecycle ordering. Returning to Active restores the current session's prior Score-sort choice.
5. Switching lifecycle, applying a staged company selection, or changing score tiers starts a fresh filtered query and resets the cursor. Keep the control and focus stable while the result region refreshes.
6. Company options must describe the authorized result set for the current lifecycle before pagination, not merely the first loaded 200 rows. Newly available companies begin selected, preserving the existing contract.

### Mark Applied, dismiss, and restore

1. `Mark Applied` is the only action that sets Applied. The separate external `Apply ↗` link performs navigation only.
2. On Mark Applied, optimistically remove the row from Active, set the current timestamp locally, and announce the change. Do not show a confirmation dialog.
3. Display the Undo notice for 10 seconds. A new Mark Applied action replaces the prior notice only after its prior mutation has settled; never let one Undo target a different row than its message names.
4. `Undo` disables and reads `Undoing…` while pending. Success clears `applied_at`, refetches affected lifecycle queries, and announces `Moved back to Active.` The current lifecycle view does not change automatically.
5. Dismiss keeps the existing no-confirmation optimistic behavior. Restore/Undo Applied likewise require no confirmation.
6. Every mutation updates only the authenticated user's `user_jobs` lifecycle fields. No row action deletes or mutates the shared job.
7. A mutation failure restores the exact previous row/query snapshot and presents bounded retry guidance. Never leave a row visually moved when persistence failed.

### Automatic slot backfill

1. After an Active row is successfully Marked Applied or Dismissed, request the next qualifying row for the same Active filters and current ordering automatically.
2. If a next row exists, append it at its stable sorted position so a 200-row window returns to 200. Do not flash a full-table loading state and do not change scroll position.
3. If no next row exists, keep the reduced visible count, show `You're all caught up`, and disable `Load more`.
4. If backfill fails after the lifecycle mutation succeeded, keep the moved row out of Active, retain all current rows, and show the non-blocking footer error with `Retry`.

### Load more and cursor behavior

1. Initial and subsequent batches are exactly 200 qualifying rows, except the final partial batch.
2. `Load more` appends the next cursor batch to existing rows. It never replaces the table or scrolls the user automatically.
3. Disable the control immediately while loading and label it `Loading more…`. Ignore duplicate activation until the request settles.
4. Use an opaque, stable cursor matching the active lifecycle, filters, and ordering. Deduplicate by `user_jobs.id`; rows already rendered must neither repeat nor reorder when a batch appends.
5. When no cursor remains, render `You're all caught up` as visible status text and keep `Load more` disabled. Do not render a false empty row to fill the table.
6. A next-page failure leaves loaded rows intact and shows `Couldn’t load more jobs. Your current results are still shown.` with `Retry`.

| State | Visual and copy contract |
|-------|--------------------------|
| Initial lifecycle | Both lifecycle toggles unpressed; description `New postings ranked against your preferences, newest first.` |
| Applied selected | `Show applied` pressed; Dismissed unpressed; description `Jobs you’ve marked applied, newest applied first.` |
| Dismissed selected | `Show dismissed` pressed; Applied unpressed; description `Jobs you’ve dismissed, newest dismissed first.` |
| First batch loading | Existing bordered result region with `Loading…`; filters and lifecycle controls remain visible. |
| First batch error | Existing alert `Couldn’t load your matches. Check your connection and retry.` plus `Retry`. |
| Active, no data, no narrowed session filter | Existing `No matches yet` explanation; disabled Load more and visible `You're all caught up`. |
| Applied empty | Heading `No applied jobs yet`; body `Jobs you mark applied will appear here.` |
| Dismissed empty | Heading `No dismissed jobs`; body `Jobs you dismiss will appear here.` |
| Filters produce zero rows | Heading `No jobs match these filters`; body `Select more companies or score tiers, or use Select all in Companies.` |
| Mark Applied optimistic | Row disappears immediately; same-position next row receives focus when available; polite Undo notice appears. |
| Mark Applied failed | Row returns in stable order; alert `Couldn’t mark this job as applied. It remains in Active. Try again.` |
| Undo Applied failed | Row remains Applied; alert `Couldn’t undo Applied. Try again from Show applied.` |
| Backfill pending | Current table remains interactive; no full-table spinner. |
| Backfill failed | Lifecycle move remains committed; loaded rows remain; footer error `Couldn’t load the next job. Your current results are still shown.` plus `Retry`. |
| Load more pending | Existing rows remain; disabled `Loading more…`. |
| Load more failed | Existing rows remain; footer error and `Retry`. |
| Final partial/exhausted batch | Exact row count, visible `You're all caught up`, disabled `Load more`. |

Use a straight apostrophe in implementation strings if typography tooling does not preserve curly punctuation; wording must otherwise remain unchanged.

## Accessibility Contract

- Wrap the lifecycle buttons in a semantic group labeled `Lifecycle view`. Each button has a visible focus outline and accurate `aria-pressed`; both false is documented by the visible Active description/count.
- Every row action includes the job title in its accessible name: `Mark {title} applied`, `Dismiss {title}`, `Undo applied for {title}`, or `Restore {title}`.
- Mark Applied must not leave keyboard focus on a removed node. After optimistic removal, focus the corresponding action in the next row, otherwise the prior row, otherwise the table region.
- The Undo notice uses `role="status"` and `aria-live="polite"`; its button is keyboard operable and never steals focus. Mutation failures use `role="alert"`.
- Announce lifecycle changes and appended counts without rereading the table: `Marked {title} as applied.`, `Moved back to Active.`, and `{N} more jobs loaded. {total} {lifecycle} jobs shown.`
- `Load more` and `Retry` expose native pending/disabled state and visible focus. End-of-queue text is a polite status, not a disabled-button tooltip.
- Dynamic Posted/Applied/Dismissed timestamps use semantic `time` with exact ISO `dateTime` and full localized tooltip text.
- Preserve the existing scroll-region label, `tabIndex=0`, table header scopes, resize-separator semantics, score `aria-sort` in Active, link names, dark-mode contrast, and non-color tier labels.

## Responsive Contract

- Lifecycle and filter controls wrap with 8px gaps; `Show applied` stays immediately before `Show dismissed`.
- Retain all Dashboard columns and horizontal scrolling below 768px. Do not convert rows into cards or hide Score, Apply, or Action.
- Active Action buttons wrap inside the widened fixed column when necessary and meet 44px coarse-pointer height.
- Place the Undo notice bottom-center, no wider than `min(448px, calc(100vw - 32px))`; message and button wrap without covering the full viewport width.
- Keep Load more centered below the scroll region with at least 16px separation. Its label never truncates.
