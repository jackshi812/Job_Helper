# Phase 03.5: Generic Workday Connector & Fidelity - Research

**Researched:** 2026-07-23
**Domain:** Codebase refactor — parameterize an in-repo single-tenant ATS connector (Supabase Edge / Deno / TypeScript) and admit a second tenant via forward-only Postgres migration
**Confidence:** HIGH (all findings verified by reading the actual source; endpoint facts live-verified in CONTEXT.md)

## Summary

This is a **codebase-pattern refactor**, not an external-API discovery task. The Workday adapter, detection, connector registry, and identity-guardrail migrations already exist and work for exactly one tenant (Capital One). The Fidelity CXS endpoints are already live-verified (CONTEXT.md § live-verified). The job is to lift five hardcoded seams to parameters while preserving the exact-approved production behavior (commit `7642fde8`) and the byte-identical Capital One identity contract that ~6 files and several migration parity-checks assert against.

The five seams, all confirmed by reading source: (1) module-level origin/tenant/site constants and hardcoded `companyName: 'Capital One'` in `workday.ts`; (2) a single `rawHost === capitalone.wd12.myworkdayjobs.com` branch plus a literal-typed `DetectResult` in `detect.ts`; (3) a source-key/dispatch layer in `connectors.ts` that pins the exact Capital One tuple in three places; (4) two deployed migrations (`0016`, `0028`) plus `0029` that hard-constrain the DB to `workday:wd12:capitalone:Capital_One`; (5) an inclusion-only facet mechanism whose Capital One implementation (`pollCapitalOneRecent`) already demonstrates the fail-closed pattern Fidelity should reuse.

**Primary recommendation:** Introduce a small `WorkdayIdentity` value object (origin, tenant, site, region, host-form, source_key, excluded jobFamilyGroups, companyName) — mirroring the existing `provider-identities.ts` Paylocity pattern — thread it through `pollWorkday`/`pollCapitalOneRecent`/`safeDetailPath`/`mapWorkdayDetail`, teach `detect.ts` the second URL shape, and ship migration **0035** that relaxes the Workday identity constraint from a single hardcoded tuple to an allowlist while keeping Capital One's frozen key. Implement Fidelity's category scoping as **inclusion facets for all kept jobFamilyGroups (Option b), discovered live and count-verified** — because Workday list rows do not carry family, post-fetch exclusion (Option a) is impossible without fetching all 706 details, which the egress/wall-clock budget forbids.

### Pattern 1: Identity value object (mirror `provider-identities.ts`)
**What:** Paylocity already solved "one ATS, pinned identity, shared constant across detect/connectors/migration/tests" via `provider-identities.ts` (`resolvePaylocityIdentity`, frozen `PAYLOCITY_IDENTITIES` map, exported `PAYLOCITY_SOURCE_KEY`).
**When to use:** Generalize the same shape to Workday: a `resolveWorkdayIdentity`/registry that yields `{ origin, cxsRoot, publicBoard, tenant, site, region, hostForm, sourceKey, companyName, excludedJobFamilyGroups }`.
**Why:** Keeps the Capital One byte-identical key (`CAPITAL_ONE_WORKDAY_SOURCE_KEY = 'workday:wd12:capitalone:Capital_One'`) as one frozen entry while admitting Fidelity as another. `connectors.ts` already imports and re-exports that constant from `workday.ts` — extend, don't replace.
```typescript
// Source: existing supabase/functions/_shared/provider-identities.ts (analog)
export function resolvePaylocityIdentity(boardUuid: string): PaylocityIdentity | null {
  return boardUuid === PAYLOCITY_BOARD_UUID ? paylocityIdentity : null
}
// Generalize: resolveWorkdayIdentity(tenant, region, site, hostForm) → WorkdayIdentity | null
```

### Pattern 2: Parameterize the three module-level origin seams in `workday.ts`
Currently module constants (lines 51-57):
```typescript
const TENANT = 'capitalone'; const REGION = 'wd12'; const SITE = 'Capital_One'
const PUBLIC_ORIGIN = `https://${TENANT}.${REGION}.myworkdayjobs.com`
const PUBLIC_BOARD  = `${PUBLIC_ORIGIN}/${SITE}`
const CXS_ROOT      = `${PUBLIC_ORIGIN}/wday/cxs/${TENANT}/${SITE}`
const LIST_URL      = `${CXS_ROOT}/jobs`
```
These are consumed by `safeDetailPath` (L183-196 — uses `PUBLIC_ORIGIN`, `CXS_ROOT`, `PUBLIC_BOARD`), `pollWorkday` (L349 `LIST_URL`), `pollCapitalOneRecent` (L538 `LIST_URL`), `verifyWorkdayListing` (L697 `LIST_URL`). Origin construction differs per form:
- **Form A (Capital One):** `origin = https://{tenant}.{region}.myworkdayjobs.com`
- **Form B (Fidelity):** `origin = https://{region}.myworkdaysite.com`
- **Both:** `cxsRoot = {origin}/wday/cxs/{tenant}/{site}`, `publicBoard = {origin}/{site}` (Form A) — note Form B public board URL includes `/{locale}/recruiting/{tenant}/{site}`, but the **absoluteUrl written into jobs** only needs to be a valid public link; confirm the shape the planner wants for `mapWorkdayDetail`'s `absoluteUrl`.
**Refactor:** turn `safeDetailPath(value)` into `safeDetailPath(value, origin, cxsRoot, publicBoard)` (or a closure bound to the identity). The SSRF invariants (origin equality, no `..`, no `?`/`#`, no `%2f`/`%5c`, no creds/port) are origin-agnostic and stay intact.

### Pattern 3: `companyName` hardcode
`mapWorkdayDetail` (L268), `mapRecentListPosting` (L475), `mapRecentDetail` (L500) all set `companyName: 'Capital One'`. `poll-tick/index.ts` L233 uses `normalized.companyName ?? company.name`. **Two clean options:** (a) thread `identity.companyName` into the mappers, or (b) set `companyName: null` so `poll-tick`'s `?? company.name` supplies the DB-stored name. Option (b) is smaller and defers naming to the row the user added. Recommend (b) unless a canonical display name is needed at map time.

### Anti-Patterns to Avoid
- **Changing Capital One's source key.** `workday-connector.integration.test.ts` asserts exact byte equality and exact fetch counts; `0013`/`0016`/`0028`/`0029` embed the literal. Frozen forever.
- **Whole-board detail fan-out for Fidelity.** 706 detail GETs/poll blows egress + the ~150 s wall-clock cap. Use the selective recent-window model.
- **Hardcoding Fidelity facet IDs.** Facet IDs differ per tenant and can change (CONTEXT § live-verified). Discover from the live `facets` array and verify counts (existing `category_filter_unverified` fail-closed pattern).
- **Suffix/wildcard host matching.** `detect.ts` comment (L21-23) is explicit: exact hosts only, the Set is the SSRF gate. Form B must match `{region}.myworkdaysite.com` with a validated `{region}` allowlist, never `endsWith('myworkdaysite.com')` without anchoring.

## Detailed Findings by Investigation Area

### 1. Adapter parameterization (`_shared/adapters/workday.ts`)
- **Hardcoded constants:** `TENANT`/`REGION`/`SITE`/`PUBLIC_ORIGIN`/`PUBLIC_BOARD`/`CXS_ROOT`/`LIST_URL` (L51-57); `CAPITAL_ONE_CATEGORY_FACETS` (L69-72, the inclusion IDs for Analysis/Finance); `companyName: 'Capital One'` (L268/L475/L500); `CAPITAL_ONE_WORKDAY_SOURCE_KEY` export (L49).
- **Already generic (reusable as-is):** the whole protocol layer — `requestJson` (byte caps, `redirect:'error'`, 15 s timeout, content-type/JSON guards), pagination/count-reconciliation in `pollWorkday`, `safeDetailPath` SSRF logic (just needs origin params), `parseListPosting`/`parseDetail` schema validation, `incomplete()` degraded-observation builder, US/entry-level detail predicates.
- **Minimal refactor:** accept a `WorkdayIdentity` (origin, cxsRoot, publicBoard, tenant, site, region, sourceKey, companyName, excludedFamilies) as the first arg of `pollWorkday`, `pollCapitalOneRecent` (→ generalize to `pollWorkdayRecent`), `verifyWorkdayListing`, and pass origin/cxsRoot/publicBoard into `safeDetailPath` and the mappers. `LIST_URL` becomes `${identity.cxsRoot}/jobs`.
- **Two URL shapes → one CXS path:** confirmed identical `/wday/cxs/{tenant}/{site}`. Only `origin` differs. `[VERIFIED: source read + CONTEXT live-probe]`

### 2. URL detection + parsing (`_shared/detect.ts`, `verify-board/index.ts`)
- **Current detection:** `detectAts(href)` parses `new URL`, rejects non-https / creds / port / hash, then matches `rawHost` against a fixed `supportedHosts` map. Capital One branch (L73-83): `rawHost === 'capitalone.wd12.myworkdayjobs.com'` + `singlePathSegment === 'Capital_One'` + no search → returns the frozen literal object `{ats:'workday', slug:'capitalone', region:'wd12', site:'Capital_One'}`.
- **`DetectResult` type is a literal union** (L3-15): the workday variant is typed `slug:'capitalone', region:'wd12', site:'Capital_One'`. **This must widen** to `slug:string, region:string, site:string, hostForm:'jobs'|'site'` (validated by a per-tenant allowlist, not free strings, to preserve the SSRF gate).
- **New Form B branch must:** match host `{region}.myworkdaysite.com` (region validated, e.g. `/^wd\d{1,3}$/` + allowlist), parse path `/{locale}/recruiting/{tenant}/{site}` (exactly 4 segments, `recruiting` literal at index 1, strict-slug tenant/site), reject search/hash, and return `{ats:'workday', slug:<tenant>, region:<region>, site:<site>, hostForm:'site'}`.
- **Exact return shape a new branch must produce:** whatever `connectors.ts::verification()` reads — it consumes `detected.slug` (→ boardToken), `detected.region`, and `detected.site` (workday-only, → siteToken). So the Form B branch must populate all three.
- **`buildEndpoint`** (L161-187) has a hardcoded workday line (L183-184) returning the Capital One CXS `/jobs` URL — must become identity-derived.
- **`UNSUPPORTED_URL_MESSAGE`** (L17-18) names "the allowlisted Capital One Workday board" — update copy to reflect generalized Workday support.
- **verify-board is the SSRF boundary (D-04):** it authenticates (Bearer + `role==='authenticated'`), calls `detectAts`, then `verifyConnector` with a `countedFetch`. Workday is in `stagedActivationProviders` (L79-84) → inserts `activation_state='experimental'` and records an observation via `record_connector_observation`. `sourceKeyForDetection` (L111-117) hardcodes `CAPITAL_ONE_WORKDAY_SOURCE_KEY` for workday — must derive from identity. `[VERIFIED: source read]`

### 3. Connector registry (`_shared/connectors.ts`)
- **Source-key format:** `deterministicSourceKey` (L75-83) returns `CAPITAL_ONE_WORKDAY_SOURCE_KEY` for workday, else `${ats}:${region ?? 'global'}:${slug}`. The Capital One key `workday:wd12:capitalone:Capital_One` is effectively `workday:{region}:{tenant}:{site}` (4 parts — workday appends `site`).
- **Generalized key proposal:** `workday:{region}:{tenant}:{site}` for all Workday tenants → Fidelity = `workday:wd1:fmr:FidelityCareers`. Capital One's existing key already fits this scheme, so it stays byte-identical. **Open design point (see Assumptions A1):** `{region}` alone (wd12 vs wd1) does NOT distinguish Form A (`myworkdayjobs`) from Form B (`myworkdaysite`) — the origin cannot be reconstructed from region+tenant+site unambiguously. Resolve by persisting the host-form/origin (recommended: derive it at detect-time and store either in a new nullable column or re-derive via the identity registry keyed on the full tuple). Do NOT invent a `wd1`-implies-`myworkdaysite` rule — that is fragile.
- **Three pinned checks to relax:** `verifyWorkday` (L177-189) rejects anything but the Capital One tuple; `pollConnector` (L254-261) re-checks the exact tuple + source_key; `canonicalCareersUrl`/`deterministicSourceKey`/`verification` all special-case workday. All must consult the identity registry/allowlist instead of literals.
- **`ProviderConnector` interface** and `providerRegistry` (L202-235) dispatch by `ats_type`; the workday entry's `poll` currently calls `pollCapitalOneRecent(fetch, {knownIds})` ignoring the company — must pass the resolved identity from `company` fields. `region` type on `PollConnectorCompany`/`ConnectorVerification` is `'eu'|'wd12'|null` — **must widen** to admit `wd1`. `[VERIFIED: source read]`

### 4. Identity guardrail migration
- **The exact restricting constraint** (`companies_workday_identity_check`, introduced 0016 L16-25, re-added 0028 L18-28): `ats_type <> 'workday' OR (board_token='capitalone' AND region='wd12' AND site_token='Capital_One' AND source_key='workday:wd12:capitalone:Capital_One' AND activation_state IN ('experimental','active'))`.
- **The region constraint also blocks Fidelity** (`companies_region_check`, 0016 L6-11): `region is null OR (lever eu) OR (workday wd12)`. **Fidelity is `wd1`** → this MUST be relaxed (e.g. `(ats_type='workday' AND region ~ '^wd\d+$')` or an explicit allowlist).
- **Activation mechanism (D-08):** two paths converge — (a) `record_connector_observation` RPC (0029 L40-233) writes an immutable `connector_observations` ledger row per 30-min `date_bin` window (`v_window_interval = 30 minutes` for workday, L136-139), enforces replay/same-window/3-row-cap, and for **stable** providers flips to active at progress=3 (L212-216, `ats_type in ('smartrecruiters','recruitee','paylocity')` — **workday is deliberately excluded here**); (b) `promote_capital_one_after_observation` trigger (0028 L35-78) is the workday-specific promoter — it flips Capital One to active after its 3rd clean ledger row. For Fidelity to auto-promote, migration 0035 must either add workday tenants to the RPC's stable-promotion set (cleanest, uniform) or generalize the promotion trigger beyond the hardcoded Capital One tuple.
- **`claim_due_companies`** (latest def in 0029 L244-277) admits workday only via the exact Capital One tuple disjunct — must be widened to admit the allowlist (or a general `ats_type='workday' AND <tenant is admitted>` predicate). Note `record_connector_observation` gates provider via `v_provider not in ('smartrecruiters','recruitee','workday','paylocity')` (0029 L120) — workday already allowed there.
- **`connector_observations_provider_check`** (0029 L28-32) already includes `'workday'` — no change.
- **`source_coverage_catalog`:** Fidelity **already exists** as a row (`0013` L176-184) with `disposition='unsupported_with_reason'`, `careers_url='https://jobs.fidelity.com/en/jobs/'`, `source_key=null`, reason "Automated access is blocked". `company_name` is UNIQUE and there is a `truthful_disposition_check` (0013 L35-46): `experimental` requires `source_key NOT NULL` and `unsupported_reason NULL`. Migration 0035 must **UPDATE** (not insert) that row to `disposition='experimental'`, set `source_key='workday:wd1:fmr:FidelityCareers'`, `unsupported_reason=NULL`, `provider='Workday'`, and a valid `careers_url` (must match regex `^https://[^/[:space:]@]+(?:/[^[:space:]]*)?$`). Existing migration DO-block parity checks (0028 L111-120, 0029 L390-398) assert the Capital One catalog row — keep those intact.
- **Migration numbering:** latest deployed is **0034** (`0034_repair_deterministic_ranking_retry.sql`). New migration is **`0035_generic_workday_fidelity.sql`**. Forward-only — never edit 0016/0028/0029. `[VERIFIED: source read + ls migrations/]`

### 5. Facet exclusion mechanism (D-06) — RECOMMENDATION
**Decision-driving fact:** Workday **list rows carry no jobFamilyGroup** — `WorkdayListPosting` (types L23-28) is only `{title, externalPath, locationsText, postedOn}`. Family lives only in (a) the search-side `facets` array, and (b) individual job details. Therefore:
- **Option (a) fetch-whole-board-then-drop-by-family is not viable cheaply** — you cannot know a posting's family without fetching its detail. Dropping post-fetch means 706 detail GETs/poll → violates egress (5 GB/mo) and wall-clock (~150 s) budgets.
- **Option (b) apply-all-other-family facets as inclusion — RECOMMENDED.** Send `appliedFacets: { jobFamilyGroup: [<IDs of all KEPT families>] }`. Grounding: `pollCapitalOneRecent` (L538-596) already does exactly this for Analysis+Finance and **proves the filter applied** by reading the returned `facets` array, matching each expected `{descriptor,id}`, and asserting `sum(counts) === providerTotal`, else fail-closed with `category_filter_unverified` (L590-595). Reuse this verification verbatim.
- **Evolution for exclusion-by-name:** Capital One hardcodes the *kept* facet IDs. Fidelity's stable config is the *excluded* set of descriptors `{Sales, Customer Service, Sales Support}` (CONTEXT: live counts 108/83/5). Because IDs differ per tenant and can drift, **discover IDs at runtime**: first read the `facets` array (from an initial probe or the first filtered page), take all `jobFamilyGroup` values whose `descriptor ∉ excludedSet`, use their `id`s as the inclusion list, and verify `sum(kept counts) + sum(excluded counts) === total`. New families Fidelity adds later are **included by default** (safer than option-a's silent-exclude). Kept families per CONTEXT: IT (269), Relationship Management (30), Investment Operations (28), Data Analytics (18), Finance (5), etc.
- **Combine with selective recent-window import** (the `pollCapitalOneRecent` structure: recent `postedOn` window + `knownIds` shortcut + bounded detail fan-out) so steady-state egress stays tiny even though the kept board is ~510 jobs. `[VERIFIED: source read]`

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Origin/CXS URL safety | New SSRF checks | Parameterized `safeDetailPath` + `redirect:'error'` + origin-equality already in `workday.ts` | Battle-tested against traversal/encoded/protocol-relative (tests L281-299) |

## Common Pitfalls

### Pitfall 1: Breaking the byte-identical Capital One contract
**What goes wrong:** Refactor changes Capital One's source key, region handling, or fetch/observation counts; ~6 files + migration parity DO-blocks + `workday-connector.integration.test.ts` exact-match assertions fail.
**How to avoid:** Treat `workday:wd12:capitalone:Capital_One`, region `wd12`, site `Capital_One`, tenant `capitalone` as frozen. Add Fidelity as a *second* registry entry; never mutate the first. Run `npm run test` and confirm all Capital One assertions still green.
**Warning signs:** Any diff to the literal in `provider-identities`-style constant, `0013`/`0016`/`0028`/`0029`, or Capital One test expectations.

### Pitfall 2: Region type/constraint too narrow for `wd1`
**What goes wrong:** TS `region: 'eu' | 'wd12' | null` (in `connectors.ts` L30/L38, `poll-tick` L18, `watchlist.ts` L18) and DB `companies_region_check` reject `wd1`; insert/verify fails silently as a generic error.
**How to avoid:** Widen the TS union to `string | null` (or `'eu' | \`wd${number}\` | null`) everywhere it appears, and relax `companies_region_check` in 0035 to admit workday `wd\d+`.
**Warning signs:** verify-board returns generic verification error on the Fidelity URL despite a live 200 from CXS.

### Pitfall 3: Origin ambiguity from region alone
**What goes wrong:** Adapter reconstructs `myworkdayjobs` origin for a `myworkdaysite` tenant (or vice-versa) because only region/tenant/site were persisted; CXS 404s.
**How to avoid:** Persist/resolve host-form explicitly (identity registry keyed on the full tuple, or a stored origin/host-form field). See Assumptions A1.
**Warning signs:** Poll `provider_http_404` / `network_error` for a tenant that verified fine.

### Pitfall 4: Egress/wall-clock blowout on whole-board detail fetch
**What goes wrong:** Fidelity poll fetches 706 (or ~510 kept) job details each tick → 5 GB/mo egress and ~150 s cap exceeded; project risk.
**How to avoid:** Use the `pollCapitalOneRecent` selective model (recent window + `knownIds` shortcut + bounded `maxDetails`). Inclusion facets keep the working set small.
**Warning signs:** poll-tick timeouts; egress climbing in Supabase dashboard.

### Pitfall 5: Catalog UPDATE vs INSERT for Fidelity
**What goes wrong:** 0035 tries to INSERT Fidelity into `source_coverage_catalog` → unique `company_name` violation; or sets `experimental` without a `source_key` → `truthful_disposition_check` violation.
**How to avoid:** UPDATE the existing row, set source_key, null the reason, and satisfy the `careers_url` regex.
**Warning signs:** Migration 0035 aborts with a check-constraint or unique-violation error.
