### Phase Boundary

Remove every scheduled or background AI job-scoring path and replace the current AI-produced score, tiers, reasons, and gaps with an owner-configurable deterministic rubric. Preserve job ingestion, preferences, watchlist behavior, company controls, Dashboard structure, detail/apply/dismiss flows, authentication, RLS, resume management, and Phase 4 tailoring. AI resume extraction and future tailoring are not removed by this phase; only automatic job scoring is removed.

### Deterministic ranking formula

- **D-01:** The default score is additive and totals 100 points.
- **D-02:** A strict target-title match earns 30 points. Strict means a normalized, case-insensitive target-title phrase appears in the job title.
- **D-03:** A weak target-title match earns 20 points. Weak means every significant target-title concept appears in the job title regardless of order, using the existing approved synonym and conservative inflection behavior.
- **D-04:** A preferred-location keyword match earns 10 points. The existing Locations preference becomes a soft keyword list for ranking; it is not a preferred-location hard filter.
- **D-05:** A job posted within the preceding 24 hours earns 10 points.
- **D-06:** A job from a company/source on the user's watchlist earns 10 points.
- **D-07:** An explicitly stated minimum required experience below the user's configured maximum earns 20 points. A requirement equal to or above the maximum earns zero points but does not hide the job. Missing, ambiguous, preferred, or non-required experience language earns zero points.
- **D-08:** Description include-keyword matches earn 3 points for one match, 5 for two, 10 for three, 15 for four, and 20 for five or more. Include keywords remain positive signals and never exclude a job.
- **D-09:** Preferences shows the complete scoring rubric. Every point value is editable. Validation requires category maximums to total 100; keyword steps must be nondecreasing and cannot exceed the keyword category maximum.

### Hard-filter boundaries

- **D-10:** A job with neither a strict nor weak target-title match never appears on the Dashboard.
- **D-11:** Jobs explicitly located outside the United States never appear. Blank locations and `Remote` without a stated country remain eligible; explicitly US and US-remote jobs remain eligible.
- **D-12:** Existing title-exclusion keywords remain hard title-only filters. Existing general Exclude keywords remain hard literal title-and-description filters.
- **D-13:** Preferred-location keywords and the maximum-experience preference are scoring signals only, not hard filters.

### Tiers and AI-score retirement

- **D-14:** Default tiers remain Strong 75–100, Good 50–74, and Weak 0–49.
- **D-15:** Preferences allows users to edit the Good and Strong thresholds, validating `0 < Good < Strong <= 100`.
- **D-16:** Before the Dashboard switches to deterministic ranking, every current job must be recalculated with the deterministic rubric. Users must never see a mixture of AI and deterministic scores.
- **D-17:** Historical AI scores, reasons, and keyword-gap data may remain only as non-displayed migration evidence. The active UI and ranking path must not read or present them.
- **D-18:** The existing match-reason/gap presentation is replaced by a deterministic category breakdown showing points earned, points possible, and the evidence that earned each category.

### Recalculation and presentation

- **D-19:** Saving preferences or rubric changes starts deterministic recalculation while the previous complete Dashboard remains visible with an `Updating` notice. The new result set replaces the prior set atomically only after the whole snapshot is complete.
- **D-20:** Newly ingested jobs appear only after hard filtering and deterministic scoring complete; there is no temporary Unranked or synthetic Weak state.
- **D-21:** The Dashboard keeps its current score/tier surface and existing newest-first default, explicit score sorting, company controls, tier controls, table, detail navigation, and other unrelated behavior.
- **D-22:** The scoring explanation appears on job detail as a rubric table. The removed Dashboard Match reason column does not return.
- **D-23:** If recalculation fails, keep the previous complete result set, show a bounded error with Retry, and never publish a partial or mixed rubric version.

### Automatic AI removal and deferred manual AI

- **D-24:** No cron, scheduled worker, preference save, resume event, ingestion event, retry, or background process may make an AI job-scoring request or reserve paid job-scoring capacity.
- **D-25:** Automatic AI job scoring is deferred rather than permanently forbidden. After Phase 4 tailoring is complete, a user may explicitly request one AI score from an opened job detail and may explicitly request a second score after tailoring a resume. Each call must be a visible, separate user action; no background scoring returns.

## Summary

The current production worker cannot be modified incrementally into the requested behavior without adding a publication boundary. It claims and mutates each `user_jobs` row independently, and the browser decides visibility from mutable AI status/freshness fields. Preference saves mark every open row stale and evict the feed cache, which is exactly why prior saves can temporarily empty the Dashboard. [VERIFIED: `supabase/functions/score-tick/index.ts`, migrations 0025/0027, `web/src/lib/preferences.ts`, `web/src/lib/feed.ts`]

Use a staged deterministic run and retain the existing `user_jobs` row as the stable feed identity/state record. Compute every result into a run-item staging table, then promote the complete run into new deterministic columns on `user_jobs` in one PostgreSQL transaction. PostgreSQL MVCC makes readers see either all old active values or all newly committed values, never a row-by-row mixture. Keep the AI columns physically present as migration evidence, but remove them from every active browser query and deterministic worker write. New jobs start with no active deterministic result and therefore remain hidden until an individual deterministic result is committed. [VERIFIED: current one-row-per-user/job schema in migration 0019; recommended architecture derived from D-16/D-19/D-20/D-23]

Containment is time-sensitive. Production currently has an every-minute `score-tick` cron, Edge function v9 imports the OpenAI wrapper, reserves paid capacity, and writes `ai_usage` with `purpose='score'`. The first executable plan should replace that deployed function with a schema-compatible no-AI/no-reservation implementation before the next UTC budget reset. The same endpoint and cron name may remain to minimize rollout risk; the proof requirement is that its source and runtime contain no job-scoring AI path. `extract-resume` may retain OpenAI because the phase explicitly preserves AI resume extraction, but its post-extraction action must only request free deterministic routing/ranking work. [VERIFIED: migration 0019, migration 0027, `score-tick/index.ts`, `extract-resume/index.ts`, Phase 03.3 rollout evidence]

**Primary recommendation:** Plan four slices in this order: (1) production-safe no-AI containment plus pure evaluator, (2) staged-run schema/worker and atomic promotion, (3) Preferences/feed/detail migration, and (4) deterministic backfill followed by the exact web switch and signed-in UAT.

## Recommended Data Model

Use three layers:

1. **Desired configuration** on `preferences`: restore `max_required_experience` to the browser projection, add one versioned `ranking_rubric` JSON object, Good/Strong thresholds, and a monotonically increasing desired ranking revision.
2. **Build state** in `deterministic_ranking_runs` and `deterministic_ranking_items`: capture the exact preference/rubric snapshot, expected universe, item claim/retry state, score, tier, breakdown, eligibility, filter reason, and best-fit routing.
3. **Active projection** in new columns on `user_jobs`: deterministic revision, eligibility, score, tier, breakdown, hard-filter code/detail, ranked timestamp, and independently recomputed best-fit/runner-up IDs. `seen_at` and `dismissed_at` stay unchanged.

Do not overwrite or repurpose legacy `score`, `tier`, `reasons`, `gaps`, `covered`, `scoring_input_hash`, or paid-defer fields. Leaving them physically intact makes rollback/forensics possible, while query removal satisfies D-17. [VERIFIED: those columns currently carry AI-era semantics in migration 0019 and worker writes]

### Rubric JSON contract

The stored rubric should have explicit integer keys for:

- strict title, weak title;
- preferred location;
- recency;
- watchlist;
- experience;
- include-keyword steps for 1, 2, 3, 4, and 5+ matches.

Server validation must enforce:

- every value is an integer in `0..100`;
- `weak_title <= strict_title`;
- `strict_title + location + recency + watchlist + experience + include_5_plus = 100`;
- keyword steps are nondecreasing and every step is `<= include_5_plus`;
- `0 < good_threshold < strong_threshold <= 100`;
- unknown/missing rubric keys are rejected.

The weak-title value and intermediate keyword steps do not participate separately in the 100-point maximum: strict title is the title-category maximum and the 5+ keyword value is the include-category maximum. This distinction is necessary to make the locked defaults total 100. [VERIFIED: arithmetic of D-01–D-09]

## Architecture Patterns

### System Architecture Diagram

```text
Preferences save
  -> authenticated save-and-start-run RPC
       -> validate desired preferences/rubric
       -> capture immutable run input
       -> seed one staging item per current open job
       -> ranking_state = updating
            |
            v
scheduled deterministic worker (cron secret)
  -> SKIP LOCKED item claim
  -> hard filters
       excluded/outside-US/no-title-match -> staged ineligible result
       eligible -> additive score + tier + evidence + local resume routing
  -> staged completed result
            |
            v
finalize RPC
  -> lock run + per-user state
  -> reject if incomplete or if current universe has missing items
  -> bulk-copy every staged result into user_jobs deterministic columns
  -> switch active revision and clear updating IN THE SAME TRANSACTION
            |
            v
Dashboard
  -> continues reading prior user_jobs deterministic columns while updating
  -> after commit, refetches one complete new projection
  -> detail reads deterministic breakdown only

New ingestion
  -> open shared job
  -> worker creates user_job + deterministic item
  -> row remains invisible
  -> one complete active result is committed
  -> row becomes visible if eligible
```

### Pattern 1: Stage, Validate, Promote

Compute into staging and make the active projection the final transaction, not the work queue. A finalizer must:

1. lock the user's ranking state and run;
2. confirm run ownership, captured revision, and `building` status;
3. confirm every expected item is terminal and no currently active/open row is missing;
4. fail closed by adding missing work instead of publishing;
5. bulk update all active deterministic columns;
6. update the active revision and run status;
7. commit once.

If any statement fails, PostgreSQL rolls the whole promotion back and the old Dashboard remains intact. [VERIFIED: existing project already uses revision/CAS and SKIP LOCKED patterns in migrations 0025/0027; recommendation extends them to a whole-run boundary]

### Pattern 2: Single authenticated save RPC

Do not keep the browser's current two-step `upsert` then `mark_recent_jobs_for_refilter` sequence. Use one security-definer RPC scoped to `auth.uid()` that validates all values, writes preferences, increments the desired revision, captures the run, and sets Updating atomically. This avoids saved preferences without a corresponding run and avoids feed eviction before publication. [VERIFIED: current two-step behavior in `preferences.ts`; recommended to satisfy D-19/D-23]

### Pattern 3: Pure evaluator with one source of truth

Refactor filter/title helpers so one pure function returns both eligibility and evidence:

```ts
interface DeterministicResult {
  eligible: boolean
  score: number | null
  tier: 'Strong' | 'Good' | 'Weak' | null
  filterReason: 'excluded_title_keyword' | 'excluded_keyword'
    | 'outside_us' | 'title_non_overlap' | null
  breakdown: Array<{
    key: 'title' | 'location' | 'recency' | 'watchlist' | 'experience' | 'keywords'
    earned: number
    possible: number
    evidence: string[]
  }>
}
```

The hard filter and point award must consume the same title-match result, preventing a row from passing on weak title logic but receiving no title evidence. React must never recompute scores or tiers. [VERIFIED: current duplicate responsibility between `cheapFilter`, `tierFor`, and browser `tierPresentation` creates multiple score/tier authorities]

### Pattern 4: Time-aware recency maintenance

The recency rule is relative to the current time. Store the evaluation timestamp and schedule free deterministic maintenance for active rows when `posted_at + 24 hours` passes. Re-evaluate with the active captured rubric, not a desired rubric whose full run is still building. Missing/invalid `posted_at` earns zero; the display may continue using `first_seen_at` as its existing visual fallback, but scoring should not. Without expiry maintenance, an old job would incorrectly retain the 24-hour bonus indefinitely. [VERIFIED: D-05 and existing `relativePostedTime` fallback behavior]

### Pattern 5: Preserve Best fit without making it a score input

To honor D-21, keep the Best fit column by running existing local `routeResume` after hard filtering. Store its result in the deterministic active projection, but exclude resume text, extracted keywords, route IDs, and resume revision from the score formula. A resume upload/extraction may enqueue a free route refresh; it must not reserve capacity or call AI for job scoring. [VERIFIED: `routeResume` is local; current Best fit table column exists; rubric D-01–D-08 has no resume category]

## Deterministic Rule Implementation Notes

### Title

- Add an exported `evaluateTitleMatch` helper.
- Strict: normalized target-title tokens occur contiguously in normalized job-title tokens; choose strict if any configured target matches.
- Weak: only when strict did not match, require every significant target concept using current bidirectional synonyms and one-step conservative inflections.
- No configured target title produces no match and therefore no Dashboard result, consistent with D-10 and current UI copy.
- Store the matched configured title and match kind as evidence.

[VERIFIED: reusable token, stopword, synonym, and inflection logic in `filters.ts`]

### Exclusions

Keep title exclusions first and general exclusions second. Title exclusions keep their bounded whole-token/phrase and PhD normalization behavior. General exclusions remain literal across title plus description. Include keywords must change to description-only for score counting, because D-08 says job description; title-only occurrences must not earn points. [VERIFIED: current include matching uses title plus description and therefore needs a deliberate contract change]

### United States eligibility

Use a pure, fixture-backed classifier with three outcomes: `us`, `outside_us`, `unknown`. Only `outside_us` is rejected.

- blank and countryless `Remote` -> `unknown` and eligible;
- explicit United States/USA/US, US state names, and unambiguous state abbreviations -> `us`;
- explicit foreign country names/aliases and unambiguous province/region markers -> `outside_us`;
- ambiguous city-only or unrecognized strings -> `unknown` and eligible.

Do not treat “does not look American” as outside-US, and do not use unconstrained two-letter substring matching. Keep normalization data in a reviewed constant with representative provider fixtures. This is conservative but obeys the locked rule that only explicitly outside-US jobs disappear.

### Experience

Restore the final Phase 03.2 `experienceMinimumRequired` parser from repository history rather than rebuilding the grammar. It already handles ranges, plus notation, mandatory qualification context, optional/preferred language, and fail-open ambiguity after several fixes. Change its consumer from a hard filter to a score category:

- parsed minimum `< configured maximum` -> configured experience points;
- parsed minimum `>= configured maximum` -> zero;
- missing configured maximum or missing/ambiguous/preferred-only requirement -> zero;
- keep the job visible in every case.

[VERIFIED: repository history immediately before commit `2ce9608`, including fixes `6a7f586` through `c970aa3`]

### Location keyword, watchlist, and recency

- Preferred location: literal normalized phrase match against `jobs.location` only; never hard-filter.
- Watchlist: `jobs.company_id IS NOT NULL` is the truthful direct-watchlist signal. `companies` is intentionally shared between the two users, so “user's watchlist” maps to the existing shared watchlist; do not add per-user ownership in this phase.
- Direct polling can replace an Adzuna duplicate with the direct provider snapshot and attach `company_id`, so the same signal remains correct after dedup.
- Recency: use `posted_at`, the run evaluation time, and the expiry maintenance described above.

## Anti-Patterns to Avoid

- **Deploying schema before containing v9:** a scheduled v9 invocation can still reserve new paid capacity during rollout.
- **Leaving a dormant AI branch:** a feature flag, retry branch, or old RPC call still violates D-24 even if the default path is deterministic.
- **Reusing `score`/`tier` as deterministic columns:** old clients and historical evidence become indistinguishable from new results.
- **Publishing rows as they finish during a preference run:** this creates the mixed snapshot forbidden by D-16/D-19.
- **Evicting `['feed']` on preference save:** this repeats the disappearing-Dashboard bug.
- **Treating pending/null as Weak:** D-20 explicitly forbids synthetic Weak.
- **Using desired preferences for active new-job/recency maintenance:** while Updating, that would mix rubric versions.
- **Scoring include keywords from the title:** the locked rule is description-only.
- **Adding the deferred watchlist-only Dashboard control:** watchlist bonus belongs in ranking; the UI-only filter is a later phase.
- **Removing OpenAI from `extract-resume`:** AI resume extraction is explicitly preserved.

## Common Pitfalls

### Pitfall 1: The “atomic” run excludes a concurrently discovered job

**What goes wrong:** A job becomes visible under the old revision after the new run's expected set was captured, then disappears or retains the old rubric at promotion.

**How to avoid:** Finalization must lock per-user ranking state, check for missing current open/active rows, seed missing items and return “not ready,” and require revision CAS for incremental publishers. A stale incremental worker must fail after active revision advances.

### Pitfall 2: Recency points never expire

**What goes wrong:** Stored scores remain ten points too high after the 24-hour boundary.

**How to avoid:** Record evaluation time and enqueue deterministic maintenance at `posted_at + 24h`; verify tier transitions around both threshold boundaries.

### Pitfall 3: Editable rubric totals appear valid only in the browser

**What goes wrong:** A direct PostgREST/RPC caller stores malformed totals or nonmonotonic keyword steps.

**How to avoid:** Validate inside the authenticated save RPC and duplicate only friendly preflight checks in React.

### Pitfall 4: Old AI fields leak through detail or table helpers

**What goes wrong:** `JobDetail` still selects `gaps`/`reasons`, or `tierPresentation` recomputes a tier from the legacy score.

**How to avoid:** Add a static source test that active feed/page files contain none of the legacy AI projection names, except an explicitly documented migration type if unavoidable.

### Pitfall 5: The shared watchlist is accidentally redesigned

**What goes wrong:** A new user-company join changes Phase 2 behavior and ingestion ownership.

**How to avoid:** Award the direct-source point from existing `company_id`; the deferred watchlist-only UI filter remains out of scope.

### Pitfall 6: First deterministic release shows a mixed feed

**What goes wrong:** New web ships before every current owner has an active deterministic projection.

**How to avoid:** Release gate queries must prove one active complete deterministic revision for each real user and no visible row with missing deterministic score/tier/breakdown. Only then deploy the web asset that stops reading AI fields.

### Pitfall 7: No-AI proof checks only usage rows

**What goes wrong:** A provider request is made but usage accounting fails, creating a false pass.

**How to avoid:** Combine static worker-source assertions (no OpenAI import/key/generate/reservation), runtime request-budget invariance, `ai_usage purpose='score'` invariance, and a deliberately triggered worker/preference run.
