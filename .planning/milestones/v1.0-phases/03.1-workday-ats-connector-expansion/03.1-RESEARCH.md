### Scope and ordering

- **D-01:** Phase 03.1 covers **SAP SuccessFactors and Paylocity Recruiting only**. New Workday expansion is deferred.
- **D-02:** The existing fixed Capital One Workday connector remains untouched. Regression tests must prove the phase does not widen its exact identity or provider eligibility.

### Paylocity contract

- **D-04:** Paylocity uses the documented public endpoint `GET https://recruiting.paylocity.com/recruiting/v2/api/feed/jobs/{guid}`.
- **D-05:** The company GUID is derived server-side from a canonical public employer URL and validated as a strict UUID. Client-provided GUIDs, alternate origins, credentials, ports, fragments, and ambiguous paths are rejected before network access.
- **D-06:** A Paylocity observation is closure-credible only after HTTP 200, JSON content type, byte-cap compliance, well-formed root identity, a jobs array, and schema validation of every row. A malformed row degrades the whole observation for closure purposes while preserving any safely parsed rows as partial evidence.
- **D-07:** Root `displayName` is the company identity source and is cross-checked against per-job company data when present. Identity disagreement is drift and cannot authorize closure or activation.
- **D-08:** Provider job identifiers remain immutable external IDs. Re-polling the same feed must update last-seen lifecycle state without creating duplicates or overwriting first-sight snapshots.

### SuccessFactors contract

- **D-09:** SuccessFactors is not treated as one universal public API. Research must identify two or three named real employers and record the exact public host, locale, company/site identifier, list request, detail request, pagination/count behavior, and response fields for each.
- **D-10:** Only exact, server-owned employer identities may be fetched. Detection parses a supported public careers URL into an allowlist lookup; user-controlled hostnames, data-center substitutions, guessed tenant IDs, and arbitrary query endpoints are rejected.
- **D-11:** A SuccessFactors adapter may be implemented only if live proof establishes a repeatable unauthenticated JSON contract with stable external IDs, truthful company identity, complete list pagination/count reconciliation, job detail sufficient for the existing scoring pipeline, and bounded request behavior.
- **D-12:** If those conditions cannot be proven, the employer and provider disposition is `unsupported_with_reason`. The phase must not fall back to generic DOM/HTML scraping or label recognition as support.
- **D-13:** Proof for one SuccessFactors employer authorizes only that exact allowlisted identity. No tenant, host, locale, or data-center generalization occurs without its own fixtures and live evidence.

### Observation, activation, and polling safety

- **D-14:** Only a complete, positive, reconciled observation may close missing jobs. Timeouts, non-2xx responses, content-type drift, schema drift, byte/page/deadline caps, partial pagination, duplicate-path conflicts, and implausible emptiness retain prior jobs and last successful health.
- **D-15:** Provider-confirmed zero results for an established board remain `implausible_empty`; they never read as a healthy empty board without an independently justified cold-start rule.
- **D-16:** Each company must earn at least three distinct server-timed, warning-free, closure-credible verification windows before scheduled activation. Evidence is company-specific and provider-specific.
- **D-17:** Scheduling is fail-closed at both boundaries: SQL claim eligibility and application dispatch. Catalog recognition or UI activation state alone cannot authorize polling.
- **D-18:** One employer's failure, drift, or unsupported disposition cannot close another employer's jobs, delay its polling, or promote its activation.
- **D-19:** Recurring jobs use the existing scheduler and source-observation health contracts. New provider-specific cron infrastructure is prohibited unless the existing claim/dispatch model cannot express the contract and the plan documents why.

### Dashboard delivery and schema

- **D-20:** Provider jobs enter the existing `jobs` persistence, preference filter, scoring, and All/Focused feed contracts. No provider-specific frontend insertion, synthetic score, or bypass is allowed.
- **D-21:** Schema work starts after the already-shipped `0028_capital_one_recent_active.sql`; refreshed plans must not reuse migration number 0028.
- **D-22:** Production schema pushes, Edge deployments, scheduler activation, and live state mutations remain explicit owner-approved checkpoints. Local implementation and read-only public endpoint research may proceed without production mutation.

## Summary

Paylocity is implementable, but the prior assumption about identity is wrong in an important way. Official Job Feed V2 documentation calls `{guid}` a required API key. Direct proof showed that the UUID in a normal public Paylocity board URL is not that key: three current finance-company board UUIDs returned HTTP 200 placeholder roots with zero jobs, and The Only Facial's public board UUID likewise returned an empty placeholder. The Only Facial separately publishes a Job Feed key on its employer-owned site; that distinct key returned a valid 15-job V2 snapshot with descriptions, requirements, immutable job IDs, and matching company identity. `[VERIFIED: Paylocity official documentation and direct provider responses]`

Therefore Paylocity must start as an exact server-owned allowlist, not a generic UUID extractor. Detection may parse the canonical board UUID, but the Edge code must map it to a separately reviewed feed key. The valid representative is The Only Facial because its employer-owned page publishes the feed key and the live provider response is complete. A standard Paylocity board URL alone is insufficient evidence that Job Feed V2 is enabled. `[VERIFIED: direct comparison of The Only Facial board UUID d6628b21-949b-4400-a3d0-c9082bbf3eb1 and feed key f3f28b00-201d-4fba-a7dd-532a9e558191]`

SuccessFactors does not pass the owner-approved implementation gate. W. L. Gore and Statsforvalteren i Troms og Finnmark expose an undocumented JSON list POST only after an HTML/session bootstrap supplies a CSRF token. The list provides stable-looking IDs and `totalJobs`, but omits full descriptions; descriptions are available on HTML detail pages. W. L. Gore also produced a duplicate ID across sequential pages during the live proof, demonstrating that count reconciliation can drift while a board changes. Because D-11 requires a repeatable unauthenticated JSON list-and-detail contract and D-12 prohibits HTML parsing, both employers and the provider must end `unsupported_with_reason`; no executable `successfactors` provider value should be added. `[VERIFIED: direct provider responses; CITED: https://help.sap.com/docs/successfactors-platform/sap-successfactors-api-reference-guide-odata-v2/jobrequisition]`

**Primary recommendation:** implement one exact allowlisted Paylocity Job Feed V2 connector using the existing bounded observation and staged-activation architecture; record the two SuccessFactors proofs as unsupported evidence; preserve the literal Capital One Workday identity and claim branch byte-for-byte except where a new stable `paylocity` value must be added alongside existing stable providers. `[VERIFIED: codebase grep and direct provider responses]`

## Critical Planning Correction: Paylocity Has Two UUIDs

| Identity | The Only Facial value | Meaning | Safe use |
|---|---|---|---|
| Public board UUID | `d6628b21-949b-4400-a3d0-c9082bbf3eb1` | Appears in every job's public `listUrl` | Canonical board identity, `board_token`, and source-key component |
| Job Feed V2 API key | `f3f28b00-201d-4fba-a7dd-532a9e558191` | Employer-published key accepted by `/v2/api/feed/jobs/{guid}` | Server-owned allowlist value used only to construct the provider request |

The two values are not interchangeable. Calling Job Feed V2 with the public board UUID returned HTTP 200 and `{displayName: <uuid>, jobs: []}`; calling it with the feed key returned `displayName: "The Only Facial"` and 15 jobs. `[VERIFIED: direct provider responses]`

Inference: D-05 can be implemented safely only if “derived server-side” means “parse the public board identity, then resolve an exact server-owned mapping to the reviewed feed key.” If D-05 instead requires the feed key itself to be derivable from every standard Paylocity board URL, the phase is blocked by the provider contract and the decision must be amended. `[VERIFIED: official parameter label and direct negative controls]`

### Official SuccessFactors API boundary

SAP's documented `JobRequisition` and `JobRequisitionPosting` OData v2 APIs are permissioned tenant APIs. SAP documents Recruiting OData enablement, operator/template permissions, and administrator permissions such as OData API Requisition Export. Those APIs are not anonymously available to Job Copilot for arbitrary employers. `[CITED: https://help.sap.com/docs/successfactors-platform/sap-successfactors-api-reference-guide-odata-v2/jobrequisition]`

SAP officially documents Career Site Builder site URLs, including `<subdomain>.jobs.hr.cloud.sap`, but the public `/services/recruiting/v1/jobs` POST used by the observed sites is not documented as a supported integration contract. `[CITED: https://help.sap.com/docs/successfactors-release-information/8e0d540f96474717bbf18df51e54e522/8dd258ce0a0f44cdbce978e28ef64ff5.html; VERIFIED: official-documentation search]`

## Common Pitfalls

### Pitfall 1: Feed-key/board-key confusion

**What goes wrong:** verification sees HTTP 200 and zero jobs, then incorrectly accepts an empty board or claims the feed works. `[VERIFIED: direct Paylocity controls]`

**How to avoid:** require a reviewed board-to-feed-key mapping, expected root name, per-job board UUID reconciliation, and positive job evidence for activation. Empty is never closure-credible. `[VERIFIED: CONTEXT D-06/D-07/D-15]`

### Pitfall 2: SuccessFactors locale and pagination drift

**What goes wrong:** the wrong locale produces zero; live changes between pages can duplicate or omit IDs while `totalJobs` remains plausible. `[VERIFIED: Statsforvalteren locale control and W. L. Gore pages]`

**How to avoid:** do not implement this provider under the current gate. Preserve the exact proof as unsupported evidence; if a future JSON detail contract appears, fixtures must cover locale, total changes, duplicate IDs, terminal pages, and no-progress pages. `[VERIFIED: CONTEXT D-11/D-13/D-14]`

### Pitfall 3: Accidental Capital One rollback

**What goes wrong:** a new migration recreates an older stable-only claim function and stops Capital One polling, or a generalized Workday union admits other tenants. `[VERIFIED: migrations 0016 versus 0028]`

**How to avoid:** structural regression tests must assert the exact literal Workday tuple remains the sole Workday claim/dispatch identity, that `workday` is not inside a broad provider `IN` list, and that Paylocity changes no Workday adapter/filter code. `[VERIFIED: web/tests/workday-connector.integration.test.ts]`

### Pitfall 4: Partial rows accidentally authorize activation

**What goes wrong:** safe rows from a malformed snapshot get ingested, but verification records `jobCount === expectedCount` using only the safe subset. `[VERIFIED: current activation RPC contract]`

**How to avoid:** only call `record_connector_observation` for `complete`, warning-free, closure-credible results whose expected count equals normalized jobs. Partial results may be retained during scheduled polls but never advance activation. `[VERIFIED: migration 0015 and verify-board]`

### Pitfall 5: Identity-free Paylocity rows
