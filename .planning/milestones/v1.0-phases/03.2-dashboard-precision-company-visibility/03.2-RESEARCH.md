## User Constraints (from CONTEXT.md)

### Locked Decisions

#### Company visibility behavior
- **D-01:** The Dashboard supports hiding current-list companies and an optional preferred-companies-only view; prioritization is a filter mode, not a ranking boost or pinned section.
- **D-02:** Company visibility is session-only. It resets on Dashboard refresh/navigation and never changes matching, scoring, persistence, polling, or future ingestion.
- **D-03:** Default state shows all companies. Checked means visible; unchecked hides that company's current rows. The panel has a company-filter Reset action.
- **D-04:** The company list and autocomplete derive only from truthful company names already present in the current authorized feed. Users cannot type arbitrary companies here; genuinely new companies are added through the existing URL/watchlist flow.

#### Company control placement
- **D-05:** Controls live only on the Dashboard in an inline expandable panel above results, not in Preferences or a modal/side panel.
- **D-06:** The panel includes a search/autocomplete input, checkbox list, Reset, and Show results interaction modeled on the user's reference screenshot.

#### Entry-level preference semantics
- **D-07:** Add a user-configurable maximum required-experience preference. A value of 3 keeps jobs requiring 3 years and removes jobs whose explicit required minimum exceeds 3 years.
- **D-08:** Do not infer seniority from title words such as Senior, Lead, Manager, Director, Staff, or Principal. Filtering is based on explicit required years in the job description.
- **D-09:** Jobs with missing, ambiguous, or unparseable required-years language remain eligible.
- **D-10:** For a range such as 3–5 years, use the required minimum (3). Preferred, desired, bonus, or nice-to-have years never exclude a job.
- **D-11:** Preference changes reuse the existing per-user refilter/rescore invalidation path; the filter remains provider-neutral.

#### Dashboard precision and table layout
- **D-12:** Precision work is limited to company and score-tier filtering for this phase. Score tiers use Strong/Good/Weak toggles, all selected by default.
- **D-13:** Company visibility and tier selections compose with AND semantics: a row must match a selected tier and a visible company.
- **D-14:** Keep the existing navigation/header shell but let Dashboard use the full remaining browser width instead of the shell's current `max-w-6xl` content window.
- **D-15:** Remove Match reason from the table; the full reason content remains on job detail after the user opens a job.
- **D-16:** Add a Location column using the existing `jobs.location` feed field.
- **D-17:** Table columns are draggable/resizable. Widths persist per browser using local storage; no reset-width action is required. This is independent of the company-filter Reset action.

- **Add entry-level-only job preference filter:** Folded into D-07 through D-11. The original title-based and `3+` exclusion proposal is superseded by the owner's explicit required-years-only and `> threshold` decisions.

## Summary

Phase 03.2 should extend the existing native React table and provider-neutral `cheapFilter` path without adding a UI library, table library, parser dependency, or ingestion branch. The repository already has every required foundation: truthful company identity and `jobs.location` in `web/src/lib/feed.ts`, match reasons in `JobDetail.tsx`, a single per-user preferences row plus refilter RPC, and one source-agnostic filter call before AI scoring. [VERIFIED: `web/src/lib/feed.ts`, `web/src/pages/JobDetail.tsx`, `web/src/lib/preferences.ts`, `supabase/functions/score-tick/index.ts`]

The experience preference is the backend-critical slice. It needs migration `0030` to add a nullable, range-checked preference and extend the `user_jobs.filter_reason` check; the browser preference projection/form; `FilterPreferences`; the worker's preference projection; the pure filter; and the semantic scoring-input hash/revision. Missing any one of those seams can produce a save that appears successful but is ignored, a worker write rejected by PostgreSQL, or stale score reuse after the preference changes. [VERIFIED: `supabase/migrations/0017_preferences.sql`, `supabase/migrations/0019_user_jobs_scoring.sql`, `supabase/functions/_shared/filters.ts`, `supabase/functions/_shared/scoring-input.ts`, `supabase/functions/score-tick/index.ts`]

The dashboard slice should keep applied company state and panel draft state separate, derive company options only from loaded `FeedRow` data, and use one pure filtering pipeline for eligibility, company, tier, and sorting. Model company selection as hidden normalized keys rather than a fixed visible set: an empty hidden set naturally means “show all,” and a company introduced by the one-minute feed refresh is visible by default. The major compatibility correction is that the current `defaultVisible` predicate hides every Weak row before a Weak toggle can act; the plan must replace or refactor that pre-filter so all three selected tiers are meaningful on first render. [VERIFIED: `web/src/pages/Dashboard.tsx`, `web/src/lib/feed.ts`, approved `03.2-UI-SPEC.md`]

**Primary recommendation:** Plan three ordered slices: (1) migration + experience preference/filter contract, (2) pure dashboard state/width helpers + full-width accessible UI, and (3) integration, local regression, and an explicit migration/Edge/web rollout checkpoint. [VERIFIED: codebase dependency order and prior Phase 03/03.1 rollout pattern]

### Pattern 1: Hidden-key company selection with draft/apply state

**Use:** Canonicalize each truthful display name to a case-insensitive key for identity, alphabetize display labels with `localeCompare`, and store `appliedHiddenKeys` plus `draftHiddenKeys`. An empty hidden set means all current and future loaded companies are visible. Opening copies applied to draft; Reset clears draft; Show results copies draft to applied. [VERIFIED: D-02 through D-06 and UI interaction contract]

```typescript
// Source: approved 03.2-CONTEXT.md and 03.2-UI-SPEC.md
const companyKey = (name: string) => name.normalize('NFKC').trim().toLocaleLowerCase()

const visibleRows = eligibleRows.filter((row) => {
  const name = companyName(row)
  if (!name) return false // listFeed already enforces this; remain fail-closed
  return !appliedHiddenKeys.has(companyKey(name))
})
```

This representation prevents a background-refreshed company from being silently excluded without requiring an effect that mutates a visible-company set on every query refresh. [VERIFIED: `Dashboard.tsx` refetches every 60 seconds; UI contract requires new companies checked by default]

### Pattern 2: One pure dashboard row pipeline

**Use:** Compute company options from the entire authorized loaded feed, then compute displayed rows in a deterministic order: existing open/current/dismissed eligibility → company visibility → selected tier → sort. Company and tier are strict AND filters. [VERIFIED: D-12/D-13 and current Dashboard sorting]

```typescript
// Source: approved 03.2-UI-SPEC.md
function filterDashboardRows(rows: FeedRow[], state: DashboardFilterState) {
  return rows
    .filter((row) => baseDashboardEligible(row, state.viewAll, state.showDismissed))
    .filter((row) => isCompanyVisible(row, state.hiddenCompanyKeys))
    .filter((row) => state.selectedTiers.has(tierPresentation(row.score).label))
    .toSorted(state.sortComparator)
}
```

Do not call the current `defaultVisible` unchanged before tier filtering: it hard-codes score `>= 50`, making an initially selected Weak toggle unable to reveal Weak rows. Either replace it with a current scored-row base predicate or change its contract and tests so tier selection owns the score boundary. [VERIFIED: `feed.ts#defaultVisible`, D-12]

### Pattern 3: Conservative required-experience extraction

**Use:** Parse only explicit numeric year expressions connected to experience and confirmed as required. Treat every uncertainty as eligible. Preserve existing exclude → location → title reason precedence, then run the experience gate before routing/hashing/AI. [VERIFIED: D-07 through D-10; `filters.ts` check order; `score-tick/index.ts` survivor ordering]

Recommended grammar:

- Normalize Unicode dash/space variants and preserve enough separators to identify headings/clauses. [VERIFIED: existing Workday parser normalizes these cases in `workday.ts`]
- Recognize lower bounds in `3 years of experience`, `at least 3 years`, `minimum 3 years`, `3+ years`, `3–5 years`, and `3 to 5 years`; for a range, record the first number. [VERIFIED: D-07/D-10 and existing Workday regex precedent]
- Require nearby obligation context such as `required`, `minimum`, `at least`, `must have`, `basic qualifications`, or `minimum qualifications`, and an experience term. [VERIFIED: D-07/D-09]
- Suppress candidates inside `preferred`, `desired`, `nice to have`, `bonus`, or optional sections/clauses. [VERIFIED: D-10]
- If multiple independently required minimums are found, compare the maximum of their lower bounds to the saved cap because the posting requires all stated minima. [RECOMMENDED: conservative interpretation of D-07]
- Return no required minimum for word-only, malformed, contradictory, optional-only, or context-free year language; the job remains eligible. [VERIFIED: D-09]
- Never inspect `job.title` for seniority; the user's explicit existing exclude keywords still retain their documented behavior. [VERIFIED: D-08 and existing D-02 keyword contract]

The Capital One Workday adapter contains a useful parser precedent, but it is provider-specific, consumes provider HTML, uses strict `< 3` semantics, and treats all numeric years inside a required section as relevant. Do not import or generalize that adapter function into scoring. Build the Phase 03.2 parser over normalized `jobs.description_text` in `_shared/filters.ts` so every provider follows the same user preference. [VERIFIED: `workday.ts#requiredExperienceMinimums`, `score-tick/index.ts`]

### Pattern 5: Resizable native table with one width model

**Use:** Keep width definitions in one typed constant containing id, label, default, min, and max. Hydrate once through a guarded parser, render widths through `<colgroup>`, and calculate the table's minimum width from the current model. One focusable separator lives at the right edge of every header except Action. [VERIFIED: approved `03.2-UI-SPEC.md`]

```typescript
// Source: approved 03.2-UI-SPEC.md; localStorage failures per MDN
function loadColumnWidths(storage: Storage | undefined): ColumnWidths {
  try {
    const raw = storage?.getItem(COLUMN_WIDTHS_KEY)
    const parsed = raw ? JSON.parse(raw) : null
    return validateKnownFiniteAndClamp(parsed, COLUMN_DEFINITIONS)
  } catch {
    return defaultColumnWidths()
  }
}
```

On pointer down, capture the pointer and remember starting X/width; on move, clamp the delta; on pointer up persist; on pointer cancel restore the normal cursor/selection state and keep a valid clamped width. On keyboard input, Left/Right use 8px, Shift+Arrow 24px, and Home/End use bounds. The Score sort button and separator must be separate focus/click targets so resizing cannot sort. [VERIFIED: approved `03.2-UI-SPEC.md`; CITED: https://www.w3.org/WAI/ARIA/apg/patterns/windowsplitter/]

### Anti-Patterns to Avoid

- **Persisting company/tier state:** Do not use local/session storage, preferences, URL query state, or the database for Dashboard filters; only column widths persist. [VERIFIED: D-02/D-17]
- **Fixed visible-company set initialized after fetch:** It hides companies introduced by background refetch unless synchronized perfectly; hidden-key state makes new companies visible by default. [VERIFIED: UI contract refresh rule]
- **Arbitrary company entry:** A search input is a checklist filter, not a combobox or watchlist mutation. [VERIFIED: D-04 and copy contract]
- **Pre-filtering with score >=50:** It contradicts all-three-tiers-selected behavior by eliminating Weak before the toggle pipeline. [VERIFIED: `defaultVisible`, D-12]
- **Title seniority inference:** Do not add Senior/Lead/etc. regexes; parse explicit required years only. [VERIFIED: D-08]
- **Provider-specific experience logic:** Do not call Workday/Paylocity/etc. adapters from scoring or inspect provider/source fields. [VERIFIED: D-11 and existing worker isolation test]
- **Optional-section numeric scanning:** Searching every `N years` expression will reject jobs based on preferred experience and unrelated durations. [VERIFIED: D-09/D-10]
- **Client-only preference validation:** Direct Supabase writes can bypass the form; retain the database range check. [VERIFIED: existing preference schema security pattern]
- **Unvalidated storage hydration:** JSON shape, finite numeric values, known keys, and min/max bounds must be checked before applying widths. [CITED: https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage]
- **Widening every Shell route:** The job detail and all other pages must retain their existing centered content width. [VERIFIED: D-14 and UI contract]
- **Removing match reasons from detail/query:** Remove only the Dashboard column; `FEED_DETAIL_COLUMNS` and `JobDetail.tsx` remain the detailed reason surface. [VERIFIED: D-15]

## Common Pitfalls

### Pitfall 1: Weak is selected but impossible to display
**What goes wrong:** All three tier buttons show selected, but `defaultVisible` already discarded scores below 50. [VERIFIED: `feed.ts#defaultVisible`]
**How to avoid:** Make score tier the sole score-boundary step for scored rows; test initial Strong, Good, and Weak fixtures together. [VERIFIED: D-12]

### Pitfall 2: New feed companies inherit an accidental hidden state
**What goes wrong:** A visible-company set snapshots the first response and never includes companies arriving on the 60-second refresh. [VERIFIED: Dashboard refetch interval and UI contract]
**How to avoid:** Store hidden keys or explicitly merge new keys as visible; test an in-session feed refresh. [RECOMMENDED]

### Pitfall 3: Search mutates results before Show results
**What goes wrong:** Filtering company options or checking a box immediately changes the table, violating the draft/apply contract. [VERIFIED: UI interaction contract]
**How to avoid:** Keep search, draft selection, and applied selection distinct; Escape discards draft. [VERIFIED: UI accessibility contract]

### Pitfall 4: Optional experience causes a false rejection
**What goes wrong:** `3 years required; 5 preferred` is interpreted as a five-year minimum, or a Preferred Qualifications section is scanned as required. [VERIFIED: D-10]
**How to avoid:** Partition/suppress optional contexts before comparing required lower bounds and include adversarial table tests. [RECOMMENDED]

### Pitfall 5: The database rejects the new filter outcome
**What goes wrong:** The worker writes `experience_above_max`, but the old `user_jobs_filter_reason_check` permits only three strings. [VERIFIED: migration `0019`]
**How to avoid:** Migration `0030` extends the constraint before the worker is deployed; structural tests pin the final enum. [RECOMMENDED]

### Pitfall 6: The preference saves but the worker ignores it
**What goes wrong:** The browser column is added but the worker select/map or `FilterPreferences` type is not, so the cap becomes `undefined`/uncapped. [VERIFIED: current explicit projections]
**How to avoid:** Test the complete preference projection from browser payload through worker mapping and filter. [RECOMMENDED]

### Pitfall 7: Stale score reuse after cap changes
**What goes wrong:** The refilter RPC runs, but the semantic hash does not include the cap or the filter revision, so a passing job can reuse an input generated under a different preference. [VERIFIED: current `shouldRescore` equality contract]
**How to avoid:** Canonicalize the nullable cap in `scoringInputHash` and bump `SCORING_FILTER_REVISION`; retain the existing daily budget guard. [RECOMMENDED]

### Pitfall 8: Resize triggers score sorting
**What goes wrong:** The Score header's drag handle bubbles pointer/click/keyboard events into the sort button. [VERIFIED: current nested Score sort control]
**How to avoid:** Make sort button and separator siblings, stop the relevant handle event propagation, and test sort state separately. [RECOMMENDED]

### Pitfall 9: Storage denial breaks Dashboard render
**What goes wrong:** Accessing `window.localStorage`, parsing malformed JSON, or writing under restrictive browser policy throws. [CITED: https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage]
**How to avoid:** Wrap access/read/parse/write, validate known finite fields, clamp, and silently use defaults. [VERIFIED: approved UI contract]

### Pitfall 10: Shell route widening leaks into Job Detail
**What goes wrong:** Removing `max-w-6xl` from the shared `<main>` makes every page wide. [VERIFIED: current `Shell.tsx`]
**How to avoid:** Choose the main class from the current pathname and test `/`, `/jobs/:id`, and `/preferences`. [RECOMMENDED]

### Pitfall 11: Match reason disappears completely
**What goes wrong:** A broad data/type cleanup removes `reasons` from both list and detail or removes the detail section. [VERIFIED: shared `FeedRow` type]
**How to avoid:** Remove only the list table cell/column; assert `JobDetail` still renders “Match reasons.” [VERIFIED: D-15]

### Pitfall 12: Pointer cancellation leaves the page unselectable
**What goes wrong:** A drag interrupted by pointer-cancel/unmount leaves `user-select: none` or resize cursor state behind. [RECOMMENDED: pointer lifecycle safety]
**How to avoid:** Centralize cleanup and call it on pointer-up, pointer-cancel, and component unmount. [RECOMMENDED]

### Preference input validation

```typescript
// Source: approved 03.2-UI-SPEC.md
function parseMaximumExperience(raw: string): number | null {
  if (raw.trim() === '') return null
  const value = Number(raw)
  if (!Number.isInteger(value) || value < 0 || value > 20) {
    throw new Error('Enter a whole number from 0 to 20, or leave blank.')
  }
  return value
}
```

The same bounds must exist in PostgreSQL; HTML attributes and browser validation are not an authorization boundary. [VERIFIED: existing RLS/check pattern]
